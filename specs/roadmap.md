# 里程碑與通過條件

> 動手之前先讀 [doctrine.md](doctrine.md)（準則）與 [api.md](api.md)（契約）。

里程碑只有一種形狀：

> **W*n*：開發者能做到 ___，寫 ___ 行，而且比原本快 ___。**

通過條件一律用**使用者寫的程式碼**表達，不用內部狀態表達。子系統存在與否
不是里程碑 —— 十個子系統全部打勾而沒有人能用它，是這個專案實際發生過的事。

所有數字都是這台開發機的量測。天花板是**開發用的儀器**，不是引擎的規格；
引用時要帶機器與日期，換一台機器就重跑一次。

## ✅ W1 — 換一個字就有效

把 `THREE.InstancedMesh` 換成 `WW.InstancedMesh`，其他一行不動，得到螢幕
誤差 LOD 與空間分割剔除。

| | 條件 | |
| --- | --- | --- |
| 1 | 一個真的 Three.js 專案（不是 benchmark 場景），改一行 | ✅ [`apps/example`](../apps/example) |
| 2 | 物件數提高到原本無法接受的量級，幀時間不變 | ✅ |
| 3 | 換回 `THREE.InstancedMesh`，程式照樣跑，只是慢 | ✅ `?ww=0` |
| 4 | `raycast`、`.position`、`traverse`、後處理、陰影照舊 | ✅ |
| 5 | 沒有 `update()` 呼叫、沒有初始化步驟 | ✅ |

### `ab-native-instanced` vs `ab-ww-instanced`

真實 GPU、600 幀、**交錯執行 3 輪**取中位數。程序化內容，60,000 個 instance，
同一個種子的矩陣、同一條相機路徑、同一份材質與燈光。

| | `THREE.InstancedMesh` | `WW.InstancedMesh` | |
| --- | ---: | ---: | --- |
| 幀 p50 | 197.20 ms | **19.30 ms** | **10.2×** |
| 幀 p95 | 219.21 ms | 37.00 ms | |
| GPU | 194.90 ms | **17.68 ms** | 11.0× |
| CPU | 0.40 ms | 6.10 ms | ↑ |
| 三角形 | 30,000,001 | 2,178,381 | 13.8× |
| draw call | 2 | 27,227 | ↑ |
| 前 30 幀 | 5,727 ms | **594 ms** | 9.6× |
| GPU 記憶體 | 26.5 MB | **15.2 MB** | |

「幀時間不變」的量法是問：原生跑到同樣的幀時間能放多少物件？實測
`count=6000` → 幀 p50 **21.20 ms**。所以是 **10 倍的物件數，21.20 → 19.30 ms**。

三角形少 13.8 倍是兩個機制相乘：**剔除** 60,000 → 27,418 可見（2.2×），
**LOD** 平均 500 → 79 個三角形（6.3×）。

### CPU 的組成

6.10 ms 拆開（`stats.cpuMs` 只量 `onBeforeRender` 裡面）：

```text
剔除 + 選階        3.70 ms   29,418 個 instance，126 ns 一個
renderer 送繪製    ~0.95 ms  27,227 次
Three 的場景走訪等  ~1.4 ms
```

這個場景 GPU 受限（17.68 ms），所以 CPU 的餘裕不反映在幀時間上。

### 品質契約的實測

`__ww.verifyQuality()`，640×360，參考影像用真的 `THREE.InstancedMesh`
（最細幾何、不剔除、不選階）畫。判準是「強化版的每個像素，在參考影像的
±2 像素鄰域裡找得到相符的顏色」—— 逐像素相等會被輪廓平移的抗鋸齒差異淹沒。

| | 一般 | 加上後處理與陰影 |
| --- | ---: | ---: |
| 鄰域外的像素 | 708 / 230,400（0.307%） | 329 / 230,400（0.143%） |
| 最大未匹配色差 | 56 / 255 | 74 / 255 |
| 那些像素處的影像梯度 | 67.9 | 60.3 |
| 全域平均梯度 | 7.9 | 9.4 |

梯度比值 6–8 倍代表差異集中在**輪廓**，那是「幾何誤差 ≤ 2 像素」允許的
位移。加上 bloom 與陰影之後反而更低，因為兩者都會糊掉邊緣。

陰影驗的是「有沒有真的走到」：關掉 `rocks.castShadow` 會讓 1,840 個像素
（0.8%）改變，代表 instance 確實進了 shadow map。這條路徑沒有為它寫任何
程式碼 —— `BatchedMesh.onBeforeShadow` 會轉呼叫 `onBeforeRender`。

### 換成真實資產之後

`ab-native-real` / `ab-ww-real`：同樣的數量、種子、相機路徑與燈光，內容換成
cook 過的 Avocado（682 個三角形、7 階、albedo + normal + ORM 各 1024² BC）。

四個場景在**同一輪裡交錯**執行三次取中位數，所以程序化那一組的數字與上面
那張表略有出入（205.40 對 197.20）—— 那是不同次執行的機器狀態差異，只有
同一輪裡的四個數字彼此可比。

60,000 個 instance、spread 900：

| | 原生 | WW | |
| --- | ---: | ---: | --- |
| 程序化 幀 p50 | 205.40 ms | 18.80 ms | 10.9× |
| **真實 幀 p50** | **100.10 ms** | **7.80 ms** | **12.8×** |
| 程序化 GPU | 205.02 ms | 19.32 ms | |
| 真實 GPU | 99.46 ms | 6.25 ms | |

3,000 個 instance、spread 60（物件在螢幕上大得多）：

| | 原生 | WW | |
| --- | ---: | ---: | --- |
| 程序化 幀 p50 | 16.20 ms | 6.50 ms | 2.5× |
| 真實 幀 p50 | 11.40 ms | 6.20 ms | 1.8× |

**兩件事成立：**

1. 「換一個字」的效益在真實內容上**沒有變小**（10.9× → 12.8×）。
2. 剔除與選階的 CPU 成本與內容無關：60,000 個時 126–141 ns，3,000 個時
   91–100 ns，程序化與真實之間沒有系統性差異。矩陣數學不看貼圖。

### 真實資產反而比較便宜，而原因不是「真實」

上面每一個配置裡真實資產都比較快。這**不是**內容性質，是三件事同時不同：

| | 程序化 | 真實（Avocado） |
| --- | ---: | ---: |
| LOD0 三角形 | 500 | 682 |
| LOD0 頂點 | **1,500（非索引）** | **406（索引）** |
| 階數 | 3 | 7 |
| 最粗階 | 80 三角形 | **4 三角形** |
| 材質 | 無貼圖 | 三張 1024² BC |

頂點少 3.7 倍、最粗階少 20 倍，兩者都壓過了多出來的三張貼圖取樣。
`IcosahedronGeometry` 是非索引的，用它當基準會**高估**真實內容的幾何成本。

這一組的用途因此是「A/B 的效益在真實內容上還在不在」，而不是
「真實內容貴多少」—— 後者要控制住索引與階數才問得出來。

### 明講的不相容

| | |
| --- | --- |
| `.geometry` | 回傳內部合併後的幾何，使用者傳進來的那份在 `.sourceGeometry` |
| `.isInstancedMesh` | 沒有這個旗標（有 `.isBatchedMesh`） |
| 動態矩陣 | 靜態是宣告的（`dynamic`）。沒宣告而量到格子不划算時暫停，說出來，停下來就恢復 |

## ✅ W2 — 資產不再是門檻

三條路，同一個 API 形狀 —— 差別只在第一個參數：

```js
new WW.InstancedMesh(geometry, material, n);                     // 在 worker 裡自動產生
new WW.InstancedMesh({ lods, errors }, material, n);             // 自備
new WW.InstancedMesh(await WW.load(manifest, id), material, n);  // cook 過的
```

材質走同一條路，回傳的就是 `THREE.MeshStandardMaterial`：

```js
const material = await WW.loadMaterial(manifest, 'mesh:rock');
```

第二個參數收材質 id 或**網格 id** —— cooker 的材質命名是內部的，使用者手上
有的是網格 id，所以 `MeshEntry` 自己記著該用哪個材質（schema v3）。

| | 條件 | |
| --- | --- | --- |
| 1 | 不 cook 也有 LOD | ✅ |
| 2 | LOD 產生在 worker，不卡主執行緒 | ✅ |
| 3 | cook 過的路徑仍然可用且更快 | ✅ `@webworld/cook` |
| 4 | 缺 LOD 鏈時明確說出來，不靜默用最細的幾何 | ✅ |
| 5 | cook 出來的貼圖與材質載得進來 | ✅ `WW.loadMaterial` / `WW.loadTexture` |

### 真實資產的 LOD 鏈比程序化的短

程序化球體一律拿得到 7 階，真實資產不是 —— 簡化器停在誤差上限，而 UV 接縫
與材質邊界會擋住邊塌陷：

| | 三角形 | 階數 |
| --- | --- | --- |
| Avocado | 682 | 7 |
| DamagedHelmet | 15,452 | **4**（最後一階 3,863 → 3,258，幾乎沒簡化） |
| ToyCar | 88,837 | **4** |
| Corset | 18,324 | 7 |

**階數與三角形數無關。** 用程序化資產推論「LOD 鏈有多長」會高估真實資產，
而那個高估的方向是「以為遠處省得比實際多」。

### 自動產生的成本

一份沒處理過的密網格（`IcosahedronGeometry(1, 24)`，12,500 個三角形、非索引）：

```text
LOD 產生       39.7 ms   在 worker 裡
主執行緒付了    2.1 ms   複製一份給 worker + 把結果接回批次幾何
```

兩個數字必須分開報 —— 「在 worker 裡跑」沒有主執行緒那一項撐著就只是宣稱。

### worker 起不來的時候

worker 是**內嵌成 blob** 的（`?worker&inline`），所以沒有任何路徑要解析。
靠路徑的寫法在發布出去的套件上會壞：打包工具各自處理不同，不認得的那些
不會把 worker 檔案搬進使用者的輸出目錄，於是 404 之後靜靜退回主執行緒 ——
畫面正常，只是開場多一次卡頓，沒有紅字。

代價是需要 CSP 允許 `worker-src blob:`。不允許就走退路，並且說出來。

退路要能走，資料就必須還在。`postMessage` 的轉移是當場生效的，所以
**worker 必須先報到，主執行緒才把幾何交出去**：

```text
worker 端啟動後立刻 postMessage({ ready: true })
主執行緒收到才算可用，3 秒沒收到就當它死了
```

沒有這個握手的話，`new Worker()` 同步成功、非同步失敗的那段空窗裡，第一個
請求的緩衝區已經被轉移走了 —— 錯誤傳回來時主執行緒手上沒有資料可以重算，
那個 mesh 就永久停在最細的幾何。

### cook 值不值得

同一份資產（`mesh:rock-large`，5,120 個三角形）：

| | cook 過的 | 執行期自動產生 |
| --- | --- | --- |
| 階數 | 7 | 7 |
| 三角形 | 5120/2560/1280/512/204/80/32 | 一模一樣 |
| 誤差 | 0/.0492/.0795/.1393/.1971/.2895/.3901 | 0/.0489/.0795/.1386/.1946/.2624/.3666 |
| 產生成本 | **0 ms** | 12.8 ms（worker）+ 0.7 ms（主執行緒） |
| 額外下載 | `.wwm` 191 KB（16-bit 索引） | meshoptimizer chunk 44 KB |

鏈的形狀相同，因為執行期的預設比例與 cooker 對齊 —— 兩邊參數不同的話，
「cook 過的更快」就變成在比兩組設定而不是在比 build 時與 runtime。

所以 cook 的價值是**零產生成本、16-bit 索引、不必下載簡化器**，不是畫質。

### 三個發布的套件

| | |
| --- | --- |
| `@webworld/three` | runtime，裝進使用者的 Three.js 專案 |
| `@webworld/cook` | 離線 CLI（Node）：`npx ww-cook ./assets --out ./public/cooked` |
| `@webworld/format` | 上面兩個之間的格式契約（只有型別與常數） |

**format 必須是獨立的套件**，不能兩邊各自內聯一份 —— 內聯的話
`ASSET_SCHEMA_VERSION` 會悄悄分岔，而症狀是「cook 完載不進去」且訊息指向
錯的方向。拆出來之後 npm 的版本解析就是那個契約的守門員。

**cook 也必須與 runtime 分開**：`sharp` 與 `@gltf-transform/*` 絕不能出現
在瀏覽器的 bundle 裡。同一個套件同時提供兩者就得靠 tree-shaking 保證那件事，
而那是一個壞掉時完全沒有徵兆的保證。

`tools/package-check` 把三個都打包、裝進乾淨專案、真的跑一次 cook，比對兩邊
解析到的 `ASSET_SCHEMA_VERSION` 是否一致，最後用 esbuild 把它打包成一個網站
在瀏覽器裡跑起來。

最後那一段**只 serve 打包產出**，`node_modules` 讀不到 —— 那才是使用者網站
的樣子。它抓過一個真的會出去的 bug：worker 的 URL 被建成絕對路徑，在任何
使用者的站台上都是 404。當時的檢查全綠，因為它用 `autoLod: false`，剛好繞開
唯一會壞的那條路。

### 下載量

`apps/example` 建置後（把動態 `import()` 換成靜態的做對照）：

```text
主套件                608.7 kB   靜態 import 的話是 644.8 kB
lod-worker chunk       44.9 kB   只有走自動 LOD 才抓
lod-generation chunk   44.0 kB   只有 worker 不可用的退路才抓
```

meshoptimizer 走動態 `import()`，所以自備 LOD 鏈的專案不會下載它。

### 誤差的兩條規則

**每一階都從第 0 階簡化，不是從上一階。** `simplify()` 回傳的誤差是相對於
傳進去的網格，串接會拿到增量而不是相對 LOD0 的總誤差 —— 而品質契約講的是
「跟原始幾何差幾個像素」。實測 icosphere(3) 上串接會低估最多 23%，方向是
在太近的距離挑到太粗的階。

**丟掉被支配的階。** 簡化器對每個目標三角形數各做一次貪婪選擇，所以誤差
不保證隨階數遞增：球體會出現「第 5 階 0.3888（80 個三角形）比第 6 階
0.3709（32 個）還大」。前者同時比後者多三角形又比它不準，留著只是佔空間。
選階本身不會因此出錯，但「更粗 = 更不準」是所有下游都在假設的性質。

## ✅ W3 — 世界比記憶體大

```js
WW.worldFor(scene).stream({
  cellSize: 120,
  radius: 600,
  load(cx, cz, place) {
    for (let i = 0; i < 400; i++) place(rocks, matrix.compose(/* … */));
  },
});
```

| | 條件 | |
| --- | --- | --- |
| 1 | 長時間巡遊，記憶體漂移 ≈ 0 | ✅ |
| 2 | 使用者只回答「這格有什麼」，不碰載入時機、遲滯、優先序 | ✅ |
| 3 | 不開串流時一切照常運作，只是內容全部常駐 | ✅ |

直線走 600 個 tick，途中載入 750 格、卸載 823 格：

```text
                 開始      結束
geometries          1         1
textures            1         1
instance 數    38,400    38,400
capacity       60,000    60,000
JS heap      42.58 MB  43.23 MB
failedLoads / cancelled / pending    0 / 0 / 0
```

前四項是確定性的，那是能下結論的部分。JS heap 受 GC 時機影響，+0.65 MB
落在雜訊裡（每次載入會配一個暫存陣列）。

排程（遲滯、預算、優先序、自適應幀預算）沿用 `internal/engine` 的
`WorldStreamer`，payload 泛型化成任意型別。

**幀預算是量出來的，不是猜的。** 串流觀察這台機器安靜時的幀間隔當基準，
預算 = 基準 × 1.5。60 Hz、144 Hz、弱機器各自得到自己的值。

**`load` 是把東西交出去，不是回傳陣列。** 回傳陣列的話
`[m.makeTranslation(a), m.makeTranslation(b)]` 兩筆會指向同一個被改到最後
一次的 `Matrix4`，而重複使用暫存物件是 Three.js 到處都在做的事。
症狀是整格的東西疊在同一個點上，數量與統計全部正常。

## W4 — 兩端各自到極限

| | 條件 | |
| --- | --- | --- |
| 1 | 先有天花板數字 | ✅ 三角形那個修正過，見下 |
| 2 | 四格模型剩下三格逐一填上，附上相對天花板的位置 | ✅ 四格都有數字，含 CPU 那格的**正確**下界（見「CPU 的下界一直比錯對象」） |
| 3 | 全部用真實資產量測 | ✅ `ab-*-real`，`pnpm cook:real` |

### 天花板（`ceiling-*` 場景，2026-08-17）

| | | 怎麼量的 |
| --- | ---: | --- |
| **CPU：純讀取下界** | **208,000 instance/ms**（5 ns） | 同一批矩陣，只把 64 個位元組讀進來 |
| CPU：剔除＋選階 | **13,780 instance/ms（73 ns）** | 我們自己的迴圈，物件不在場景裡 |
| **GPU：三角形（索引）** | **490,100 三角形/ms** | 20,000 instance × 1,620 面，全畫不剔除 |
| GPU：三角形（非索引） | 146,200 三角形/ms | 同一份幾何，只是沒有焊接 |
| **GPU：繪製呼叫** | **6,424 次/ms**（156 ns） | 30,000 次 multi-draw，每次 2 個三角形 |

「剔除＋選階每毫秒幾個」不能當天花板 —— 它量的是我們自己的實作，拿來對照
永遠是 100%。純讀取下界才是這件事最快能多快，**兩者差 15 倍**。

#### ✅ 快取的排列順序要對齊走訪順序（機制層）

包圍球快取原本依 **instance 編號**存，而走訪是依**空間格順序**走的 ——
所以每一次讀都是陣列裡的隨機位置。

那在小工作量上看不出來：六萬個 instance 的快取是 960 KB，塞得進 L2。
一百萬個是 16 MB，於是每一次讀都是一次快取失誤。

把快取排成走訪順序（格子重建時一起重排，本來就是同一個時機）之後：

| 一百萬個 | 之前 | 之後 | |
| --- | ---: | ---: | --- |
| CPU 總計 | 29.787 ms | **9.596 ms** | 3.1× |
| ↳ 走訪 | 27.204 ms | **6.989 ms** | **3.9×** |
| 每個 instance | 146 ns | **37 ns** | |

25 萬個那一格的 CPU 也從 1.855 → **1.083 ms**。

**一行邏輯都沒改**，只是換了資料的排列順序。這正是機制層的形狀：同樣的
工作，做得便宜一點。

> **這個問題是「拆解對不上」才發現的。** 一百萬個時 CPU 是 26.475 ms，而
> 「逐一走訪的數量 × 先前量到的每個 59 ns」只有 6.5 ms —— 差四倍。
> 帳不平就代表我對自己的程式有錯誤理解，所以先把 `cpuMs` 拆成
> 空間格／走訪／烘焙三項。拆完才看到烘焙只花 1.8 ms（我原本猜是它），
> 27.2 ms 全在走訪。

#### ✅ 世界空間包圍球快取（機制層）

熱迴圈原本每個 instance 要讀 12 個矩陣元素，做九次乘加算最大縮放、再做
九次把球心轉到世界空間 —— 而那些值**只在矩陣改變時才會變**。

改成矩陣一改就算好 `[cx, cy, cz, radius]`，熱迴圈只讀 4 個 float：

| | 之前 | 之後 | |
| --- | ---: | ---: | --- |
| `ceiling-cpu` 每個 instance | 123 ns | **73 ns** | 1.7× |
| 離純讀取下界 | 30 倍 | **15 倍** | |
| `ab-ww-real`（關 HLOD） | 136 ns / 4.017 ms | **59 ns / 1.738 ms** | **2.3×** |

代價是每個 instance 多 16 個位元組，以及矩陣改變時多走一趟。

**快取失效必須跟空間格綁在一起。** `setMatrixAt` 不會動
`instanceMatrix.version`，所以只看版本號的話，用 `setMatrixAt` 的人會永遠
拿到舊的包圍球 —— 物件搬走了，剔除與選階卻還在看原本的位置。

#### 三角形天花板曾經低估 3.35 倍

原本這個場景用 `IcosahedronGeometry`，而它出廠是**非索引**的 —— 每個三角形
帶三個獨立頂點。於是它量到的是頂點吞吐，卻被當成三角形吞吐報出去。

同一份幾何，唯一的差別是有沒有焊接：

| | 三角形/ms | 頂點/ms | 每三角形頂點 |
| --- | ---: | ---: | ---: |
| 索引 | **490,100** | 253,800 | 0.52 |
| 非索引 | 146,200 | 438,600 | 3.00 |

**真實資產一律是索引的**（Avocado 682 個三角形只有 406 個頂點），所以要用
的是 490,100 那個數字。

頂點速率反而是非索引的比較高，這代表索引之後瓶頸已經不在頂點端了 ——
兩個數字都不是「硬體上限」，它們都取決於內容。所以這個場景現在**兩個都報**，
擺在一起就藏不住「這份幾何的頂點三角形比是多少」。

低估天花板的後果比高估嚴重：它會讓人以為已經接近硬體極限，於是停在不該停
的地方，而且停得理直氣壯，因為手上有數字。

### GPU 時間的組成

W1 的 A/B（2,178,381 三角形、27,227 次繪製）。這個場景的幾何是**非索引**的，
所以對照的是非索引那個天花板：

```text
三角形   2,178,381 ÷ 146,200 = 14.9 ms
繪製呼叫    27,227 ÷   6,756 =  4.0 ms   ← 21%
                              ──────
                         合計 18.9 ms（實測 17.68）
```

兩項相加大致就是全部。繪製呼叫佔 21% —— `BatchedMesh` 在 WebGPU 上是每個
可見 instance 送一次 `draw()`，不是真正的 multi-draw-indirect。

**這個比例只對這種內容成立。** 換成索引幾何，同樣的三角形數只要 4.4 ms，
於是繪製呼叫的佔比會跳到 4.0 / 8.4 ≈ **48%**。真實資產全部是索引的，所以
繪製合併在真實內容上的價值遠高於這裡看到的。

### 真實 PBR 材質的價碼

`ab-native-real`，DamagedHelmet（15,452 個三角形、4 階），3,000 個 instance、
spread 300。這是最乾淨的量法：**單一 draw call、全部在 LOD0**，三角形數是
精確的而不是從 LOD 分佈估的。

```text
3,000 × 15,452  =  46,356,000 個三角形
GPU 162.51 ms   →     285,000 三角形/ms
天花板（索引、無貼圖）    490,100 三角形/ms
```

**58% 的天花板，也就是真實 PBR 材質讓每個三角形貴 1.72 倍。** 那個倍數裡
有三件事還沒拆開：三張 1024² 貼圖的取樣、法線貼圖需要的切線屬性、以及
48 位元組的頂點（天花板場景是 position + normal + uv）。

同一份內容換成 `WW.InstancedMesh`：

| | 原生 | WW | |
| --- | ---: | ---: | --- |
| 幀 p50 | 165.10 ms | **22.00 ms** | **7.5×** |
| GPU | 162.51 ms | 21.82 ms | |
| 三角形 | 46,356,000 | 約 4,872,000 | 9.5× |

繪製呼叫在這裡幾乎不算數：1,390 次 ÷ 6,424 = 0.22 ms，佔 1%。

**所以「三角形與繪製呼叫誰重要」也是內容決定的**：輕幾何（Avocado 682 個
三角形，60,000 個）是繪製呼叫，重幾何（Helmet 15,452 個）是三角形。這正是
第 3 條說的「哪個比較大不是該修哪個」—— 兩端都要各自到它自己的極限。

### 繪製呼叫值多少錢

`ceiling-gpu-drawcalls` 有對照組：**同樣的幾何、同樣的擺放、同樣 30,000 個
instance**，只差送法。

| | 幀 p50 | GPU | 幀 p95 |
| --- | ---: | ---: | ---: |
| 30,000 次繪製（`BatchedMesh`） | 6.35 ms | **5.62 ms** | **12.71 ms** |
| 1 次繪製（`InstancedMesh`） | 6.10 ms | **0.61 ms** | 6.50 ms |

**每次繪製 167 ns，佔那個場景 GPU 時間的 89%。而 p95 直接翻倍** —— 網站上
那個比 p50 重要。

同一組場景在 WebGL2 上（`--param forceWebGL=1`）：

| | 幀 p50 | GPU |
| --- | ---: | ---: |
| 30,000 次繪製 | 18.75 ms | 6.29 ms |
| 1 次繪製 | 6.10 ms | 1.28 ms |

**GPU 差額 5.01 ms，與 WebGPU 完全相同。** 所以 167 ns 是硬體與驅動的每次
繪製成本，不是某個 backend 的產物 —— 換 backend 換不掉。兩邊只有 CPU 側
差很多（18.75 對 6.35），那是 WebGPU 的迴圈比 WebGL2 的退路便宜。

這個場景裡**每一次繪製的 index range 都相同**，所以 167 ns 是固定的每次開銷，
不是幾何切換的成本。推論：**按 LOD 階排序不會有幫助，只有減少次數才有用。**
（先量再做省下的就是這種工。）

W1 的 A/B 有 27,227 次繪製 → 4.55 ms。

### 為什麼還沒做繪製合併

`WW.InstancedMesh` 的所有 instance 共用同一份來源幾何，只有 LOD 階不同 ——
所以 27,227 次繪製理論上可以收斂成**階數**次（3 到 7）。把可見清單按階排序
之後，每一階就是一段連續的 instance，一次 instanced 繪製就送得完。

而且 shader 不必改：Three 的 batching node 在 WebGPU 上用 `instanceIndex`
去查 `_indirectTexture`，而 `firstInstance` 會把 `instanceIndex` 平移到該段
的起點，查表結果剛好正確。

**卡在 Three 的 backend。** `WebGPUBackend.draw()` 對 `isBatchedMesh` 的分支
是每個 instance 一次 `drawIndexed(counts[i], 1, …)` ——`instanceCount` 寫死
是 1，而那個分支排在 indirect draw 的 `else if` 之前，所以 BatchedMesh 永遠
走不到 `geometry.setIndirect()` 那條路。

三條路，都不是這一層能自己決定的：

| | |
| --- | --- |
| 上游修 Three | 在那個迴圈裡把相同 `(start, count)` 的連續段合併成一次 instanced 繪製。約十行，而且**每一個 BatchedMesh 使用者都受益** |
| 自己畫 | 不再是 `BatchedMesh`，於是 `instanceof`、raycast、後處理全部要自己重來 —— 那正是 ADR 0001 用掌控權換相容性時說好要付的代價 |
| 接受並寫下來 | 現在這樣 |

#### 做完 HLOD 之後這題就結束了

當初的判斷是「先做 HLOD，做完重量一次再決定」。量完的結果是**不要動**：

| | 繪製次數 | 佔 GPU 時間 |
| --- | ---: | ---: |
| HLOD 之前 | 27,418 | **70%** |
| HLOD 之後 | 1,830 | **15%** |
| 假設自己畫 | 約 7 | — |

自己畫能再省 `(1830 − 7) × 167 ns` = **0.30 ms**。而這台機器的幀時間已經
卡在 **6.10 ms 的顯示上限**（空場景也是這個數字），所以那 0.30 ms 不但只佔
5%，還根本反映不到畫面上 —— 連驗證都驗不出來。

拿「使用者的材質、raycast、陰影全部要重寫」去換一個看不見的 0.30 ms，
差得很遠。

**先繞過去的價值就在這裡**：直接改架構的話，現在會付了全部的相容性代價，
然後發現省下的東西被顯示上限吃掉。

所以**機制層這一格暫時堵住了**，價值轉移到演算法層：減少可見 instance 數
（HLOD、遮擋剔除、impostor）同時砍掉三角形與繪製呼叫，而那完全在這一層
控制得了。

### 遠景幾乎全是繪製呼叫

把 `ab-ww-real`（Avocado、60,000 個、GPU 6.25 ms）拆開。LOD 分佈
`0/0/4/46/93/227/28522`，對應 Avocado 的 `682/341/170/68/26/9/4`：

```text
繪製呼叫  27,418 × 167 ns              = 4.58 ms
三角形    約 122,000 ÷ 490,100 tri/ms  = 0.25 ms
                                        ──────
                                   合計 4.83 ms（實測 6.25）
```

**繪製呼叫佔 73%，三角形只佔 4%。** 遠處那 28,522 個 instance 每個只有
4 個三角形，卻各自付一次完整的繪製成本 —— 送出去的錢比畫的東西貴 19 倍。

這就是 HLOD 的形狀：把一個 cell 的遠景 instance **烘成一份合併幾何**，
那個 cell 就從幾千次繪製變成一次。

### ✅ 遠景合併（HLOD）

`ab-ww-real`，Avocado、60,000 個。同一個場景開關 `hlod`：

| | 開 | 關 | |
| --- | ---: | ---: | --- |
| 繪製次數 | **1,830** | 27,418 | 15× |
| 合併格數 | 494 | 0 | |
| GPU | **2.06 ms** | 6.59 ms | 3.2× |
| 幀 p50 | **6.10 ms** | 8.60 ms | |
| **幀 p95** | **6.40 ms** | 16.20 ms | **2.5×** |
| 剔除＋選階 | **0.392 ms** | 4.017 ms | 10× |
| LOD 分佈 | 0/0/4/**46/93/227**/977 | 0/0/4/**46/93/227**/28522 | |

**畫質沒有動。** 細階的 46/93/227 兩邊完全相同 —— 該用細節的那些 instance
一個都沒被降級，被合併掉的全部來自最粗階。

CPU 少 10 倍是意料外的紅利：整格合併之後，那一格的逐 instance 視錐測試與
選階完全跳過。

#### 兩個 bug，兩個都「畫面完全正常」

**合併自己寫矩陣，被當成內容在動。** `setMatrixAt` 會把空間格標成過期，
而合併正好要寫一次 —— 於是每幀都失效，整個空間分割被當成動態內容
關掉。幀時間變差，畫面正常，沒有錯誤。是場景自我檢查抓到的，單元測試
沒看到（它們只跑一兩幀）。

**合併的距離判斷漏掉 instance 縮放。** 第一次量出來的數字更漂亮
（繪製 509 次、GPU 1.85 ms），但 LOD 分佈露餡：細階的 366 個掉到 22 個。
逐一判斷用的是「縮放 ÷ 距離」，合併若只用「1 ÷ 距離」就等於把物件當成小了
25 倍，於是提早合併 —— **那不是變快，是偷偷降畫質，而且效能數字更好看**。

第二個特別危險：只看幀時間的話會直接當成成功。

#### 代價

| | |
| --- | --- |
| 記憶體 | 合併等於把最粗階複製一份。超過 `hlodBudgetMB`（預設 64）就不啟用，並且說出來 |
| 剔除粒度 | 合併過的格子只剩 cell 層級的視錐剔除，沒有逐 instance 的。那些格子本來就遠、螢幕上很小 |
| 重建 | 矩陣一改就要重烘。舊的會先拆掉（`deleteGeometry`／`deleteInstance`），不會愈積愈多 |

而這件事完全不需要 Three 改任何東西 —— `BatchedMesh` 本來就支援多份幾何，
而且 `setInstanceCount()` 與 `setGeometrySize()` 都是公開 API，所以 LOD 鏈
從 worker 回來之後還能把容量長大。

形狀（還沒實作）：

```text
lodReady 之後
  每個 cell 烘一份合併幾何 = 該 cell 全部 instance 的最粗階，變換烘進頂點
  addGeometry(merged) + addInstance()，矩陣是 cell 中心
collect() 裡
  該 cell 的每個 instance 都會挑最粗階  →  只送那一次合併繪製，跳過整個 cell
  否則                                  →  照現在逐 instance 送
```

**代價是記憶體，而且必須有預算。** 合併幾何等於把最粗階複製 N 份：Avocado
的最粗階只有 4 個三角形，60,000 份仍然很小；DamagedHelmet 的最粗階是 3,258
個，同樣份數就爆了。所以超過預算就不啟用 HLOD，並且**說出來** —— 靜靜不啟用
的話，使用者會以為自己拿到了它。

### 容量掃描：這台硬體到底放得下多少

**幀時間會飽和，容量不會。** 這台機器的幀時間卡在 6.10 ms 的顯示上限
（空場景也是這個數字），所以「多快」問到某個點就問不下去了。改成問
**「維持流暢的前提下放得了多少東西」**，那個數字永遠有下一個量級可以問。

`ab-ww-real`（Avocado + 完整 PBR），一路往上加：

| instance | 幀 p50 | GPU | 繪製次數 | 合併格數 | CPU/instance |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 60,000 | **6.10 ms** | 2.04 ms | 2,094 | 494 | 14 ns |
| 250,000 | **9.60 ms** | 6.60 ms | 10,980 | 1,925 | **9 ns** |
| 1,000,000 | **23.90 ms** | 20.86 ms | 81,592 | 7,442 | **9 ns** |

CPU 分項（一百萬個）：空間格 0.666 + 走訪 2.695 + 烘焙 0.967 = **4.336 ms**。

**一百萬個那一格要暖機 900 幀。** 遠景合併是惰性烘的，每幀 2 ms 的預算，
而 15,876 格要烘十幾秒。暖機 120 幀時量到 40.20 ms，900 幀時 **23.90 ms** ——
兩個都是真的，但前者量的是暖機途中。

那個十幾秒**不只是量測問題，是真實的使用者體驗**：網站載入後有十幾秒是慢的。
下一步是把烘焙搬進 worker（它是純陣列運算，可以轉移），那樣預算才能開大。

**250,000 個帶完整 PBR 材質的物件維持在顯示上限附近。**

#### 掃描抓到一道自己造成的懸崖，修了兩次

第一次掃的時候一百萬個是 **100.85 ms，而合併格數是 0**。

記憶體預算原本是「全有或全無」：算出整份要多少，超過就**一格都不合併**。
於是 250,000 個好好的，一百萬個掉回 457,540 次繪製 —— 不是硬體撐不住，
是自己把功能關掉了。

| 一百萬個 | 全有或全無 | 用到為止 | **槽位池** |
| --- | ---: | ---: | ---: |
| 幀 p50 | 100.85 ms | 59.50 ms | **45.30 ms** |
| 合併格數 | 0 | 3,378 | **5,274** |
| 繪製次數 | 457,540 | 238,592 | **180,340** |

**第一次修**是「一格一格花到預算用完」—— 平順了，但一百萬個仍然只涵蓋
3,378 / 15,625 格。

**第二次修才對到根因**：一次烘全部格子的話，記憶體需求等於**世界有多大**。
但任何一刻真正需要合併幾何的只有**看得見的遠景**，而那個數量由視野決定。

所以改成一池固定大小的槽位反覆換內容：

```text
槽位大小 = 最大那一格的空間（大小不一的話回收後換不進去，池子會碎掉）
槽位數量 = 預算 ÷ 槽位大小
內容      = 按需要換，最久沒畫到的先回收
```

同樣 64 MB，合併格數 3,378 → **5,274**，因為槽位是重用的。

`BatchedMesh.setGeometryAt` 可以就地替換已保留範圍裡的幾何。**不能用
「刪掉再加」** —— `addGeometry` 會重用 id 但一律從 `_nextVertexStart` 往後
配，freed 的範圍要等 `optimize()` 才回收，所以那樣是會漏的。

#### 烘焙是惰性的，而且用時間當預算

收集時登記「這一格想合併」，之後在每幀 **2 ms** 的預算內烘。還沒烘好的
那幾格照原本逐 instance 送 —— 畫面完全正確，只是那幾幀還沒省到。

停下來等它烘完會變成一次卡頓，而那正好發生在**相機剛轉過去**的時候。

**預算用時間而不是「幾格」**：一格的成本差好幾個數量級（最粗階 4 個三角形
對 3,258 個），而且不同機器差很多。固定格數在小內容上浪費、在大內容上爆掉
—— 那正是準則裡說的「作者在自己機器上調好」那種常數。

> **懸崖是掃描才看得到的東西。** 只量一個工作量的話，250,000 那一格看起來
> 完美無缺，而且兩次修正都不會被發現有必要。

### 遮擋在這種內容上不值得做

先前否決遮擋剔除的那次，用的是一片散開的石頭 —— 那種內容裡根本沒有東西
擋住東西，量出來當然是「沒有價值」。所以用 **Sponza**（圖學界的標準遮擋
測試場景：室內、有牆、有柱子）重新問一次。

`occlusion-sponza`，103 個 primitive、262,267 個三角形，相機站在中庭：
幀 p50 9.30 ms、GPU **7.43 ms**。拆開對照天花板：

```text
三角形    262,267 ÷ 490,100 tri/ms = 0.54 ms
繪製呼叫      103 × 167 ns         = 0.02 ms
                                   ──────
                       幾何那一側    0.56 ms   ← 只佔 7.5%
```

**剩下的 6.9 ms 是 fragment 與材質，而那是畫在看得見的像素上的。**
被擋住的片段早就被硬體的 early-Z 丟掉了（Three 對不透明物件會由近到遠
排序，正好餵給 early-Z）。

遮擋剔除能省的**只有幾何那一側** —— 也就是最多 7.5%，而且實際上只是其中
完全被擋住的那部分。**不值得做。**

> 曾經用深度預繪製當探針，但它慢了 5.82 ms，遠超過一趟幾何該有的
> 0.54 ms —— 慢的原因不只是「多畫一趟」，而原因沒查清楚。那條路徑已經
> 從場景裡移掉了：**一條自己都不信的量測比沒有量測更糟**。上面的結論
> 來自拆解，不依賴它。

### ✅ 靜態變成宣告，門檻換成量測（2026-08-17）

原本是「矩陣連續 8 幀在變就**永久**停用空間分割」。兩個問題：8 是我訂的，
而永久停用讓載入時抖動幾幀的內容永遠拿不回空間分割 —— 畫面完全正常，
只有幀時間差。那正是 doctrine 說的「靜靜改變行為」。

改成宣告（`options.dynamic`），沒宣告時用**量出來的**帳判斷。順手量到的
第一個數字就推翻了原本的猜測：

| instance 數 | 每幀整份重建（17 幀累計） | 省下的走訪 | |
| ---: | ---: | ---: | --- |
| 2,500 | 8.16 ms | 0.10 ms | 81 倍不划算 |
| 10,000 | 16.30 ms | 0.83 ms | 20 倍 |
| 40,000 | 66.80 ms | 3.89 ms | 17 倍 |
| 160,000 | 267.64 ms | 16.63 ms | 16 倍 |

**每幀整份重建在任何規模上都不划算**，而且比例不隨規模改善。所以暫停是
對的判斷 —— 舊的門檻猜對了結論，只是沒有依據。

`HLOD_MIN_INSTANCES` 一併從 4 改成推導值 2。A/B 交錯量測（60,000 個真實
資產）：合併 494 格、槽位 1024/1024、p50 6.10 ms —— **兩邊完全相同**。
原因是空間格的目標是每格 64 個，所以這個下限只咬得到分佈的尾巴。
它值得改是因為 4 沒有論證，不是因為 4 比較慢。

### ✅ 串流期間會失去空間分割 —— 已補（用區塊表，見下面第三步）

上面那張表的直接後果：串流每載入一格就寫一批矩陣，於是載入中的每一幀
都要整份重建，而帳算不過來 → 暫停。載入停下來之後會恢復（這一版修掉了
永久停用），但**載入中就是逐 instance 走訪**。

這是機制層的洞，不是演算法層的：往格子裡塞 20 個 instance 不該需要把
10,000 個重新排序一次（doctrine 機制層第一問）。增量插入之後串流全程都
保得住空間分割。

#### 儀器先做好了：`streaming-move`（2026-08-17）

相機直線前進穿過世界，每十幀跨一格。34,459 個常駐 instance：

| | |
| --- | ---: |
| **spatial（有用到空間格的幀）** | **4.3%** |
| 平均逐一測試 / 常駐 | 32,978 / 34,459 |
| 空間格 CPU | 0.224 ms |
| 走訪 CPU | 0.988 ms |

**格子在串流全程幾乎是關著的。** 每一幀都在走訪全部三萬四千個。

#### 這個場景一開就抓到三個真的 bug

三個都是「畫面正常或幀時間正常，所以沒人看得出來」，而且三個都只有在
**內容會變動**的場景裡才浮現 —— 在那之前所有場景都是一次擺完的。

| bug | 症狀 | 為什麼靜態場景抓不到 |
| --- | --- | --- |
| `BatchedMesh` 快取的包圍球過期 | 相機走遠之後**整個物件一格都不畫**，console 一片乾淨 | 第一幀矩陣就都在了，那顆球算對了 |
| HLOD 槽位池每次重建都重配 | GPU 記憶體三秒漲 90 MB；空間格那步 0.05 → **7.38 ms**，幀 p50 **44.25 ms** 且一路變差 | 空間格只重建一次 |
| `ensureCapacity` 沒算槽位佔的 instance id | 串流丟 `Maximum item count reached`，78 幀裡 **117 格內容不見** | 容量從不成長 |

第一個的修法是關掉物件層級的視錐剔除（我們自己做的是逐 instance 的精確
剔除，外面那一層沒給我們任何東西，只帶來一顆會過期的球）。第二個是讓池子
只長大不重配。第三個是長大前先把槽位的 instance 讓出來、長大後排到新的尾巴。

#### 然後在同一條線上抓到第四個，而它比前三個嚴重

**`apps/example` 的 JS heap 是 1,005 MB。**

| | heap | 首次可見 | 外層頁面 rAF（3 秒） |
| --- | ---: | ---: | ---: |
| 這一輪開始時 | 165.6 MB | 499 ms | 128 幀 |
| 上面三個修完之後 | **1,005.7 MB** | 1,109 ms | 25 幀 |
| 修好之後 | **43.6 MB** | 407 ms | 172 幀 |

W5 記錄的是 13.8 MB —— 那是遠景合併之前量的，而合併進來之後**沒有人再看
那個數字**（site-check 只把它印出來，沒有擋）。所以 165 MB 那一步也是靜靜
發生的。

根因有兩層：

1. **記憶體估算只算了 position。** `slotBytes = 頂點數 × 12`，而帶法線與 UV
   的幾何是 32 B/頂點。低估三倍的後果是預算「看起來還很寬」，於是實際配下去
   的量是預算的好幾倍。
2. **預設預算是「要多少給多少，護欄 512 MB」。** 那在 benchmark 上是對的，
   在網站上是一張空白授權書 —— 典型的「把我這裡當成全世界」（這台開發機
   有很多顯示記憶體）。

改成 32 MB 的政策預設（不夠時說出想要多少、拿到多少），並且**讓
site-check 擋 heap**。真實 cook 過的內容在 32 MB 下拿到 1,365 / 1,395 個
槽位 —— 98%，所以頭條數字沒有變。

#### 順手學到：貴的不是「配很多槽位」，是「槽位被回收」

中途試過一個看起來更聰明的版本：池子只配「同時看得見幾格」而不是「總共
幾格」。實測否決了它 —— **繪製次數只多了 11%，GPU 卻從 2.79 漲到 7.90 ms**。

原因是 `BatchedMesh.setGeometryAt` 會把整個保留範圍標成 `needsUpdate`，所以
每一次重烘都是一次緩衝區重傳。池子剛好等於工作集時，相機一動就互相回收，
於是每幀都在重傳。一格一個槽位的話穩態下再也不烘，成本回到零。

這也是為什麼記憶體的解法是**壓小每個槽位**（槽位大小改用 `instancesPerCell`
而不是「最大那一格」，離群的大格子不再撐大每一個槽位），不是壓少槽位數。

#### 兩個機制層的優化，還不夠

| | 之前 | 之後 |
| --- | ---: | ---: |
| 空間格重建（34,000 個） | 6.047 ms | **1.189 ms**（計數排序） |
| 空間格重建（160,000 個） | 33.306 ms | **5.831 ms** |
| 整個空間格步驟（490,000 個常駐，串流） | 356 ms | **38.5 ms** |
| ↳ 其中 HLOD 重新分組 | 339 ms | **21.3 ms** |

而它省下的走訪，在 490,000 個時是 **9 ms/幀**（走訪 12.4 → 3.4 ms）。
38.5 對 9 —— 還是四倍算不過來，所以格子在串流中仍然被暫停（spatial 9%）。

**結論沒變，但變得清楚了：全份重建再快也不夠，要的是增量維護。**

#### 第一步做完了：包圍球快取只算改過的那幾段

先量再做，而量出來的第一名不是格子：**每幀走訪的 11.93 ms 裡有 6.76 ms 是在
重算全部 490,000 個包圍球**，而那一幀真正改過的不到千分之一。

改成追蹤「改過的編號區間」（最多 8 段，超過就退回整份重算）。兩個地方要
特別處理，兩個都是實測才發現的：

| | |
| --- | --- |
| `count` 每幀都在變（串流每載入一格就變一次） | 那條路原本走一般的失效 → **每幀把整份標髒**，增量等於沒做。改 count 不動任何矩陣，所以只讓格子過期 |
| 快取陣列長大時換了一塊新的 | 沒把舊的搬過去的話舊資料歸零，而半徑 0 的包圍球會被靜靜剔掉 |

| | 之前 | 之後 |
| --- | ---: | ---: |
| 包圍球（490,000 個常駐） | 6.76 ms | **3.6 ms** |
| 整個走訪 | 11.93 ms | **8.9 ms** |

剩下的 3.6 ms 幾乎全在**格子重建的那幾幀** —— 走訪順序一換，「第幾號髒了」
就對不到「快取的第幾格」，只能整份重算。要再往下就得有一張反向表。

正確性靠一組拿 Three.js 自己的 `Frustum` + `Sphere` 走世界座標的獨立實作
交叉比對：每做一次變動就比一次「該看得見的都還在嗎」。漏標一段的症狀是
畫面破洞而所有數字正常，所以這個測試自己也要驗 —— 故意把區間標窄之後它
確實會紅。

#### 第二步：不要蓋一座馬上就拆的橋

量到 p95 **31.93 ms**，而尖峰的形狀正好是一次格子重建（30 ms）。原因是恢復
的規則太急：「有一幀沒動就恢復」，而串流不是每一幀都在寫矩陣（載入本身有幀
預算）。於是**恢復 → 重建 → 又不划算 → 再暫停**，來回震盪，每一輪丟掉 30 ms。

改成要先回本：暫停期間累計「不用格子多花的走訪」，累積到超過那次重建才恢復。
兩邊都是量到的，不是幀數門檻。

中間走錯一次，而錯的地方值得記下來：**回本的帳一旦被打斷就要歸零**。第一版
讓它跨越「動了」的幀繼續累加，於是算出「該重建了」—— 但那次重建只撐得住
一幀（下一幀又有內容進來），等於花 30 ms 換一幀 6.9 ms 的節省。回本估的是
「靜下來之後每幀省多少」，而那筆錢只有在格子撐得住時才拿得回來。

| 490,000 個常駐、串流中 | 之前 | 之後 |
| --- | ---: | ---: |
| 幀 p50 | 12.15 ms | **9.55 ms** |
| 幀 p95 | 31.93 ms | **22.41 ms** |
| 重建次數（398 幀內） | 一路都在 | 16 次，而且都在暖機期 |

剩下的 p95 不是重建了 —— 是載入本身（建幾何、上傳）。那是另一件事。

#### ✅ 第三步：分割本來就在手上，不必算

前兩步都是在讓「重建」變便宜。第三步是發現那件事**根本不必做**。

空間分割的重點是「一次剔掉一整群在一起的東西」，而串流**已經知道哪些東西
在一起**了 —— 它就是照 cell 載入的，一次 `writeMatrices` 就是一格的內容，
寫在一段連續的編號上。原本的做法是把那個資訊丟掉，再用排序重建出來。

所以加了一張區塊表（`InstanceBlocks`）：邊界在寫進來的當下就知道，包圍球
在同一趟順手算完（那段記憶體本來就在手上）。每幀的成本是「測幾十顆球」。

| 490,000 個常駐、串流中 | 空間格 | 區塊表 |
| --- | ---: | ---: |
| 有做空間剔除的幀 | 4.0% | **100%** |
| 逐一測試 | 465,000 | **128,533** |
| 分割本身的 CPU | 1.5 ms（重建時 30 ms） | **0.013 ms** |
| 走訪 | 8.9 ms | **5.6 ms** |

34,000 個常駐時同樣是 100%，逐一測試 33,331 → 11,565，走訪 0.74 → 0.55 ms。

兩者是互斥的：只要有人用 `setMatrixAt` 動過區塊裡的東西，那一塊的包圍球
就過期了，整張表作廢、退回空間格。**過期的包圍球會讓一整塊憑空消失**，
所以寧可作廢也不猜。

猜錯過一次卸載的形狀：以為是「把最後一塊搬進洞裡」，實際上串流是「把洞
後面的全部往前挪」。猜錯的代價是每一次卸載都讓整張表作廢 —— 而症狀是
「加了新東西但數字沒有變好」，不是壞掉。

正確性靠一組**掃 48 個角度**的交叉比對。單一視角測不出來：只有視錐邊界
正好切在區塊邊界上時，「有沒有把 instance 的體積加進半徑」才會分岔。
把那一項拿掉之後測試確實會紅。

#### ✅ 第四步：遠景合併也接到區塊表上

分組原本掛在空間格的 cellRanges 上，所以串流走區塊表之後就沒有遠景合併了。
接上去的關鍵是**不要沿用「重建時整份重算」** —— 那 22 ms 會原封不動留著。

區塊的變動形狀是已知的：載入接在後面，卸載把洞後面的往前挪。所以分組也照著
做：前者只替新那一段建組，後者刪掉那幾組、把後面的編號整體平移。都是整數
工作，與世界大小無關。

| | 之前 | 之後 |
| --- | ---: | ---: |
| 34,000 個常駐：繪製次數 | 7,965 | **3,684** |
| 34,000 個常駐：走訪 | 0.35 ms | **0.19 ms** |
| 34,000 個常駐：GPU | 2.21 ms | **1.75 ms** |
| 490,000 個常駐：走訪 | 5.6 ms | **3.0 ms** |
| 490,000 個常駐：幀 p50 | 10.70 ms | **9.80 ms** |
| 490,000 個常駐：GPU | 10.97 ms | **9.05 ms** |

490,000 個時只合併了 14,567 個（槽位 1,365 / 可合併 7,520）。

**我當時把這寫成「卡在記憶體預算」，那是錯的。** 後來實際 A/B 才發現：

| 槽位 | 每幀合併 | 涵蓋 | 幀 p50 |
| ---: | ---: | ---: | ---: |
| 341（32 MB） | 72–81 | 17,931–20,375 | 12.15 ms |
| 2,304（512 MB） | 76–82 | 19,135–20,449 | 12.10 ms |

**槽位多 6.7 倍，合併量沒有動。** 因為限制的從來不是槽位數，是**每一幀
有幾組夠遠到整組都該用最粗階** —— 那個數字大約 80，而 341 個槽位早就夠了。

錯在哪：我拿「槽位數」跟「可合併的總組數」比（1,365 對 7,520），但後者是
**整個世界的組數**，不是這一幀的候選數。實際在用的槽位只有 188 個。
**兩個數字放在一起看起來像瓶頸，其實不是同一個量綱。**

真正的限制是合併的判準：一組要全部都夠遠才併得起來，而組的半徑越大越難
達標。所以要提高涵蓋率該調的是顆粒度與判準，不是記憶體。

### 順帶量到：槽位調大是白賺的

固定預算下，涵蓋到的 instance 數與槽位大小無關（槽位數 × 每槽位的量 =
預算 ÷ 每個 instance 的量），但**繪製次數等於槽位數**。所以調大槽位是
同樣的涵蓋、更少的繪製：

| `hlodSlot` | 每幀合併 | 涵蓋 | 平均可見 | 幀 p50 |
| ---: | ---: | ---: | ---: | ---: |
| 64（預設） | 188 | 12,014 | 77,767 | 12.70 ms |
| 256 | 79 | 19,867 | 74,066 | 12.20 ms |

代價是顆粒變粗（一組要全部達標才併），所以這不是免費的 —— 但在這份內容上
它同時改善了兩邊。**預設值還是 `instancesPerCell`，因為最佳值取決於內容的
分佈，那是開發者的旋鈕。**

接上去的過程踩到一個：烘焙那一段還在讀空間格的順序表，而區塊路徑用的是
恆等表。症狀是「分組建好了、槽位配好了、合併次數 0」—— 每一步看起來都對。

#### ✅ 第五步：搬過去的東西不必重算包圍球

卸載一格是「把洞後面的全部往前挪」，而原本那一段被整段標成髒 —— 平均是
半個世界。實際上那些 instance 的**內容完全沒變**，只是換了編號，所以快取
依編號排的時候一次 `copyWithin` 就對了（矩陣本來就是這樣搬的）。

| 490,000 個常駐 | 之前 | 之後 |
| --- | ---: | ---: |
| HLOD 分組（含包圍球） | 3.8 ms | **0.42 ms** |
| `onBeforeRender` 全部 | 6.8 ms | **3.4 ms** |

34,000 個常駐時分組 0.31 → **0.04 ms**。

#### 這個配置的幀時間不可信，CPU 才可信

490,000 那一組每次執行的常駐數在 470,000–510,000 之間跳，繪製次數 79k–94k
—— **工作量本身就差 15%**，所以幀時間的差異讀不出程式碼的差異。這一組要看
的是 `stats` 裡的 CPU 分項，那是同一份工作量下的直接量測。

（34,000 那一組穩定得多，而且它一直在顯示器的下限上，所以那一組看 GPU。）

#### 量過否決：不回收「這一幀沒畫到」的槽位

池子裝不下工作集時槽位會互相踢，而每一次重烘都要重傳整個批次緩衝。看起來
只填空槽位就好 —— 實測否決：合併次數從 248 掉到 **14**，幀時間沒有變好。
槽位會被暖機期早到的那批佔住，而它們早就不在視野裡了。

真正的限制還是記憶體預算（1,365 槽位對 7,238 組）。那是開發者的旋鈕。

#### ✅ 第六步：熱迴圈裡兩件不必做的事

還是同一個問題：**已經知道的事不要再算一次**。

1. **整段都在視錐內側時，不必逐一測那六個平面。** 區塊測試一趟同時答得出
   「碰得到嗎」與「整顆都在內側嗎」（前者比 `-radius`，後者比 `+radius`），
   而後者成立時裡面每一個都必然可見。這條只會少做事、不會少畫東西 ——
   判斷錯的方向是多測一次，不是漏掉。
2. **選階不必開根號也不必除法。** 判斷式移項到距離那一側再兩邊平方：
   每階的係數與 instance 無關，每幀算一次，迴圈裡只剩一次乘法與一次比較。

| | 之前 | 之後 |
| --- | ---: | ---: |
| 走訪（490,000 個常駐） | 3.0 ms | **2.38 ms** |
| 走訪（34,000 個常駐） | 0.198 ms | **0.16 ms** |

選出來的階完全相同 —— `ab-ww-real` 的 LOD 分佈兩邊都是 `0/0/4/46/93/227/980`。
那是這個改動唯一該驗的東西：它是恆等變換，不是取捨。

（踩到一次：先取本地參照再長大陣列，於是本地那份還指著長度 0 的舊陣列，
讀出來是 NaN，比較永遠不成立 —— **所有東西固定用第 0 階**，畫面完全正常
只是慢。單元測試抓到了。）

### ✅ 畫面級的檢查：`pnpm visual-check`（2026-08-18）

這一輪抓到的四個 bug 全都是「數字正常、畫面不對」，而 `__ww.verifyQuality()`
早就存在 —— **只是從來沒有任何東西在跑它**。跟 heap 那個數字一樣：印出來、
沒有擋（準則第八條）。

現在有 `tools/visual-check`：建 example app、開真的瀏覽器、**兩個模式各掃
八個相機角度**，取最差的那一個。參考影像是一個真的 `THREE.InstancedMesh`
畫的 —— 同一批矩陣、最細的幾何、不剔除、不選階、不合併。

兩個模式都要驗，因為靜態與串流是**兩份不同的程式碼**，而這一輪四個 bug
全部只在串流那條路上出現。

順手修掉的三件：

| | |
| --- | --- |
| `verifyQuality` 只認得建構時的容量 | 串流時活著的是 `rocks.count`，所以它比的一直是錯的數量 |
| 兩張圖之間串流還在載入卸載 | 差的就不是畫質而是內容。現在先 `stopStream` 凍住 |
| 縮放畫布會改變哪幾格夠遠 | 於是第一幀正好落在重新烘焙的中間。擷取前先跑 60 幀 |

#### 查清楚了：數字會晃 2.5 倍是因為槽位池吃不飽

同一頁、同一個角度連續量五次：**959 / 959 / 2967 / 2129 / 959**。所以不是
載入時的狀態差異，是擷取當下的差異。

原因是遠景合併的槽位遠少於可合併的格數（預設預算下是 **60 對 443**），
於是每一幀被合併的是不同的那幾格。合併與不合併**都在品質契約內**，所以
那不是畫質問題 —— 但畫面因此每一幀都不一樣，檢查就讀不出程式碼的差異。

給滿槽位之後同一個角度連續五次是 958 / 958 / 958 / 958 / 1058。

第二個原因是**烘焙沒烘完就擷取**：縮放畫布會改變哪幾格夠遠，而原本只跑
固定 60 幀。改成跑到「這一幀沒有在烘」為止 —— 判準不能用「合併數量有沒有
變」，烘看不見的那幾組時它是不動的，會提早判定穩定。

順帶量到的產品面事實：**程序化那份內容在預設預算下是一直在互相踢的**，
而換槽位內容要重傳整個批次緩衝。它的最粗階是 80 個三角形而且非索引
（cook 過的真實資產是 4 個），所以特別容易撞到 —— 正是準則說「合成內容
不具代表性」的那件事。

#### 讓它長出牙齒：內容得換成「螢幕上很大」的

修完變異之後拿兩個故意做壞的版本試，**兩個都通過**。原因是內容不對：
example 預設是兩萬個又遠又小的物件，螢幕上每個只有幾個像素，本來就全部
在最粗階 —— 選階算錯根本不動畫面。

所以把 `spread`、`size`、`orbit` 開成參數，加了**近景那兩組**（600 個、
放大 20 倍、相機拉近），那時換一階會動到成千上萬個像素：

| 故意弄壞的地方 | 舊的兩組 | 加上近景之後 |
| --- | --- | --- |
| 選階固定挑最粗的一階 | ❌ 沒反應 | ✅ 多畫 1.675% / 2.174%，兩組都紅 |
| 區塊包圍球半徑縮成 0.7 倍 | ❌ | ❌ 少畫只從 0.29% 動到 0.51% |

第二個仍然抓不到，而且原因是結構性的：整塊在畫面邊緣被剔掉只佔幾百個
像素。那一類由單元測試掃 48 個角度、拿獨立實作比可見集合來擋（那一組
確實抓得到）。**兩邊互補，缺一個都會漏。**

另外兩件也是這一輪學到的：

1. **兩個方向都要比。** 「強化版有、原生版沒有」抓多畫；「原生版有、
   強化版沒有」抓**東西不見了** —— 後者才是這個引擎最危險的錯，而且只
   在那個方向上出現。挑最差角度時看的也是它。
2. **門檻要逐個模式訂。** 統一一條線的話，最鬆的那組會把所有組拉鬆：
   靜態那組乾淨狀態就有 1.58%，近景那組是 0.18% —— 用同一條線等於把
   唯一驗得動畫質的那一組鬆了九倍。

#### 剩下那一半：第一次到某個角度時量到的值偏高

逐角度量兩輪才看得出形狀 —— **大部分角度穩到小數第三位，而每一輪會有
一兩個角度爆高，爆的是哪一個每次不同**：

```text
第 1 輪:  0.172  0.174  0.811  1.545  0.193  0.184  0.177  0.171
第 2 輪:  0.172  0.174  0.166  0.161  0.202  0.255  0.177  0.171
```

不是隨機雜訊，是**第一次到那個角度**與**再訪**的差別。所以檢查改成同一個
角度量兩次取第二次。之後近景那兩組三次執行**一字不差**（0.178 / 0.286），
串流那組落在 0.195–0.338。

排除掉的：繪圖緩衝被清掉（開 `preserveDrawingBuffer` 沒有改善）、載入時的
狀態差異（換一頁重來形狀一樣）、烘焙沒烘完（擷取前已經跑到不再烘為止）。

#### 查下去：不是槽位裝錯，是合併的涵蓋範圍還在漂

第一輪證據看起來像引擎的缺陷：**引擎的決定幾乎一模一樣，只有像素差 4.5 倍**。

| t=4.8 | 第一次 | 第二次 |
| --- | ---: | ---: |
| 少畫 | **0.848%** | **0.189%** |
| 合併次數／涵蓋 | 244／11,028 | 243／10,902 |
| 可見／走訪 | 430／11,291 | 425／11,242 |
| LOD 分佈 | 0/0/186 | 0/0/182 |

那個形態正好是先前記下來的「槽位裝的內容對不上它宣稱的那一組」。

**但再查一層就排除掉了。** 從 `drawnInstances` 直接檢查：合併的那幾筆用的
是槽位的 instance id，同一個 id 出現兩次就代表兩組宣稱同一個槽位 ——
**重複是 0**，逐一送的那些也沒有任何一個被畫兩次。所以槽位對應是好的。

真正在動的是**合併涵蓋多少**，而且在「已經跑到不再烘」之後還在動：

```text
t=8   第一次: 合併 249／11,370   逐一 123
      第二次: 合併 248／11,356   逐一  78
```

合併次數只差一，逐一送的卻少了 45 筆。所以還沒穩的是「哪些格子算夠遠」，
不是槽位的內容。

**定位再修正一次**：不是引擎畫錯，是這個狀態比我以為的更慢才收斂，而
「這一幀有沒有在烘」不足以判斷它收斂了。

#### 查到了：量測期間動畫迴圈沒有停

`capture()` 中間有 `await`（等 PNG 解碼），而動畫迴圈會在那段空檔裡繼續跑
—— 它把相機移走、重新烘遠景、改變可見格。**「同一個 t 量兩次」實際上量的
是兩個不同的狀態。**

證據：連續呼叫 `verifyQuality(8.0)` 三次，相機矩陣是 0.235566 / 0.275634 /
0.310396。停掉迴圈之後，八個角度兩輪一字不差：

```text
停之前  0.172  0.174  0.811  1.545  0.193  0.184  0.177  0.171
停之後  0.172  0.174  0.166  0.162  0.193  0.184  0.177  0.171
```

也因此前面那條「可見格數會漂」的線索是**假的**：`stats` 是在 promise
resolve 之後讀的，那時動畫迴圈已經又畫了好幾幀，所以它反映的根本不是被
擷取的那一幀。**用錯時機讀到的狀態，會長得像一條很有說服力的線索。**

修掉之後門檻從「整片壞掉」的等級（3%／梯度比 1.5）收到量到值的兩倍以內
（0.3%–0.6%），而選階那個破壞照樣紅（1.675% / 2.174%）—— 收緊沒有犧牲
鑑別力。

#### 這條線索鏈值得留著

判斷改了四次：儀器雜訊 → 疑似引擎缺陷 → 排除槽位裝錯 → 疑似空間格漂 →
其實是量測時機。**每一次都有當時看起來充分的證據**，而每一次都是再挖一層
才推翻的。停在任何一層收工，接下來都會去修一個不存在的東西。

#### 還沒做的

~~**槽位指到別人身上的那種錯，測試看不到。**~~ **已經看得到了。**

當時寫的是「要真的驗它得比對畫面」—— 而畫面比對後來做出來了，所以回頭
量了一次：把合併幾何的位置寫掉（讓它留在原點，正是「畫成別的地方的東西」）：

| | 乾淨 | 弄壞之後 |
| --- | ---: | ---: |
| 靜態 | 少畫 0.193% | **14.464%** |
| 串流 | 少畫 0.179% | **40.571%** |

兩組都遠遠超過門檻。**這一項不再是缺口。**

順帶量到四個模式的分工：近景那兩組完全沒動（0.178 / 0.286）—— 那個距離下
物件很大、挑的是細階、根本沒有東西在合併。所以**遠景那兩組驗合併，近景
那兩組驗選階**，互補而不是重複。

**走訪本身還是純量、單執行緒。** 490,000 個常駐時走訪 2.38 ms、分組 0.41 ms。
剩下的每個 instance 約 18 ns，而純粹讀過一遍的下界是 4 ns。這一格是四格模型裡的「CPU × 機制層」，
下一步是 SIMD 或 Worker。

### 四格模型

| | 演算法層 | 機制層 |
| --- | --- | --- |
| **CPU** | ✅ 剔除、LOD、分割、串流 | ✅ 量清楚了：**下界 3.74 ns／instance，實際約 25 ns／可見 instance**，差距幾乎全在那六個平面（24 次乘加）。先前寫的「4.5 倍」比錯對象了 —— 見下面那一節 |
| **GPU** | ✅ **HLOD**（繪製 15×、p95 2.5×、畫質不變）。遮擋剔除**量過否決**：幾何側只佔 7.5%，fragment 側 early-Z 已經處理掉了。impostor 待評估 | ✅ **已結案**：繪製合併卡在 Three 的 backend，但 HLOD 之後繪製只剩 15% GPU 時間，自己畫再省 0.30 ms —— 不值得付相容性 |

遮擋剔除與 GPU 驅動繪製先前被「GPU 沒問題」否決過。那個結論是用非索引、
無貼圖的程序化內容量出來的，而那種內容在兩個方向上都不具代表性 ——
**兩者都要重新評估**。

下一步的順序由內容決定，而不是由「現在哪個數字比較大」決定：

| | 誰是瓶頸 | 該做什麼 |
| --- | --- | --- |
| 輕幾何、多物件 | 繪製呼叫（索引內容約 48%） | 繪製合併 |
| 重幾何 | 三角形（只到天花板的 58%，差額是材質） | HLOD、impostor、遮擋剔除 |

兩條都要走完才算「GPU 到極限」。

## ✅ W5 — 網站跑得動

把這個套件用在網站上，而不只是 demo。幀率**量不到**這四件事，而它們才是
網站上會被感覺到的東西。

| | 條件 | |
| --- | --- | --- |
| 1 | 首次可見時間 | ✅ 429 ms（擋 3,000 ms） |
| 2 | 下載總量 | ✅ 606.9 kB（擋 800 kB） |
| 3 | 分頁記憶體 | ✅ JS heap 43.6 MB（擋 150 MB；遠景合併的槽位池佔大部分） |
| 4 | 與頁面其他內容共存 | ✅ 外層 rAF 149 幀／3 秒 |
| 5 | **看不見的時候完全停下來** | ✅ 捲出畫面後 1 幀／1.5 秒 |
| 6 | 畫面在品質契約內 | ✅ `pnpm visual-check`，靜態與串流兩條路各掃八個角度 |

**六條全部有東西擋。** 這一輪之前有兩條只是印出來 —— 而 heap 就是那樣從
13.7 MB 漲到 1,005 MB 沒人發現的（準則第八條）。

`pnpm site-check`（`tools/site-check`）量的是 **example app**，不是 benchmark
app —— 網站的指標必須用網站的形狀量。benchmark 為了量測本身載入了 overlay、
harness 與十幾個場景，那些數字對使用者沒有意義。

### 60,000 個 instance 的網站（2026-08-17）

```text
首次可見        468 ms
下載總量        601.4 kB（2 個檔案）
JS heap         13.7 MB
GPU 物件        3 個幾何、3 張貼圖
```

首次可見量的是「把第一幀交給 GPU 的時刻」，不是「像素真的出現在螢幕上」——
後者從頁面裡量不到，硬報一個數字比誠實地少報一段更糟。

### 與頁面共存

3D 在真實網站上通常只是頁面的**一塊**，而 demo 永遠是整頁一個 canvas 加
自己的 rAF 迴圈 —— 那種寫法在真實頁面上會跟頁面本身的動畫打架，而 demo
看不出來。

所以檢查把 example app 放進一個 400×300 的 iframe，外層頁面跑自己的 rAF：

```text
外層頁面的 rAF  168 幀（3 秒內）   ← 沒有被佔住
iframe 首次可見 178 ms
iframe 可見物件 27,385
畫布 400 px / 視窗 400 px          ← 沒有假設獨佔整個視窗
```

三條斷言都是「壞掉時 demo 完全正常」的那一種：外層停住代表主執行緒被吃光，
畫布比視窗寬代表假設了全螢幕，可見物件為 0 代表在非全螢幕的容器裡剔除算錯。

### 看不見的時候完全停下來

網站上的 3D 大多數時間不在視野裡（在頁面下方、在別的分頁）。套件若自己排了
`setInterval` 或 `requestIdleCallback` 去串流、去烘遠景，那些工作會在使用者
根本沒在看的時候吃他的電池 —— 而 demo 永遠看不出來，因為 demo 就是整頁一個
canvas，永遠在視野裡。

驗的是**行為不是實作**：把 iframe 設成 `display:none`（瀏覽器停掉它的 rAF），
然後看引擎的幀數有沒有繼續往前。抓 `setInterval` 的字串擋不住第三種寫法。

實測整個套件只有兩個計時器，而且都不是迴圈：worker 的三秒握手逾時，以及
裝置遺失後的重試延遲。所以「頁面不畫，引擎就完全不動」是**構造上成立**的，
而現在有一條線在守著它。

### 這一節不涵蓋什麼

寫下來免得被當成空白支票。清單一開始有四件，查下去之後剩一件 ——
**其中兩件是我列錯的**：

| | 狀態 |
| --- | --- |
| WebGL2 退路 | ✅ **一直都有驗**。`apps/example` 用的就是 `WebGLRenderer`，而 site-check 與 visual-check 都跑它 —— benchmark 才是 WebGPU。兩個後端各自有 gate |
| 同一頁兩個引擎實例 | ✅ 單元測試（相機不互相污染、兩個 scene 各自串流） |
| 慢速網路 | ✅ 單元測試（見下） |
| 真手機 | 🚫 **明確排除**，見「範圍宣告」。不是沒驗，是不在範圍內 |

### 慢速網路：網速不可控，慢下來時的行為是套件的

會出事的三種形態，而且三種在快網路上都看不出來：**佇列無限長**（相機一直
走，每格都排進去）、**卡死**（某格永遠不回來就停在那裡）、**悶著**（追不上
了而開發者從 `stats` 看不出來）。

用一個永遠不回來的 `load` 驗：同時在飛的有上限（預設 16）而不是「走過幾格
就幾個」、排隊的數量從 `stats.pending` 讀得到、放行之後接得上而且沒有失敗。

**降級是開發者的政策，但前提是引擎先把狀況講出來** —— 所以這裡驗的不是
「慢的時候還很快」，是「慢的時候不會爆、不會死、而且看得見」。

**同一頁兩個引擎實例已經驗了**（單元測試）：兩個 mesh 各自用自己的相機、
統計不互相污染；兩個 scene 各自串流、載入自己的內容，停掉一個不影響另一個。

會擔心是因為套件裡確實有模組層級的共用狀態（LOD worker 是單例、manifest
有快取）—— 那是刻意的，一個 worker 服務所有 mesh 才對。但共用狀態只要有
一份是「以為只有一個使用者」寫的，症狀就是**其中一塊套用了另一塊的相機**，
而 demo 永遠看不出來，因為 demo 只有一塊。

### 首次可見的一個發現

計時原本只加在手動推幀那條路上，而動畫迴圈另外寫了一份 render 呼叫 ——
於是永遠量不到。兩條路各寫一份是這個 app 裡最容易寫歪的地方，現在都走
同一個 `renderFrame()`。

## 範圍宣告：桌機瀏覽器

`load-material.ts` 一直指向「roadmap 的範圍宣告」，而那段從來沒有寫下來。
決定是真的做過的，只是留在腦子裡 —— 這一段補上。

### 在範圍內

桌機瀏覽器（Chrome / Edge / Firefox / Safari），WebGPU 或 WebGL2。

### 不在範圍內，而且是**明確排除**不是「還沒做到」

| | 為什麼 |
| --- | --- |
| 行動裝置的壓縮貼圖 | cooker 只產 BC 系列。手機要的是 ETC2/ASTC，那是另一條編碼管線，不是調個參數 |

**排除的是「cook 過的貼圖」這一條路，不是整個套件。** LOD、剔除、串流、
遠景合併全部與貼圖格式無關 —— 手機上自己 load 一張 PNG 給 material，
其餘功能照常。

### 宣告不等於可以靜靜壞掉

原本踩到這條線的症狀是：把壓縮資料交給不支援的 GPU，貼圖變黑或不見，
材質看起來像沒接上，而錯誤（如果有）在 renderer 深處。

現在 `loadTexture` 會先問這台裝置支不支援，不支援就**丟出例外並說清楚**
缺什麼、少了它會怎樣、可以怎麼繞。準則第 155 行講的就是這件事：
「缺前置時必須大聲說出缺什麼、少了它會怎樣」。

判準用的是 WebGL2 的三個擴充（s3tc / rgtc / bptc）。那是**代理指標**：
問得到、同步、不需要拿到使用者的 renderer，而會缺的裝置兩邊都會缺。
所以訊息講的是「這台裝置**看起來**不支援」。

### 什麼時候該重新看這條線

要支援行動裝置的話，缺的不是一個開關，是 cooker 多一條 ETC2/ASTC 的編碼
路徑加上 manifest 帶多組格式、runtime 依裝置挑一組。那是一個里程碑的量，
不是一個修補。

## W6+ — 五條軸，不是六個功能

原本這裡是一份候選清單，而清單沒有辦法回答「做完沒有」。改成 doctrine 〇
的那個形式：**每一條優化軸推到量得出來的上限，或者寫下擋住它的平台限制**。

### 五條軸現在都有數字了（2026-08-18）

按上面那個判準，**量測的部分五條都收了**：

### 下一條是「材質成本」，而且是推導出來的

判準是「離上限最遠**而且量得出來**」。四條空的軸裡：

- **材質成本**已經有數字了 —— W4 量到真實 PBR 只跑到幾何天花板的 58%，
  也就是**四成的吞吐掉在材質上**，而這條軸一行程式碼都還沒寫。
- **一個極細物件**、**大地表**都得先造內容才量得到，而「先造內容再量」
  正是準則警告的順序 —— 造出來的內容會決定量到什麼。
- **會動的東西**與核心假設衝突，該最後做（UE 自己遇到規模問題也是繞開，
  用 VAT 把會動的變回像不會動的）。

所以不是「我選材質」，是**只有材質這條軸現在量得出來**。

#### 事後補一句：內容的盤點是查出來的，不是憑印象（2026-08-18）

上面說「一個極細物件、大地表得先造內容」，那句沒問題。但順手把
`assets/source/gltf-sample` 清點了一遍之後，**會動的那條軸其實有內容**：

| | 數量 |
| --- | --- |
| 有動畫的資產 | 22 個 |
| 有骨骼蒙皮的 | 3 個（BrainStem 61,666 三角形／18 骨、CesiumMan 4,672／19 骨） |
| 最密的單一物件 | MetalRoughSpheresNoTextures 1,040,409 三角形（但那是 100 顆球，不是一個物件） |
| 真正的單一密物件 | ScatteringSkull 188,871、DragonAttenuation 134,995 |

所以：

- **會動的東西**不是內容擋住的，是「它打破其他所有優化的前提」擋住的 ——
  那是設計問題，不是素材問題。
- **一個極細物件**確實沒有內容：最密的單一物件只有 18.9 萬個三角形，而這條
  軸真正的題目是百萬級以上。而且 Sponza 已經是 103 個 primitive 各自有 LOD
  鏈，等於粗糙的叢集 LOD 已經在跑了，那次量到幾何只佔 GPU 的 7.5%。

**盤點花的時間比爭論少。**

#### 事後：這條軸的結論是「引擎在這裡沒有槓桿」（2026-08-18）

量完之後那 42% 拆成兩塊，而**兩塊都不是引擎的**：

| | 佔 GPU | 誰的 |
| --- | ---: | --- |
| 光照（shading model 本身） | ~30%，幾乎不隨距離變 | 開發者傳進來的材質 |
| 貼圖取樣 | 5%（遠）→ 33%（近） | 同上 |

引擎唯一試得出來的槓桿是「貼圖被縮小時跳過取樣」，而那個**量出來是淨虧
15–20%**（下面那一節）。原因是前提反了：被縮小的取樣本來就便宜。

所以這條軸真正的答案是：**引擎能動的不是「每個 fragment 多貴」，是「送幾個
fragment 進去」。** 那是剔除、選階、遠景合併 —— 也就是「很多物件」那條軸
已經在做的事，以及當時還沒做的**遮蔽剔除**。

（遮蔽剔除後來做了，而且量出來在這種內容上剔不到東西 —— 見本檔後面那一節。
那條軸的結論不是「還沒做」，是「做了，走不到」。）

換句話說，這條軸沒有帶出新功能，它帶出的是一把尺（`pnpm gpu-check`）和一個
把下一條軸指出來的結論。

### 第一次量到：那四成掉在哪（2026-08-18）

`ab-ww-real` 加了 `material` 參數，同一份幾何、同一條相機路徑，只換材質，
每一組與 `full` 交錯 A/B。60,000 個 Avocado：

| | 拿掉了什麼 | GPU | 對 full |
| --- | --- | ---: | ---: |
| `full` | — | 2.60–2.92 ms | — |
| `albedo` | normal + ORM 兩張貼圖 | 2.67 ms | −8% |
| `flat` | 全部貼圖，只剩 PBR 光照 | 2.61 ms | −8% |
| `basic` | 光照本身 | **1.72 ms** | **−34%** |

**貼圖不是主要成本，PBR 光照才是。** 三張 1024² BC 貼圖全部拿掉只省 8%，
而把 PBR 光照換成無光照直接省三分之一。

這推翻了一個很自然的假設 —— 「材質貴是因為貼圖取樣」。在這份內容上不是：
物件在螢幕上很小（60,000 個鋪在 spread 900），每個只有幾個像素，貼圖取樣
次數少而且 mip 命中率高；而**光照計算是每個 fragment 都要算的**。

所以這條軸該往哪走也跟著變了：不是「壓縮更兇的貼圖」，是**光照的成本要
可控**（UE 的 Quality Level 與 shading model 選擇正好在這一層）。

#### 換成近景之後整個翻過來（2026-08-18）

3,000 個、spread 60（物件在螢幕上大得多），同一組剝層：

| | 遠景（60,000／spread 900） | 近景（3,000／spread 60） |
| --- | ---: | ---: |
| `full` | 2.60–2.92 ms | 5.35–5.78 ms |
| 拿掉 normal + ORM | −8% | **−27%**（4.03 ms） |
| 再拿掉 albedo | −8% 合計 | **−33%** 合計（3.59 ms） |
| 再拿掉光照 | −34% 合計 | **−62%** 合計（2.04 ms） |

把兩份合起來看，材質成本拆成兩塊，而它們的行為完全不同：

| | 遠景 | 近景 | |
| --- | ---: | ---: | --- |
| **光照** | ~32% | ~28% | **與物件大小無關的固定稅** |
| **貼圖取樣** | ~5% | ~33% | **完全由螢幕上多大決定** |

而貼圖那一塊裡，**normal + ORM 兩張就佔了 27%，albedo 只有 6%** —— 因為
前兩張每個 fragment 都要取樣而且參與光照計算，albedo 只是乘上去。

所以這條軸有兩個獨立的旋鈕，不是一個：

1. **光照的成本**（固定稅）—— 對應 UE 的 shading model 與 Quality Level
2. **貼圖依螢幕大小降級**（隨距離變）—— 對應材質的 LOD

#### 第二個旋鈕本來以為被結構擋住，驗過之後沒有

一開始的判斷是：「遠處用便宜的材質」需要同一批 instance 裡不同 instance
用不同材質，而整個引擎建在一個 `BatchedMesh` 上（一份幾何、一次 multi-draw），
所以做不到。

**那個判斷是錯的，而且錯在把「不同材質」當成唯一的做法。** 去讀 Three 的
batching shader chunk 之後：

```glsl
// batching_vertex.glsl
mat4 batchingMatrix = getBatchingMatrix( getIndirectIndex( gl_DrawID ) );
```

**每個 instance 的世界矩陣在 vertex shader 裡本來就拿得到。** 所以逐 instance
的材質變化不需要逐 instance 的材質 —— 一份材質，在 shader 裡依那個矩陣算出
「這個 instance 在螢幕上多大」，再決定要不要取樣 normal／ORM 就好。

兩個 BatchedMesh 遷移、instance 索引會變 —— 那條路整條不必走。

#### ✅ 旋鈕二做出來了（WebGL2），而且順手挖出一個缺陷

`materialDetailPixels`：投影半徑小於這麼多像素時停止取樣 normal 與 ORM。
**預設關** —— 它會讓遠處變平，那是改變畫面，屬於開發者。

實作方式證實了前面的判斷：**一份材質就夠**。`onBeforeCompile` 注入一段
vertex 程式碼，用 `batchingMatrix` 算出這個 instance 在螢幕上多大，寫進
varying；fragment 端把三個取樣包進分支，導數在分支外算好、分支內用
`textureGrad`（`texture()` 在非均勻控制流下導數未定義）。

驗證：

| | 結果 |
| --- | --- |
| 不設定 | 完全不掛鉤子，畫面數字與之前**一字不差** |
| 門檻 0（永不觸發） | 與有貼圖的基準**完全相同** —— 注入是惰性的 |
| 替換的字串 | 直接與 Three 的 `ShaderChunk` 比對，升級後字串改了會紅 |
| 使用者原本的 `onBeforeCompile` | 接住不蓋掉 |

#### 為了驗它，gate 第一次走到有貼圖的內容 —— 然後抓到一個量測 bug

example 預設是純色材質，所以 normal/ORM 的取樣一直沒有被任何檢查走過。
加上 `?cooked=1` 之後第一次量到：**強化版與原生版差 19.7%**（純色時 0.19%），
而且**近景更糟（42.7%）**。

那個形態很像引擎的缺陷，我也照著查了：

| 排除的 | 怎麼排除的 |
| --- | --- |
| 遠景合併 | `hlod=0` 之後數字**一字不差** |
| LOD 選階 | 再加 `lodLevels=1`（只留第 0 階）之後反而略差 |
| 合併幾何丟屬性 | 批次與來源的屬性完全一樣（normal/position/tangent/uv），索引也一樣 |

**三個都不是。真正的原因是參考影像用錯幾何。**

`verifyQuality` 的參考一直是 `lods[0]` —— 模組頂層那份**程序化**幾何。而
`?cooked=1` 時強化版吃的是 cook 過的鏈，所以兩邊畫的根本是不同的形狀。
純色時看不出來（形狀相近、顏色一樣），有貼圖時就爆開。

改成 `rocks.sourceGeometry`（依定義就是「強化版拿到的那條鏈的第 0 階」）之後：

| | 修之前 | 修之後 |
| --- | ---: | ---: |
| 有貼圖・近景 | 42.7% | **0%** |
| 有貼圖・遠景 | 19.7% | **3.3%** |

**近景是 0%** —— 有貼圖、挑細階時強化版與原生版逐像素完全一致。

#### 順帶把契約的那個缺口量出來了

遠景剩下的 3.3% 是**粗階的著色漂移**，也就是 doctrine 早就寫下來的那個缺口：
「幾何誤差 ≤ 2 像素」綁的是頂點位置，**不綁法線、不綁著色**。

第一次有數字：**純色 0.19%、有貼圖 3.3%** —— 貼圖把那個缺口放大 17 倍。
缺口仍然沒有咬人（梯度比 2.5，差異集中在輪廓），但現在它是一個被守著的
數字而不是一句話。

#### 這是這一輪第四次「以為是缺陷、其實是量測」

前三次：合併涵蓋在漂（其實是動畫迴圈沒停）、可見格數會漂（其實是讀取時機）、
記憶體預算是瓶頸（其實是拿兩個不同量綱在比）。

共同形態是**證據看起來很充分，而且指向程式碼**。這次我甚至已經排除了三個
嫌疑犯才發現量尺本身是歪的。所以那條「先量再做」還要再加一句：
**先確認量尺量的是你以為的那個東西。**

#### ⛔ 省多少還量不到，而卡住的是工具不是引擎（後來推翻了 → 見本軸最後一節）

`onBeforeCompile` 是 WebGL 那條路的鉤子。`WebGPURenderer` 用 node 材質，
整條編譯路徑不經過它 —— 所以旋鈕在那邊**什麼都不會發生**。

而工具的分工正好相反：

| | 後端 | 能做什麼 |
| --- | --- | --- |
| `apps/example`（site/visual-check） | WebGL2 | 驗畫面對不對 ✅ |
| `apps/benchmark`（`pnpm bench`） | WebGPU | 量 GPU 時間 ✅ |

**實作在 WebGL 這邊，GPU 計時在 WebGPU 那邊。** 所以「開了省多少」現在量不到。

試過用 example 自己量：`step()` 只反映 CPU（GPU 是非同步的），加 `gl.finish()
也沒有拉開差距，而絕對值小到不合理 —— 那條路不成立，不是結論。

**至少它不會靜靜沒作用**：裝在 node 材質上會警告，說清楚它不會生效、
其餘功能不受影響。靜靜沒作用的症狀是「開了旋鈕但沒省」，那看起來像旋鈕沒用，
而不是沒生效 —— 兩者的下一步完全不同。

#### 這條軸的狀態

| | |
| --- | --- |
| 成本拆解 | ✅ 光照是固定 ~30% 的稅，貼圖 5%→33% 隨螢幕大小 |
| 旋鈕一（光照） | ✅ 不需要引擎做任何事 —— 材質是開發者傳進來的 |
| 旋鈕二（貼圖依大小降級） | ⛔ 量出淨虧 15–20%，**已移除** —— 見本軸最後一節 |
| 省多少 | ✅ 量到了，而答案是負的 |

#### ✅ 換了判準，然後做完了（WebGL）

本來的判準是「這個 instance 在螢幕上多大」。換成**「這張貼圖還有沒有在
貢獻細節」**，直接量 UV 的螢幕導數：

```glsl
max( length( dFdx( uv ) ), length( dFdy( uv ) ) ) < 門檻
```

三個好處：不需要 instance 的矩陣（node 那邊拿不到 `batchingMatrix`，所以
兩個後端可以共用同一個式子）、把 UV 的縮放也算進去（大物件貼圖鋪得稀時
本來就看不到細節）、導數本來就要算（`textureGrad` 需要）。

實測（有貼圖、近景）：

| | 少畫 | |
| --- | ---: | --- |
| 關 | 0% | 基準 |
| 門檻 1（永遠取樣） | **0%** | 注入是惰性的 |
| 門檻 0（永遠不取樣） | 2.6% | 有界的畫面改變 |

#### 路上三個 bug，症狀完全一樣

**「關 / 惰性 / 最大效果」三個設定量出來完全同分。** 三次都是這個症狀，
而三次的原因完全不同：

| | 為什麼沒生效 |
| --- | --- |
| 替換對象錯了 | `onBeforeCompile` 拿到的 shader **還沒展開 `#include`**，去換展開後的內容一行都對不上 |
| 比對是隱形的 | 參考影像共用**同一個材質物件**，所以材質層級的改動兩邊都套到，比不出來 |
| 編譯直接失敗 | 導數那兩行沒包在 chunk 的 `#ifdef` 裡，於是每個沒有那張貼圖的材質都編不過 |

**三個數字一模一樣本來就該當成訊號，不是巧合。** 我第一次看到時把它當成
「效果太小」，那讓後面兩個 bug 又各多花一輪。

順帶修好的：`verifyQuality` 的參考現在用 `material.clone()`（`clone()` 不會
複製 `onBeforeCompile`），所以材質層級的改動從此看得見 —— 那是這個檢查
本來就少的一塊。

#### 還沒做：node 材質

`onBeforeCompile` 是 WebGL 那條路的鉤子，`WebGPURenderer` 不經過它。所以：

- WebGPU 上這個旋鈕**還不能用**（會警告，而且 `handle.active` 讀得到）
- **省多少還是量不到** —— GPU 計時在 `pnpm bench`（WebGPU）那邊

上限已知：近景時 normal + ORM 佔 GPU 的 27%。判準已經選成兩邊共用的形式，
所以 node 那份只是把同一個式子用 TSL 再寫一次。

#### 這條軸剩下的工作

| | 狀態 |
| --- | --- |
| 旋鈕一：光照成本 | **已經滿足了** —— 材質是開發者傳進來的，他要換 shading model 或用更便宜的材質本來就可以，引擎不擋 |
| 旋鈕二：貼圖依螢幕大小降級 | 路確認可行（上面），還沒實作 |

實作的四件事，順序不能換：

1. **預設關**。少取樣 normal／ORM 會讓遠處變平 —— 那是改變畫面，屬於開發者
   （四問第一問）。門檻由開發者宣告，引擎不自己訂。
2. **兩個後端都要**。`apps/example` 是 WebGL2（site-check 與 visual-check 跑它），
   `apps/benchmark` 是 WebGPU（`pnpm bench` 跑它）。**驗證與量測分別在不同的
   後端上**，所以只做一邊等於只有一半。
3. **shader 裡的動態分支要小心導數**。`texture()` 在非均勻控制流裡的行為是
   未定義的，要用明確的 LOD。而且只有整個 warp 走同一邊才真的省得到 ——
   遠處整個物件會一致，近處不會。
4. **量到才算數**：近景那組現在 normal + ORM 佔 27%，那是這個旋鈕的上限。
#### 這個結論只對這份內容成立

物件很小是這裡的關鍵前提。**近距離、大面積的內容上貼圖取樣會反過來變成
主項** —— 那正好是 `visual-check` 的近景那兩組的形狀，而這裡還沒量過。
下一步要在那個形狀上再量一次，兩份數字合起來才知道旋鈕該長什麼樣。

### 這條軸的第一步是儀器，不是功能

UE 的做法值得照抄：它**沒有**替你決定材質多貴，它做的是把成本變成看得見
的東西（shader complexity 視圖、instruction count、sampler 數），然後給
Material Instance（同一個 shader 只換參數）與 Quality Level 當旋鈕。

那正好是四問的第一問：**會改變畫面的決定永遠是開發者的，引擎負責把成本
算出來交出去。** 所以第一步是「這個場景的材質花了多少、花在哪」，不是
「自動把材質變便宜」。

#### ⛔ 量到了，然後把整個旋鈕拿掉了

TSL 那份沒有寫。先把「省多少」量出來，因為那個問號從頭到尾沒有答案 ——
而答案是**負的**。

做法是把 GPU 計時搬到旋鈕真正生效的那條路上：example 走 WebGL2，那邊有
`EXT_disjoint_timer_query_webgl2`，可以直接問 GPU。三個設定交錯量（這台
機器的量測是雙峰的），逐輪配對：

| | 注入本身要多少 | 少取樣省多少 | **使用者拿到的** |
| --- | ---: | ---: | ---: |
| 近景（600 個大物件） | +22.8% | −2.2% | **−20.2%** |
| 遠景（20,000 個小物件） | +24.7% | −7.1% | **−15.7%** |

**兩種內容都是淨虧。** 而原因不是實作有 bug —— 是前提整個反了。

##### 前提反在哪裡

「貼圖被縮小時跳過取樣」聽起來是省，但**貼圖被縮小時本來就是便宜的那一邊**：
縮小代表取到小的 mip，而小的 mip 一直在快取裡。真正貴的是被放大的那些，
也就是這個判準一定會保留的那些。

於是它做的事是：在貴的路徑上加一個分支，去省便宜的工作。

拆開量過，成本在哪很清楚：

| | GPU 時間（近景） | |
| --- | ---: | --- |
| 原本的 `texture2D` | 12.65 ms | 基準 |
| 無條件 `textureGrad` | 13.40 ms | +6.0% —— 換取樣指令的代價 |
| 加上逐 fragment 的分支 | 15.53 ms | **+16% —— 分支本身** |

分支要 16%，而取樣佔 GPU 的上限是 27%。這個帳在任何內容上都不會正。

##### 正確的做法是不要分支

UE 在這件事上不是逐 fragment 分支，是**讓遠的東西走另一個 shader**（材質
品質階／HLOD proxy 的簡化材質）。沒有分支就沒有那 16%。

這個引擎裡遠景本來就已經被合併成獨立的繪製了，所以那份材質可以直接簡化 ——
那是這條軸真正該做的，而不是這一個。

##### 這條軸的狀態（取代前面那張表）

| | |
| --- | --- |
| 成本拆解 | ✅ 光照是固定 ~30% 的稅，貼圖 5%→33% 隨螢幕大小 |
| 旋鈕一（光照） | ✅ 不需要引擎做任何事 —— 材質是開發者傳進來的 |
| 旋鈕二（逐 fragment 分支） | ⛔ 量出淨虧 15–20%，**已移除** |
| 正確的做法（遠景另一份材質） | ⛔ 想清楚之後不做 —— 它會**讓合併變成看得見的** |

##### ⛔ 「遠景另一份材質」不做，而擋住它的是正確性不是成本

材質那條軸失敗之後留下這一句：逐 fragment 分支不行，正確的做法是**讓遠的
東西走另一份便宜的材質**（那也是 UE 的做法）。它掛在待做上很久。

先算它值多少。fill-bound 探針（幾何釘住）說遠景那組 fragment 只佔 **29%**，
而材質拆解說 normal + ORM 在遠景只佔 GPU 的 **8%**。合併的 instance 又只佔
遠景場景的三分之二 —— 所以上限大約是**那個場景的 5%**。

但真正擋住它的不是這個數字。

###### 它會讓「合併」變成看得見的

遠景合併現在是**看不見**的：一整格被烘成一份幾何送出去，而畫面上完全沒有
變化 —— 因為幾何在契約內、材質一模一樣。那正是它可以自動發生、不必問開發者
的原因。

換一份便宜的材質之後，**合併的那一瞬間物件的外觀會變**。而合併的時機是引擎
依螢幕誤差決定的，也就是相機走著走著，某一格突然變了個樣子。

那是看得見的跳動，而且是引擎自己造成的 —— 它會把一個「安靜的最佳化」變成
「會改變畫面的決定」，而按四問的第一問，那就得交還給開發者。於是它從一個
自動的東西變成一個旋鈕，而那個旋鈕值 5%。

###### 這與前面兩個「不做」是同一種判斷

| | 為什麼不做 |
| --- | --- |
| 逐 fragment 的材質降級 | 量出淨虧 15–20%（分支比省下的貴） |
| 多層 HLOD | 它要省的繪製呼叫這裡已經是 2 次了 |
| **遠景另一份材質** | **上限 5%，而且會讓合併變成看得見的** |

三個都是「照 UE 抄會做出來、但在這個機制下不划算或不正確」的東西。

##### 這把尺第一次量到的正面數字（2026-08-18）

同一份內容、同一條相機路徑，只換 `?ww=0/1`，五輪交錯：

| | 原生 | 強化版 | |
| --- | ---: | ---: | ---: |
| **近景**（600 個大物件） | 14.216 ms／3,072,002 三角形 | 12.603 ms／2,188,802 | **省 11.3%** |
| **遠景**（20,000 個） | 204.590 ms／102,400,546 三角形 | 6.511 ms／728,570 | **省 96.8%** |

遠景那組是這個套件整個存在的理由被量出來的樣子：**一億個三角形變成
七十三萬個，204 ms 變成 6.5 ms。**

但這張表裡有一個值得追的東西：**兩邊都是次線性的。** 遠景少畫 140 倍只快
31 倍，近景少畫 29% 只快 11.3%。如果純粹被幾何綁住，那兩個比例應該對得上。
對不上代表**有一塊固定的 fragment 成本**，而那一塊決定了剩下每一條軸的
上限 —— 見下一節的探針。

##### 探針的答案：這些內容是**幾何綁的**，不是 fragment 綁的（2026-08-18）

上面那個次線性追下去了。做法是把畫布邊長減半兩次（像素變 1/16），同時用
`lodLevels=1&hlod=0` 把幾何**釘住**，於是只有像素在動。釘住那組的三角形數
在三個尺寸下完全一樣，所以這個實驗自己驗證自己。

| 內容（幾何釘住） | fragment 佔 | 幾何佔 |
| --- | ---: | ---: |
| 近景・有貼圖（2,406,402 三角形） | 53% | 47% |
| 遠景・有貼圖（5,258,242 三角形） | 29% | 71% |
| 遠景・純色（5,115,002 三角形） | **7%** | **93%** |

**三種內容全部是幾何佔多數。**

###### 這推翻了我上一輪的推論

那時拿 Sponza 的「幾何只佔 GPU 的 7.5%」去推論「剩下的幾何側優化上限都很
低」。那個 7.5% 是**Sponza 的**：室內、有牆、262,267 個三角形鋪滿整個螢幕
—— 那是 fragment 綁的內容。而這個套件的題目是幾百萬個三角形的 instance，
形狀正好相反。

**一個數字的適用範圍跟數字本身一樣重要。**

###### 順帶解釋了材質那個旋鈕為什麼救不回來

它省的是 fragment 那一側，而 fragment 在遠景只佔 29%（純色 7%）。也就是
它在爭一塊本來就小的餅，卻付了一個 16% 的分支 —— 那個帳從一開始就不可能正。

###### 這個探針不能拆的東西

它分的是「跟著像素走」與「不跟著像素走」。**不跟著像素走的那一塊裡面**還
混著頂點運算、primitive setup、繪製提交、以及每幀的固定成本 —— 這支分不開
它們。所以上表能支持「幾何側值得做」，不能支持「頂點運算是瓶頸」。

要再往下拆需要另一把尺，而在有那把尺之前，那句話只能停在這裡。

##### 然後探針指到一個沒人在看的地方：**鏈見底了**（2026-08-18）

既然幾何佔多數，就去看那些三角形花在哪。遠景那組（60,000 個、程序化）：

```text
逐一畫的     10,679 個 instance     其中 10,647 個掛在**最粗階**
合併的       22,024 個 instance     485 組
三角形總數   2,598,466
```

「全部掛在最粗階」有兩種讀法，而兩種的下一步完全相反：

1. 引擎已經挑到最粗了 —— 那就沒事做了。
2. **鏈只有這麼粗，引擎想再粗也沒得挑** —— 那是開發者給的鏈在當瓶頸。

分辨的方法是接一階上去看它會不會被用到。接了一階 20 個三角形的（原本最粗
是 80 個）：

| | 三階（原本） | 四階（多接一階） |
| --- | ---: | ---: |
| 選階分佈 | 0 / 32 / 9,826 | 0 / 32 / 734 / **5,077** |
| 三角形 | 2,598,466 | **689,402** |
| GPU 時間 | 14.716 ms | **5.693 ms** |
| | | **省 61.3%** |

**是第二種。** 而且新那一階一接上去就有 5,077 個 instance 搬過去 —— 品質
契約本來就想要更粗的，只是沒得挑。

###### 這是引擎的責任，不是開發者的

品質契約是引擎在守的：只有誤差投影到螢幕 ≤ 2 像素的階才會被選。所以**多
一階不會改變畫面**，它只是讓契約有得選 —— 那不是四問第一問裡「會改變畫面
的決定」，那是引擎自己的工作。

而引擎本來就有這個能力：`autoLod` 就是在 worker 裡從一份幾何生一整條鏈。
現在的行為是「開發者給幾階就用幾階」，而給得不夠粗的時候**它什麼都不說，
只是慢 2.6 倍**。那正好是準則裡最不能接受的形態：靜靜地做得比較差。

###### cooked 那條鏈也見底

`?cooked=1&count=20000` 的選階分佈是 5 / 34 / 110 / 147 / 310 / 443 / **3,212**
—— 七階，而 75% 的 instance 掛在最粗那一階。**引擎自己生的鏈一樣不夠粗。**

所以這不是「這份示範內容沒調好」，是一個機制上的缺口。

##### 試著讓引擎自己接長鏈，然後撞到一件更基本的事（2026-08-18）

既然鏈見底、而引擎本來就有 worker 裡的簡化能力，那就讓它自己接。做出來了，
數字也漂亮：程序化那條鏈 3 階 → 7 階、2,598,466 → 551,972 個三角形，
接鏈的主執行緒成本從 101.8 ms 降到 0.3 ms（預留的量是算出來的：接上去的每
一階都比最粗那階小，所以留一份最粗階的大小就一定夠）。

**然後 `visual-check` 紅了：多畫 0.769%，門檻 0.45%。**

第一個猜測是誤差湊錯了 —— 我拿「最粗階的誤差 + 新產生的誤差」相加。改成從
第 0 階直接產生、完全不湊，**還是紅的**。第二個猜測是誤差上限太鬆，收回
0.2（跟其他地方一樣），**還是紅的**。

於是回頭問那個數字本身準不準。

###### 簡化器回報的誤差不是上界，而契約建立在它上面

真值用矢高算（icosphere 這類幾何的頂點都在同一顆球上，有封閉解）：

| 產生的階 | meshopt 說 | 真值 | |
| ---: | ---: | ---: | --- |
| 250 面 | 0.0385 | 0.0556 | 低估 1.44 倍 |
| 124 面 | 0.0599 | 0.0672 | 低估 1.12 倍 |
| 50 面 | 0.1408 | 0.2079 | **低估 1.48 倍** |
| 20 面 | 0.3344 | 0.3779 | 低估 1.13 倍 |
| 12 面 | 0.3932 | 0.5305 | 低估 1.35 倍 |

**每一階都低估。** 所以實際的契約是「≤ 大約 3 像素」而不是宣稱的 2 像素，
而這**與接長鏈無關 —— 現有的 `autoLod` 那條路一直是這樣**。接長鏈只是把
它放大到看得見：新的階誤差更大，同樣的低估比例換算成的絕對像素也更大。

###### 所以接長鏈的功能收回去了

不是因為它做不出來，是因為它**建在一個不夠準的數字上**。在那個數字變成真的
上界之前，接得越長、契約破得越明顯。

留下來的是三個順手挖到的東西：

| | |
| --- | --- |
| 塌成 0 個三角形的階 | 會讓物件在遠處**整個消失**，沒有任何錯誤。已修（下限 4 個面） |
| `unifyIndexing` 只在「從頭生」時補索引 | 接上產生的階時 `BatchedMesh` 會擋（有無索引必須一致），而那個例外丟在**沒有人 await 的 promise** 裡 —— 完全靜默 |
| `appendLodLevels` 的例外沒有人接 | 同上，現在自己接住並警告 |

###### 為什麼不是「乘個安全係數」

乘 1.5 可以讓契約成立，但 1.12–1.48 是**這一種幾何**量出來的。拿一個沒有
證明過的常數去讓所有內容都變保守，等於拿所有人的效能換我的安心。

###### ✅ 改成自己量了（2026-08-18）

`@webworld/format` 加了 `maxSurfaceDeviation`：原始網格的每個頂點到簡化後
**表面**的最近距離，取最大值。點對三角形（不是點對頂點 —— 後者便宜且保守，
但在粗 icosphere 上高估 2.8 倍，那是拿所有人的幀時間換安心），用均勻空間格
壓到 O(頂點數)。

放在 `format` 而不是 `three`：**這個數字的意思本身就是格式契約的一部分**。
`cook` 寫進 `.wwm`、`three` 讀出來選階，兩邊的定義必須一模一樣 —— 而原本
兩邊各自算，各自低估。只修一邊的症狀是「cook 過的資產比 runtime 產生的糊」，
而型別檢查對此完全沒有意見。

代價量出來了：

| | 之前 | 之後 |
| --- | ---: | ---: |
| worker 裡產生 LOD | 5.7 ms | 27.6 ms |
| 自動產生的階數 | 6 | 5 |

慢 5 倍，但它在 worker 裡，而且換到的是「契約是真的」。階數少一階是因為
量出真值之後，有一階不再比前一階更不準 —— 那種階本來就該丟掉。

驗證的方式是**拿更硬的東西比**：icosphere 的矢高有封閉解，所以那是標準答案。
測試斷言回報值永遠 ≥ 真值（低估才危險），而且不超過 1.6 倍（高估太多就只是
保守到沒用）。

###### 修完之後引擎變慢了 2.6 倍，而那是對的

誠實的誤差代表選階不再挑到太粗的階，於是三角形變多：

| 遠景（20,000 個、有貼圖） | 修之前 | 修之後 |
| --- | ---: | ---: |
| 三角形 | 728,570 | 2,945,638 |
| GPU 時間 | 6.5 ms | 16.5 ms |

看起來像退步 2.6 倍。要證明它不是，就得看**把門檻放寬回去，時間會不會回來**
（`pnpm node tools/gpu-check/contract-price.mjs`）：

| `errorPixels` | GPU | 三角形 |
| ---: | ---: | ---: |
| 2（誠實的預設） | 16.49 ms | 2,945,638 |
| 3 | 10.51 ms | 1,516,722 |
| 4 | 7.91 ms | 1,006,722 |

修正前的 6.5 ms / 728,570 落在 4 以外 —— 也就是**那時候宣稱 2 像素、實際
交付大約 4 到 5 像素**。（比誤差本身低估的 1.48 倍還多，因為遠景合併的門檻
也吃同一個數字，兩邊複利。）

所以引擎沒有變慢，是以前在虛報。而這張表把「契約多嚴」變成一個標價：要更快
就調大 `errorPixels`，而且知道自己買到什麼。那正是四問第一問 —— **會改變
畫面的決定是開發者的，引擎負責把價錢算出來交出去。**

###### 兩道 gate 都還是綠的

| | 原生 | 強化版 | |
| --- | ---: | ---: | ---: |
| 近景 | 14.305 ms | 13.092 ms | 省 8.5% |
| 遠景 | 210.144 ms | 16.583 ms | 省 92.1% |

###### 接長鏈回來了，但**是宣告的**（`extendLodChain`）

地基修好之後重做了一次。誠實的誤差把 `visual-check` 的多畫從 0.769% 壓到
**0.471%** —— 修掉了絕大部分，但門檻是 0.45%，還是差一點點。

證據是**真的分不出來**：

| | 值 | 判讀 |
| --- | ---: | --- |
| 少畫（東西不見了，最危險的方向） | 0.21% | 遠低於 0.3 的上限，沒問題 |
| 梯度比 | **11.0** | 整組最高 —— 差異集中在輪廓上，正是契約允許的那一種 |
| 多畫 | 0.471% | 抗鋸齒地板（0.193%）的 2.4 倍 |

梯度比只說明差異的**種類**，不說明**大小**。而多畫本來就是「位移超過 2 像素」
的計數。兩種解釋都成立：（a）還有殘餘的低估；（b）更多輪廓落在容忍邊界上，
於是抗鋸齒把更多像素推到界外。

所以它預設關，用 `extendLodChain: true` 宣告。

**沒有把門檻放寬到剛好讓自己過** —— 那是這個專案最不該做的事，而且這一輪
已經示範過為什麼：`visual-check` 紅的那一次，如果當時把線調鬆，就永遠不會
去問「那個誤差數字準不準」，而那才是真正的 bug。

###### ✅ 分辨出來了：是抗鋸齒，契約沒破（2026-08-18）

做法是換解析度重量（`tools/gpu-check/aa-or-error.mjs`）。關鍵不是「抗鋸齒
會變小」——真正的位移帶也會變小。關鍵是：**選階過粗這種違約不會因為多給
像素就自己好**，因為選階是依螢幕誤差的，解析度變高時引擎本來就會挑更細的階。
違約的話兩條線會撐開；沒違約的話會收斂。

| 靜態那組的多畫 | 640×360 | 1280×720 | 2560×1440 |
| --- | ---: | ---: | ---: |
| 關 | 0.438% | 0.265% | 0.135% |
| 開 | 1.366% | 0.471% | **0.152%** |

**收斂了**（串流那組同理：0.154 對 0.144）。

而 1280×720 那一格的 1.8 倍也對得上：接長鏈讓更多 instance 用到誤差接近
2 像素的階，輪廓帶從「遠小於 2 像素」變成「接近 2 像素」。按帶寬算上限是
4 倍，實測 1.8 倍 —— **是在用契約的額度，不是在超過它。**

###### 那為什麼還是預設關

因為 `visual-check` 的門檻是照**預設組態**校準的，它的價值來自靈敏度。為了
讓一個非預設的選項過而把線放寬，會讓所有人的迴歸檢查變鈍。

這跟一開始不敢開的理由**不一樣**，而那個區別重要：一開始是「不知道契約有
沒有破」，現在是「知道沒破，但不想為了它犧牲 gate 的靈敏度」。前者是風險，
後者是取捨。

而做這個實驗的動機值得記下來：當時已經有三個證據都指向「沒事」（少畫低、
梯度比最高、誤差改成量出來的），**很容易就此收工**。設計一個會反駁自己的
實驗才是把它變成結論的那一步。

###### 而重新量之後，那個標價比想像的小很多

之前那個「61%」是**用低估的誤差量出來的**（那時選階挑得太粗，所以多接一階
的效果被放大）。地基修好之後重量：

| | 關 | 開 | |
| --- | ---: | ---: | ---: |
| 程序化（三階，最粗 80 面） | 14.716 ms／2,598,466 | 10.637 ms／548,608 | **省 27.7%** |
| cook 過（七階，最粗 32 面） | 16.120 ms／2,945,638 | 16.216 ms／2,849,058 | **−0.6%，雜訊** |

**它只對「鏈真的見底」的內容有用。** cook 過的那條鏈本來就夠深，接上去的
三階幾乎選不到。這不是一個「開了就會變快」的旋鈕，它補的是一個特定的洞。

###### 而這裡冒出一個新的、更重要的問題

程序化那組三角形少了 **4.7 倍**，時間只少 **1.38 倍**。

fill-bound 探針說那份內容 93% 的成本與解析度無關，很容易把那讀成「93% 是
三角形」。**不是。** 探針量的是「跟不跟著像素走」，而那份不跟著像素走的成本
裡還混著逐 instance 與逐繪製的工作 —— 探針的說明裡就寫了它拆不開，現在有
數字證明那句話是必要的。

所以下一個要拆的是：**與解析度無關的那一塊，到底是頂點運算、還是逐 instance
的固定成本？**

###### 用 errorPixels 那三個點可以先拆一半（免費的）

那組資料是**同一份內容、同一條相機路徑，只有選階在動** —— 也就是唯一變的
就是三角形數。三個點擬合：

| `errorPixels` | 三角形 | GPU |
| ---: | ---: | ---: |
| 2 | 2,945,638 | 16.492 ms |
| 3 | 1,516,722 | 10.511 ms |
| 4 | 1,006,722 | 7.913 ms |

| | |
| --- | ---: |
| 邊際速率 | 196,305 三角形/ms |
| 外推到 0 三角形的固定成本 | **2.78 ms（佔 17%）** |

**所以 cook 那份內容裡三角形是主項（83%）**，固定成本只佔 17%。「很多物件」
那條軸在這份內容上確實已經貼著上限了。

而邊際速率 196,305 只有硬體天花板（490,100）的 40% —— 那個差距是有貼圖的
PBR 材質吃掉的，與 W4 量到的「真實 PBR 只跑到幾何天花板的 58%」是同一件事。

###### 程序化那組不能這樣拆，而且要說清楚為什麼

同樣的算法套在程序化那組（開關 `extendLodChain` 的兩個點）會得到「固定成本
9.5 ms、佔 65%」。**那個數字不能信**：開關它的時候合併的組數也跟著變了，
所以那兩點之間變的不只三角形。

兩點擬合本來就沒有餘裕檢查自己 —— 上面那組有三個點，而且中間那段與最後
那段的速率（238,909 與 196,305）互相對得上，那才是它可信的理由。

##### 留下來的是那把尺

程式碼刪了，但 `pnpm gpu-check` 留著，而且改成擋一件更基本的事：**強化版的
GPU 時間必須低於原生版**，兩種內容各有各的線。

這一側一直是空的 —— 其餘的證據全部在 CPU（幀時間、分組時間、traversal 時間），
但這個引擎做的每一件事改變的是**送給 GPU 的東西**。一個把 CPU 省下來卻讓
GPU 變貴的改動，在這道尺出現之前完全看不見。

而它第一次跑就抓到第二個東西：對照組是用**程序化**幾何建的，`?cooked=1` 時
強化版吃的是 cook 過的鏈 —— 兩邊畫的是不同的模型（300,002 vs 2,188,802 個
三角形），而那被讀成「強化版慢了兩倍」。同一個坑 `verifyQuality` 那邊踩過
一次、修好了，這裡是它的另一半。所以現在**三角形數與 GPU 時間一起報**。

## 「會動的東西」：量完了，槓桿是 VAT（2026-08-18）

### 為什麼這條軸先量再說

骨骼蒙皮打掉這個引擎的核心假設：`BatchedMesh` **不支援蒙皮**，所以批次、
LOD 鏈、遠景合併對它全部無效。UE 遇到同樣的規模問題也是繞開的 —— 用 VAT
（把動畫烘進貼圖，在 vertex shader 取樣）把會動的變回像不會動的。

但在寫 VAT 之前有兩件事必須先知道，而且兩件都得用量的：

1. 原生今天到哪裡撐不住 —— 那是起點。
2. 成本在**逐 instance** 還是在**三角形**上 —— VAT 省的是前者，如果成本
   其實在三角形上它就救不了。

### 量到的（`tools/gpu-check/skinned-scaling.mjs`）

程序化的蒙皮圓柱，每個 261 個三角形、8 根骨頭，各自有獨立骨架：

| 數量 | GPU | 繪製呼叫 | 三角形 |
| ---: | ---: | ---: | ---: |
| 50 | 2.276 ms | 49 | 13,058 |
| 200 | 2.514 ms | 186 | 50,322 |
| 800 | **7.566 ms** | **740** | 201,010 |

**繪製呼叫等於 instance 數** —— Three 對蒙皮完全不批次，一個一個送。

拆開來看 800 個那一格：

| | |
| --- | ---: |
| 三角形那一側（用實測邊際 196,305 三角形/ms 換算） | 1.02 ms |
| 剩下的（蒙皮 + 逐 instance） | **6.54 ms** |
| 每個 instance | **8.2 µs** |
| 對照：靜態那條路（20,000 個、16.5 ms） | 0.82 µs |

**每個會動的 instance 貴 10 倍，而且那 10 倍全部在逐 instance 那一側。**
201,010 個三角形對這台機器是微不足道的量（靜態批次 1 ms 就畫完），但它花了
7.57 ms —— 已經是 60 Hz 一幀的一半。

### 所以 VAT 是對的槓桿，而且上限算得出來

成本既然在逐 instance（繪製呼叫 + 骨骼矩陣上傳），VAT 正好消滅那一項：
動畫變成貼圖，網格變回靜態，於是整條批次／LOD／合併的路重新適用。

上限就是那 6.54 ms 裡的大部分 —— 換成一次貼圖取樣的成本。

### 這裡刻意沒有回答的

內容是程序化的，所以**絕對吞吐量不能從這裡推論**。真的資產在
`assets/source/gltf-sample`（22 個有動畫、3 個有蒙皮，BrainStem 61,666 個
三角形／18 根骨頭），而 `packages/cook` 目前**不處理蒙皮** —— 那是 VAT
落地的第一個前置。

邊際成本的四段（7.5 / −1.4 / 11.9 / 6.7 µs）抖得很兇，所以上面用的是頭尾
兩點的總量而不是相鄰兩點的斜率。要更細的曲線得多量幾輪，但那不影響「成本
在逐 instance 那一側」這個結論 —— 740 次繪製對 201,010 個三角形本身就夠清楚。

## 「大地表」與「一個極細物件」：其實是同一條軸（2026-08-18）

### 為什麼併在一起

一個從外面看的密物件，整顆離相機的距離差不多，所以「整顆挑一階」已經接近
最佳解 —— 逐區域選階在那種內容上賺不到什麼。真正需要它的是**跨越很大深度
範圍**的東西：腳下清清楚楚、地平線那端只有幾個像素，而它們是同一個物件。

地表是這個形狀的標準案例，所以只造一種內容就同時回答兩條軸。

### 量到的（`tools/gpu-check/terrain-tiling.mjs`）

同一片程序化地形（高度用世界座標算，所以切幾塊都是同一片），總三角形數固定，
相機貼著地面看地平線：

| 分塊 | 52 萬個三角形 | 420 萬個三角形 |
| --- | ---: | ---: |
| 4×4 | 省 23.4% | 省 14.2% |
| 8×8 | 省 21.6% | 省 31.4% |
| 16×16 | **省 2.2%** | **省 32.9%** |

**規模不夠的時候這條軸的價值量不出來**，而那不是「這條軸沒價值」。52 萬個
三角形對這台機器只值 2.7 ms，分太細反而被繪製呼叫吃掉。420 萬那一輪到
16×16 都還在往上。

第一輪我只量了 52 萬，差點就得出「分塊沒用」的結論 —— 那會是這一輪第五次
「內容不對，於是量到假的答案」。

### 缺口是 API 的形狀，不是機制

`WW.InstancedMesh(geometry, material, count)` 假設**所有 instance 共用同一份
幾何**，而地表每一塊的高度都不一樣 —— 那是 N 份相異的幾何。

但底層的 `BatchedMesh` **裝得下相異幾何** —— LOD 鏈就是這樣塞進去的。所以
擋住的是那個建構子的形狀，不是機制。

上面的數字是用「一塊一個 `InstancedMesh(count=1)`」模擬的，會付掉每塊一份
物件的開銷，所以那是**下界**：真的做進去只會更好。

### ✅ 做出來了：`WW.MultiMesh`（2026-08-18）

完全走 `BatchedMesh` 的公開介面（`addGeometry` / `addInstance` /
`setGeometryIdAt`），所以剔除與繪製合併是 Three 自己做的，而 `InstancedMesh`
那條熱迴圈**一行都沒動到**。那條迴圈是這個套件最怕出錯的地方（剔錯不會報錯，
只會破洞），為了一個形狀不同的需求去那裡加 indirection，風險與收益不成比例。

420 萬個三角形的地形，整片一份幾何是 11.606 ms：

| 分塊 | 一塊一個物件 | MultiMesh |
| --- | ---: | ---: |
| 8×8 | 7.953 ms（51 次繪製） | 7.601 ms（3 次） |
| 16×16 | 7.899 ms（173 次） | 6.462 ms（3 次） |
| 32×32 | **11.257 ms**（647 次） | **5.253 ms**（3 次） |

**重點在最後一列：一塊一個物件時，分更細反而變慢** —— 比 16×16 差，幾乎追平
整片一份幾何。繪製呼叫把剔除省下來的又吃回去了。

MultiMesh 把繪製次數釘在 3，所以分越細越賺。**它解掉的是那個天花板，不是分塊
本身** —— 分塊用 `THREE.Group` 加一堆 Mesh 就做得到，而那條路在 647 次繪製
的地方撞牆。

### 路上那個 bug 值得記下來

第一版覆寫了 `onBeforeRender` 但**沒有往上呼叫** —— 而 `BatchedMesh` 的那個
方法正是做剔除、排序、組 multi-draw 清單的地方。

結果是**一個三角形都沒畫**，而症狀是：沒有錯誤、沒有警告，**幀時間 1.589 ms
對 7.998 ms** —— 看起來像 5 倍的勝利。

抓到它的是**三角形數印在時間旁邊**（546 個，全是場景裡別的東西）。那個習慣
是今天稍早為了另一個 bug 加的，隔幾個小時就再救一次。

## 「會動的東西」做出來了：VAT（2026-08-18）

### 兩半分開做，而且刻意

| | 做什麼 | 怎麼驗 |
| --- | --- | --- |
| `bakeVertexAnimation` | 純 CPU：逐幀逐頂點算出位置，寫進一張貼圖 | 逐頂點比對，而且拿 Three 自己的 `applyBoneTransform` 當參考 |
| `AnimatedInstancedMesh` | shader 注入：從貼圖讀位置 | 注入後的字串 + 真的畫出來比對 |

分開的理由是**失效方式完全不同**：烘錯是算術錯，逐頂點驗得出來；注入錯是
畫面錯但不報錯。混在一起的話出問題時分不出是哪一半。

### 量到的

同一根 rig，一邊逐 instance 送骨骼矩陣，一邊烘成貼圖批次畫：

| 數量 | 蒙皮 | VAT | |
| ---: | ---: | ---: | ---: |
| 200 | 3.680 ms（186 次繪製） | 1.842 ms（2 次） | 省 49.9% |
| 800 | 7.785 ms（740 次） | 2.560 ms（2 次） | 省 67.1% |
| 3,200 | **30.107 ms**（2,971 次） | **4.920 ms**（2 次） | **省 83.7%** |

**省的比例隨數量成長** —— 因為它消滅的是逐 instance 的成本，而那正是先前
量測預測的。

### 兩個 shader 細節，都不是小事

- `textureSize()` 是 GLSL ES 3.00 才有的，而 Three 預設編 1.00。用了會整支
  編不過，而畫面上是「那個材質的東西整個不見」。寬度改用 uniform 傳。
- instance 的編號是 `getIndirectIndex( gl_DrawID )`，**不是 `batchId`** ——
  那個變數不存在。

### 第二個錯誤值得單獨記一筆

寫錯變數名之後 vertex shader 編不過。而那個失敗**量測完全看不出來**：

```text
3200 個  蒙皮   26.420 ms   2971 次繪製   807,842 個三角形
3200 個  VAT     2.764 ms      2 次繪製   803,762 個三角形
        → GPU 省 89.5%
```

三角形數對得上（`renderer.info` 算的是**送出去的**幾何，不管程式有沒有連結
成功）、繪製次數如預期、時間漂亮得不得了 —— 一個「比正確答案還好」的假結果。

抓到它的是**主控台的錯誤訊息**，而那是因為那支量測工具會把 console error
一起收。這一輪第二次靠「數字之外的東西」抓到靜默失效（第一次是 MultiMesh
沒呼叫 super，靠三角形數抓到）。

> 每加一把尺，就多一種騙不過去的方式。

### LOD 也有，而且不必重烘貼圖

一開始把 LOD 關掉，理由是「簡化會重排並丟掉頂點，而貼圖是用原始頂點編號索引
的」。**那個理由是錯的**：簡化器只移除頂點、不生出新的，而 `compact()` 會把
每一個 attribute 都帶過去 —— 包括 `wwVertexId`。實測 355 個頂點簡化到 100
個，100 個相異的編號，一個都沒亂。

所以同一張貼圖對每一階都成立。分開報兩個數字：

| 3,200 個 | GPU | 繪製 | 三角形 |
| --- | ---: | ---: | ---: |
| `THREE.SkinnedMesh` | 26.543 ms | 2,971 | 807,842 |
| VAT（關 LOD，同樣三角形數） | 4.993 ms | **2** | 803,762 |
| VAT + LOD | **3.241 ms** | **2** | 94,562 |

**只算批次是省 81.2%，整條路是省 87.8%。** 分開是因為來源不同 —— 混在一起
的話「批次本身值多少」就永遠說不清楚。而那支量測工具現在會在兩組的三角形數
對不上時**拒絕比較**。

但**只在已經有索引的幾何上開**：沒索引的話產生流程會先 `weld()`，而它的鍵值
涵蓋每一個 attribute，`wwVertexId` 逐頂點都不同 → 一個都焊不起來 → 簡化器
回傳原樣 → 「產生了 LOD 但每一階都跟第 0 階一樣」。那比沒有 LOD 更糟，因為
統計上看起來 LOD 有在運作。

### 遠景合併關掉，理由是正確性

合併是把一格的 instance 烘成一份幾何、當成**一個** instance 畫，而這條路的
動畫相位是逐 instance 的。合併之後那一整格會共用一個相位 —— 本來各動各的
一群東西，會在合併的瞬間突然同步。看得見，而且不會報錯。

### 真的資產也跑過了

程序化的圓柱回答得了「成本怎麼隨數量成長」，回答不了「真的資產上長什麼樣」。
BrainStem（18 根骨頭、59 個 primitive）× 200：**1.737 ms、2 次繪製、4 階、
貼圖 0.26 MB**。

只烘第一個 primitive，而且會在主控台講出來 —— 不講的話畫面上少掉大半個模型
會看起來像烘壞了。

### 烘一次要多久，以及為什麼不搬去 cook

| 模型 | 頂點 | 烘 32 幀 |
| --- | ---: | ---: |
| 程序化的圓柱 | 187 | 4.4 ms |
| BrainStem | 538 | 6.8 ms |
| CesiumMan | 3,273 | 28.3 ms |

線性，約 **0.27 µs / 頂點 / 幀** —— 一個 30,000 頂點的角色烘 32 幀約 260 ms。

在這個量級上搬去 cook 不划算。而且真的變成問題時，正確的解法**不是 cook 而是
worker**：那條路已經有了（`autoLod` 就在 worker 裡跑），而且保住「不需要建置
步驟」這件事。

**先量再決定要不要做** —— 這個數字讓「cook 時烘焙」從一個待辦變成一個有條件
的選項：等到有人拿著一個會卡幾百毫秒的模型出現。

### ✅ WebGPU 那條路也做了，而且有自己的 gate

`onBeforeCompile` 是 WebGL 的鉤子，node 材質不經過它。只做一邊的症狀是
**一群停在綁定姿勢、完全不動的模型** —— 不報錯，而且幀時間特別好看。

所以 node 那條路有自己的實作：`positionNode` 用 TSL 組出來，**動態 import**
（`three/tsl` 只有 WebGPU 用得到，靜態拉進來的話只用 WebGL 的人也要下載它）。
取樣用 `textureLoad` 而不是 `texture` —— 貼圖的一個維度是頂點編號，過濾它
會把兩個不相干的頂點混在一起。

驗它的是新的第六道 gate `pnpm webgpu-check`，而它的判準刻意**不是「有沒有
跑完」**：沒接上的時候「跑完了」與「沒有錯誤」都成立。它畫兩個不同時間點
再比像素。實測畫了 18,659 個三角形，兩幀不一樣。

它還會在任何 console error 出現時拒絕通過 —— 而第一次跑就抓到自己：那台
測試伺服器沒有 favicon。

#### 我一度說「這台機器驗不了」，那是量錯的

先前跑了八種組合都得到 `navigator.gpu 不存在`，於是差點把「WebGPU 在這個
環境上驗不了」寫成專案的範圍宣告。

**那個測試是錯的**：我在 `about:blank` 上問 `navigator.gpu`，而 WebGPU 需要
**安全上下文**。換到真的 origin（localhost）上：

```text
about:blank                        → navigator.gpu 不存在
localhost，headed + flag           → OK，拿到 device
localhost，headless + swiftshader  → requestAdapter 回傳 null
```

而 `pnpm bench:smoke` 本來就跑得起來 —— 那是最直接的反證，我卻先做了八次
錯的實驗才去跑它。

**這是今天第四次「量測的地方不對，於是得到一個很有把握的錯結論」。** 前三次
是對照組用錯幾何、內容規模不夠、動畫迴圈沒停。這一次差點變成寫進 spec 的
永久錯誤。

> 判準：**宣告一個限制之前，先跑一次已知會成功的東西。** `bench:smoke` 就在
> 那裡，跑它要三分鐘，而它會當場推翻那個結論。

而**今天已經有三次「沒驗過的 shader 給出自洽的假成功」**：材質旋鈕（淨虧被
讀成有效）、MultiMesh 沒呼叫 super（1.589 ms 像五倍勝利）、VAT 用了不存在的
`batchId`（省 89.5%，比正確答案還好）。

在那個紀錄之後盲寫一份 shader 然後說「應該可以」，會是這一輪最不該做的事 ——
所以先把量測修對，再寫，再驗。三件事的順序不能換。

順帶：`WW.MultiMesh` **兩條路都能用** —— 它只走 `BatchedMesh` 的公開介面，
沒有任何 shader 注入。

### runtime 烘焙，所以不必等 cook

之前把「cook 不處理蒙皮」寫成 VAT 的前置，那是錯的 —— 烘焙在瀏覽器裡做就好，
吃一個已經 bind 好的 `SkinnedMesh` 加一段 `AnimationClip`。cook 時烘會更快
（省掉啟動成本），但那是加速不是前提。

**這與整個套件的核心約束是同一句話：用了更好，不用也能動。**

## 第六條軸：世界尺度（2026-08-18）

前五條軸問的都是「**畫得動多少**」。這一條問的是完全不同的問題：
**世界很大本身帶來的問題**。

發現它的方式是回頭讀專案名字。「WebWorldEngine」承諾的是「輕鬆構建大世界」，
而前五條軸交出來的是「畫很多東西很快」—— 那是大世界的**零件**，不是大世界。

### 判準與前五條一樣

推到量得出來的上限，或寫下擋住它的平台限制。但這一條有一個不同的性質：

> **前五條是「還能更快」，這一條有幾項是「不做就不成立」。**

離原點十萬單位處畫面會抖、一盞平行光罩不住廣闊地形、地表接縫對不起來 ——
這些不是效能問題，是**功能不成立**。

### 這條軸的項目

| | 狀態 | |
| --- | --- | --- |
| **原點精度** | ✅ | 見下 |
| **世界尺度陰影** | ✅ `WW.applyShadows` | 接 Three 的 CSM addon，補掉它兩個靜默的坑 |
| **地表系統** | ✅ `WW.buildTerrain` | 逐塊 LOD 鏈 + 裙邊。29.3 萬三角形對 142.6 萬 |
| **物理整合** | ✅ `WW.PhysicsScheduler` | 只做調度，求解交給 Rapier（ADR-0005） |
| **多層 HLOD** | ⛔ 想清楚之後不做 | 它要省的東西**這裡已經沒有了**，見下 |
| **宣告式擺放（PCG 那類）** | ✅ `WW.scatter` | 規則式、決定性、密度按面積 |
| **水** | ✅ `WW.Water` + `computeBuoyancy` | 一份波形，渲染與浮力共用 —— 見下 |
| **全域光照** | ✅ 烘出來的那一半 | 即時動態 GI 仍然 ⛔（要擁有管線）；探針體積是資料問題，見 ADR-0006 |

### ✅ 原點精度做完了

float32 只有 24 位有效位數，可表示的座標間距隨距離拉開：離原點 100,000 時
是 0.008。而 instance 矩陣就存在 `Float32Array` 裡。

**兩半缺一不可，只做一半等於沒做：**

1. **把世界搬回相機腳下**（`World.rebaseOrigin`）—— 修的是相機與世界都很大
   時相減掉精度，也就是畫面在抖。平移量取整到整數，所以 `origin` 本身永遠
   可以被 float32 精確表示：搬 50 次之後「場景座標 + origin」仍然精確還原
   世界座標。
2. **內容寫進來的那一刻先減掉原點**（串流的 `place`）—— 使用者用世界座標
   描述內容（那是唯一自然的寫法），而 `place` 暫存用的是普通 JS 陣列，
   也就是**最後一個還是 double 的地方**。在那裡減掉原點，存進 float32 的
   就是一個小數字。

實測：離原點 200,000 處相距 5 公釐的兩個東西，直接寫世界座標會**擠成同一點**
（差值 0），走串流則保住 5 公釐。

**只搬套件自己管的東西**，其餘透過 `onRebase` 通知。自動搬整個 scene 就得猜
哪些是世界、哪些是 HUD —— 那是準則明確排除的「魔法加速器」。

### ⛔ 多層 HLOD：它要省的東西這裡已經沒有了

UE 的 HLOD 有很多層，越遠的整片合成一個代理物件。照抄過來很自然，但先問
「它省什麼」：**繪製呼叫**。

而這裡的遠景場景，743 組合併之後是 **2 次繪製**。

```text
遠景（20,000 個、743 組合併）
  原生   210.144 ms   102,400,546 三角形   3 次繪製
  強化版  16.583 ms     2,945,638 三角形   2 次繪製
```

原因是 `BatchedMesh` 的 multi-draw：**所有合併好的代理都在同一次提交裡**。
再合併一層不會讓 2 變成更少。

而三角形數也不會變 —— 合併是把幾何接在一起，不是簡化它。所以「更粗的
HLOD 層」真正能省的只有一件事：**把合併後的幾何簡化**。

而那正是「把 LOD 鏈接長」在做的事，那個功能已經有了（`extendLodChain`，
量到 27.7%，預設關的理由見材質那一軸）。

> **同一個名字在不同的機制下對應到不同的東西。** UE 需要多層 HLOD 是因為
> 它的合併層要各自送繪製；這裡不需要，因為底層本來就把所有東西塞進一次
> multi-draw。照抄名字會做出一個省不到任何東西的功能。

### CPU 的下界一直比錯對象（2026-08-18）

四格模型裡 CPU 那格一直寫著「離下界 4.5 倍：每個 instance 18 ns，純讀一遍
是 4 ns」。**那個比較從一開始就不對等。**

「純讀一遍」量的是把 instance 矩陣讀過去。但收集迴圈**根本不讀矩陣** ——
包圍球是預先算好的（那正是先前那一輪的優化）。拿一件它不做的事當下界，
算出來的倍數沒有意義。

正確的下界是「這個迴圈非做不可的事」：讀四個 float（球心與半徑）、寫三個
陣列元素（start／count／indirect）。實測 214,000 個：

| | |
| --- | ---: |
| 下界 | **0.8 ms（3.74 ns／instance）** |
| 實際 | 5.5–7.9 ms |
| 每個**可見** instance | 約 25 ns |

差距幾乎全在**視錐測試那六個平面**：每個 instance 24 次乘加，而下界那一版
一次都沒有。

#### 所以「剩下 Worker、SIMD」這句話要修正

| | |
| --- | --- |
| **Worker** | ⛔ **方向就是錯的**。剔除的結果這一幀就要用，丟到 worker 只能拿上一幀的答案 —— 畫面邊緣的物件晚一幀出現，那是拿正確性換 CPU |
| **SIMD** | ⛔ **做完下面那一條之後不值得了**。它只幫得到「還在做平面測試」的那 25%，而那要換一份自己出的 WASM（等於加一道建置步驟）。算下來是頭條場景幀時間的千分之幾 |
| **更好的空間分割** | ✅ **做了，而且發現那條捷徑從來沒跑過** —— 見下 |

**三條裡有一條是錯的方向**，而它在那張表上寫了很久 —— 沒有人去問「丟到
worker 之後，這一幀要拿什麼畫」。

#### ✅ 做了「更好的空間分割」，而且發現那條捷徑從來沒跑過

收集迴圈本來就有捷徑：整段都在視錐內側時跳過那六個平面。加一個計數器之後
量到 —— **跳過率 0.0%，三種規模都是 0。它從來沒有執行過。**

原因是「整段在內側」只有串流的區塊表算得出來，而格子那條路（靜態內容，
最常見的那一種）從來沒回報過，所以條件永遠是 false。程式碼寫了、出貨了、
沒跑過。

補的方式很小：格子本來就在測 cell 的視錐關係，多比一次 n-vertex 就分得出
「相交」與「完全在內」。**成本是逐 cell 的，省下來的是逐 instance 的。**

| | 跳過率 | 收集 |
| --- | ---: | ---: |
| 20 萬（三輪交錯 A/B 的中位數） | 0% → **74.7%** | 1.5 → **1.0 ms** |
| 50 萬 | 0% → **82.4%** | 5.5 → **3.8 ms** |

兩個規模都是快約三分之一，而且**可見數量每一輪都完全相同** —— 剔除的
決定一個都沒變。

（第三輪反向：1.5 → 1.7。那個規模的收集只有 1–1.7 ms，而 `performance.now`
被夾在 0.1 ms 左右，只有十來個 tick 的訊號。50 萬那組分得開，而且同向。）

##### 它差點以「錯怪使用者」的形式出貨

跳過平面之後兩個測試紅了，而失效的樣子值得記：`gridSavedMs` 用
「每個測過的 instance 平均成本」估格子省了多少。74% 的 instance 走便宜路徑
之後平均被拉低 —— 但**格子剔掉的那些不可能便宜**，它們在視錐外，一定要做
完整的平面測試。

於是格子省的錢被低估、帳算不過來，靜態內容的空間分割被判成不划算而暫停，
還附送一則「這是動態內容嗎」的警告 —— **而那個場景根本沒有東西在動**。

改成除以「做過平面測試的數量」就對了，而且**跳過率為 0 時它與原式完全相同**
——一個不改變格子行為的最佳化，不該改變「格子值不值得」的判斷。

抓到它的是兩個既有測試。沒有它們，這會以「幀時間悄悄變差 + 一則指責使用者
內容的警告」出貨。

### ✅ 水：一份波形，兩邊共用

#### 這一項是**漏掉的**，不是排在後面

需求裡明確講過「碰撞阿水阿」「希望跟真的一樣」。而它從頭到尾沒有進 roadmap
——`grep` 整包原始碼與規格，`water`／`浮力` 一個字都沒有。

**那比「決定不做」糟**：決定不做會留下一行紀錄，漏掉不會，所以沒有任何東西
會讓它浮出來。是回頭逐項核對才發現的。

#### 先講做不到的

「跟真的一樣的水」在即時演算裡做不到，**UE 也沒有**。UE 的 Water 是 Gerstner
波加著色，真正的流體模擬只在很小的局部用。海洋看起來真實是**渲染**的功勞。

所以「水」拆成兩件事，混在一起會做出一個很貴又不對的東西：

| | 誰負責 |
| --- | --- |
| 看起來像水（折射、泡沫、次表面） | 開發者的材質。與光照同一類 |
| 互動對不對（浮力、隨波起伏） | 這裡 |

#### 為什麼它是一個模組而不是兩個

水面在畫面上是 vertex shader 推出來的，浮力是 CPU 算的。**兩邊各寫一份的話
東西會浮在錯的高度** —— 船陷進浪裡或飄在半空，而且不報錯，只是「看起來
怪怪的」。

那在這裡幾乎必然會發生：兩份程式碼、兩個時間點寫的。所以波形參數只有一份，
CPU 走 `heightAt`、GPU 走 `displacementGLSL()`，而**測試會把 shader 裡的
常數挖出來跟 CPU 那份比**。

#### 兩個「不做會靜靜出錯」的細節

| | 不做的話 |
| --- | --- |
| 沉沒比例用**連續**的，不是布林的「在不在水裡」 | 物體在水面附近**彈跳不停** —— 出水瞬間力歸零、掉回去又滿力 |
| 阻尼有預設值，不是必填 | 物體**永遠上下振盪**，而那看起來像物理引擎壞了，不像少一個參數 |

陡峭度也會夾在 1：超過的話 Gerstner 的波峰會自己交叉，畫面上是水面破掉，
而那個值是開發者填的 —— 填錯不該變成破圖。

### ✅ 第七道 gate：`pnpm physics-check` —— 把時間跑過去才看得到的那一類錯

物理與水的單元測試有 605 條裡的一批，驗的都是「這一刻算出來的數字對不對」。
而這兩個模組實際犯過的錯，**每一幀的數字都是對的**：

| 實際發生過的錯 | 每一幀的數字 | 症狀 |
| --- | --- | --- |
| 碰撞體密度沒設 | 完全正確（5,297 N，剛好是夾住之後的 20 g） | 箱子 20 秒飛到 y = 183,996，還在加速 |
| Rapier 的 `addForce` 是**持續**的 | 完全正確 | 每幀再加一次，第 N 幀的力是 N 倍 |

第二個特別值得記：`addForce` 加上去之後**每一步都會施加，直到被清掉**。
少一行 `resetForces` 的症狀不是「力不對」，是力對但一直累加。看模組的程式碼
永遠看不出來，因為錯的不在模組裡。現在 `computeBuoyancy` 的用法說明第一行
就是那句 `resetForces`，而範例照著做。

密度那一個補了一道上限（`maxLiftG`，預設 20 倍重力）並且會警告說出原因。
夾住不是為了物理正確 —— 密度設錯本來就不正確 —— 是為了讓症狀從「東西消失」
變成「浮得太用力」加一行看得懂的警告。

新的 gate 真的開瀏覽器、真的跑 900 步，然後問箱子最後在哪裡。目前：

```
最後：{"active":120,"floating":58,"below":0,"maxGap":0,"afloatRest":34,"peakY":70}
```

`afloatRest` 是「停在水面 ±3 以內、而且明顯高於地表」的數量 —— 射出去的與
沉底的都不算。

#### 這道 gate 自己也差點是假的

第一版寫完八項全過。然後照 [doctrine](doctrine.md) 第 16 條把 bug 放回去，
**照樣八項全過**：門檻寫成 `afloatRest > 0`，而箱子全飛走之後剛好剩一顆；
「有沒有飛上天」拿的是 `minY`，那是**最低**的那顆，結構上抓不到往上飛的東西。

更麻煩的是飛走的箱子會離開調度器的啟用半徑被停用，從統計裡整個消失，於是
當下的高度分佈乾乾淨淨。改成記錄**有史以來的峰值**才抓得到：帶 bug 15,554，
修好 70。

而帶著 bug 那一輪**沒有任何主控台錯誤**。

### 📐 先量遮蔽剔除值不值得做（2026-08-19）

roadmap 一直把遮蔽剔除標成「還沒做的下一條軸」，但那是**推論**出來的。
[doctrine](doctrine.md) 第 5 條：先量再做。而這一條軸特別值得先量，因為
多層 HLOD 就是量完之後被否決的 —— **它要省的東西，別的機制已經拿走了**。

#### 量法：把 instance 編號畫成顏色

開一張與畫面同樣大的 render target，用覆寫材質把每個 instance 的編號編成
RGB 畫進去，深度測試照常。畫面上出現過的編號就是真的被看見的。

編號是**資料不是顏色**，所以取代的是 `colorspace_fragment` 那一步 ——
讓它經過 sRGB 編碼的話讀回來的位元組全錯，而解出來的編號會是一堆看起來
很合理的垃圾。

#### 「看不見」要拆成兩種，只有一種是遮蔽剔除的事

| 類別 | 誰的事 |
| --- | --- |
| 投影不到一個像素 | **選階**的。遮蔽剔除拿不走它 |
| 夠大但被擋住 | 遮蔽剔除的 |

不拆的話「完美可見性預言機」省下來的會被整碗算到遮蔽剔除頭上。實際拆完
發現**太小的只佔很少數**（兩萬個的場景裡 226，六萬個貼地的場景裡 0）——
選階已經把該處理的處理掉了，剩下的是真的被擋住。

#### 量到的

裝一個作弊的完美剔除器：先畫 ID 圖知道誰看得見，把「夠大但被擋住」的搬到
視錐外，讓引擎自己的剔除拿掉它們。A/B **交錯**跑三輪。

| 場景 | 送出去 | 看得見 | 被擋住 | 基準 | 完美剔除 | 省 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 遠景・兩萬個 | 16,498 | 4,770 | 11,502 | 10.29 ms | 3.75 ms | **63.5%** |
| 貼地・六萬個 | 22,343 | 6,705 | 15,638 | 15.34 ms | 5.85 ms | **61.9%** |
| 稀疏控制組・六百個 | 404 | 153 | 239 | 0.99 ms | 0.88 ms | 11.3% |

稀疏那一列是**量尺自己的檢查**（doctrine 第 11 條）：東西散得很開、彼此
擋不到的時候，這把尺必須讀出接近零。它讀出 11%，而密的場景讀出 60% 以上
—— 訊號跟著密度走，不是跟著別的東西走。

#### 而「省了 60%」這句話本身也要驗

省下來的時間只有在**畫面不變**的前提下才算數。藏掉的如果其實看得見，那不是
優化，是把東西弄不見。

所以藏完之後逐像素比對：

| 場景 | 變了的像素 |
| --- | --- |
| 遠景・兩萬個 | 9,254 / 921,600（**1.004%**） |
| 貼地・六萬個 | 1,938 / 921,600（**0.21%**） |

殘留的那 1% 是量測的假象而不是真的內容消失：ID 圖沒有多重取樣，只在像素
中心取值，而真正的畫面開著抗鋸齒 —— 只貢獻到邊緣覆蓋率的 instance 在 ID
圖裡贏不到任何一個像素中心。

#### 結論：值得做，而且是目前最大的一塊

密的內容裡有 **60% 以上**的 GPU 時間花在完全看不見的東西上。這與多層 HLOD
的情況正好相反 —— 那一條量完發現沒東西可省，這一條量完發現有一大塊。

但那 60% 是**上限**，因為這個預言機作弊了兩次：它是畫完才知道誰看得見的，
而且它自己不花時間。真正的遮蔽剔除要在畫之前猜，而猜的成本要從省下來的
裡面扣掉（doctrine 第 9 條）。

### ✅ 會動的東西現在反彈得了光 —— ADR-0006 那個限制關掉了

ADR-0006 當初寫下的限制是「**會動的東西不反彈光**」：烘出來的探針是靜態的，
一台紅車開過白牆邊，牆不會沾到紅。

那個限制的前提是「重烘太貴」—— 而重烘一顆探針從 37 ms 降到 2.7 ms 之後，
前提就不成立了。

#### 做法：標過期，優先重烘

```js
volume.invalidateAround(car.position, 14);   // 每幀，東西動了才標
await WW.bakeIrradiance(renderer, scene, volume);   // 過期的優先
```

兩個細節是**畫面會證明**的：

- **搬之前也要標**：東西原本站的地方那幾顆探針記著它的顏色，不重烘的話它
  走了顏色還留在原地。
- **過期的排在沒烘過的前面**：過期是畫面上看得到的錯（東西動了光沒跟上），
  沒烘過的只是還沒亮起來，而那本來就是漸進的。

用球不是盒 —— 盒的角落那幾顆離得比半徑遠，重烘它們是白花錢。

#### 量到的

場景裡除了一塊藍板子沒有任何藍色，所以藍是個只有它做得出來的訊號。把板子
搬到白箱子旁邊，重烘 11 顆探針之後，箱子那一面的輻照度：

| | 紅 | 綠 | 藍 |
| --- | ---: | ---: | ---: |
| 搬之前 | 1.0328 | 0.0425 | 0.0425 |
| 搬之後 | 0.5806 | 0.0529 | **0.5882** |

**藍漲了 13.8 倍**，而紅掉下來 —— 因為板子擋掉了一部分紅牆的反彈。兩個方向
都對得上「那裡真的多了一塊藍色的東西」。

把 `invalidateAround` 的標記拿掉重跑，四項全紅、數字一位小數都不動
（doctrine 第 16 條）。

#### 這一段的量測差點又量錯地方

第一版量的是**畫面像素**，而板子搬到箱子旁邊之後剛好擋在相機與箱子中間 ——
量到的那塊像素變成板子本身，紅色從 94.8 崩到 3.3。那個數字看起來像「間接光
壞了」，實際上是框裡的東西換人了。

問「附近的探針有沒有記到那塊藍板子」的話，**直接問探針**就好，而且完全不受
遮擋影響。這是這一輪第五次「量到的不是想量的」。

#### 代價寫清楚

一顆 2.7 ms。所以這不是「每幀重烘一整片」的功能 —— 標太多顆會直接吃掉幀。
合理的用法是「一個會動的東西，標它周圍那幾顆」，並且接受間接光**慢幾幀才
跟上**。那個延遲是這條路的代價，換來的是不必擁有渲染管線。

### ✅ 烘探針快了 13.7 倍，而且是量出來才知道要修哪裡

問「會動的東西能不能有間接光」的時候（ADR-0006 明寫的限制），第一步是量
**一顆探針多少錢**。量到 **38.81 ms**。

一顆比兩幀還久。所以：

- 每幀重烘幾顆這條路完全不通
- 256 顆的示範要烘 **9.4 秒**
- `budgetMs` 那個參數形同虛設 —— 預設 8 ms，實際每次超出四倍半
- 「烘的時候畫面照樣流暢」那句寫在文件上的話**是假的**

#### 先問「錢花在哪」，不要先猜

第一個直覺是「每次都開一張新的 cube render target 再丟掉」。改成重複用之後：
38.81 → 36.83 ms。**5%。** 猜錯了。

第二個直覺是「面太大」。把面寬從 4 開到 32（像素多 64 倍）：

| 面寬 | 一顆 |
| ---: | ---: |
| 4 | 36.96 ms |
| 8 | 37.46 ms |
| 16 | 37.69 ms |
| 32 | 37.61 ms |

**完全不動。** 一個與像素數無關的成本，代表它不是在算。

拆成兩半量才看到：

| | 時間 |
| --- | ---: |
| 把場景畫六次 | **0.3 ms** |
| 投影＋讀回 | **36.8 ms** |

`LightProbeGenerator.fromCubeRenderTarget` 在自己的迴圈裡**逐面 await**
`readRenderTargetPixelsAsync` —— 六個面就是六次 GPU→CPU 同步，一次約 6 ms。
它不是在算，是在等。等六次。

#### 改法：把讀回全部發出去，最後一次等完

`readRenderTargetPixelsAsync` 在呼叫的當下就把 `readPixels` 排進命令流（進
PBO）並下 fence —— 後面那顆探針重畫同一張 target **不會**蓋掉前一顆的資料，
因為 GL 命令是照順序執行的（讀 Three 的實作確認過，不是猜的）。

所以一輪裡把所有探針的畫與讀回全部發出去，最後 `Promise.all` 一次等完。

| | 一顆 | 256 顆 |
| --- | ---: | ---: |
| 之前 | 36.83 ms | 9.4 秒（256 輪） |
| 之後 | **2.72 ms** | **0.7 秒（38 輪）** |

**13.7 倍。** 而且 `budgetMs` 現在管的是「發出去」那一段（一顆約 0.3 ms），
等待是非同步的、不佔主執行緒 —— 那個參數終於名副其實。

#### 代價：投影要自己寫，所以拿封閉解驗

不再用 addon 就得自己做 SH 投影。座標對應、權重、基底、正規化全部照它逐行
搬過來 —— 這裡要的是少等幾次，不是換一套慣例。

而「一樣」不靠讀程式碼相信：測試比的**不是那個 addon**，是封閉解 ——
均勻環境的輻照度必須是 πL，而那個答案與任何實作都無關。拿 addon 當標準答案
的話兩邊一起錯就驗不出來，而這一支存在的理由就是要取代它。

#### 途中被關卡抓到一個

第一版的解碼寫成「WebGL 用 `fromHalfFloat`、WebGPU 不解碼」。但兩邊的 target
都是 HalfFloat —— 於是 WebGPU 那條路把半精度的**位元樣式**當成數值，係數變成
24,178（1.0 的半精度樣式是 15360），畫面整片爆白。

WebGL 那一側完全正常，所以只驗一邊的話會過。抓到它的是 gi-check 的 WebGPU
那一半 —— 那一半正是為了「只做一邊會靜靜地壞」才加的。

翻轉看座標系，解碼看像素怎麼存。兩件事本來就沒有關係，混在一起是我自己加的。

#### 對「會動的東西」那個限制的意義

從 37 ms 變成 2.7 ms，重烘探針從**完全不通**變成**很貴但想像得到**（一顆還是
佔一幀的六分之一）。這裡沒有做動態重烘 —— 它需要一套「誰動了、哪幾顆該重烘」
的策略，而那是另一件事。限制仍然寫在 ADR-0006 上，只是門檻不一樣了。

### 📐 虛擬貼圖：唯一一項「量不到」的，而那本身要講清楚

前面幾項都是量完再決定（impostor 不做、GPU 驅動繪製不做、遮蔽剔除做了但拿
不到）。虛擬貼圖是**唯一一項現在的內容量不了**的，而 doctrine 第 12 條正好
在講這件事：內容不夠大的時候，量到的是「這台機器不在乎」，不是「這個功能
沒用」。

所以這裡不裝作評估過，而是把**門檻**算出來。

#### 現在有多少貼圖資料

| cook 出來的內容 | 大小 | KTX2 張數 |
| --- | ---: | ---: |
| 程序化的示範 | 0.9 MB | 6 |
| 真實資產 | 46 MB | 40 |
| Sponza（一棟建築的內裝） | **83 MB** | 71 |

Sponza 是**一棟**建築、而且已經是 BC 壓過的。也就是說一座由一百棟各自獨特
貼圖的建築組成的城市大約是 8 GB —— 那正是虛擬貼圖存在的理由，而且它離現在
的示範內容有兩個數量級。

#### 這個套件現在到哪裡

串流做的是**格子**：幾何與 instance 照相機位置載入卸載。而貼圖是**逐資產**
載入的（`loadMaterial`），載了就一直在，只有 `clearAssetCache` 能整批丟掉。

所以缺的很具體：**沒有逐塊的貼圖常駐管理**。世界比記憶體大的時候，幾何那一半
處理得了，貼圖那一半處理不了。

#### 為什麼不現在做

兩個理由，一個是量測上的，一個是這個專案已經付過學費的。

**一、現在做等於盲做。** 要驗它得先有一份「貼圖資料超過 VRAM」的內容，而那
份內容本身是一個大工程。沒有那份內容的話，任何實作都只能證明「它沒有把現在
的東西弄壞」—— 那不是證明它有用。

**二、它的著色端正好踩在量過的那個坑上。** 虛擬貼圖要在每個 fragment 上多做
一次間接（查頁表再取樣）。而這個專案在材質那一軸量過非常接近的東西：逐
fragment 的動態分支**淨虧 15–20%**，那個旋鈕最後被整個拿掉。

不是說虛擬貼圖一定也虧 —— 是說**它的成本要先量**，而量它同樣需要那份還不
存在的內容。

#### 要動它的話，順序是這樣

1. 先有一份貼圖資料明顯超過 VRAM 的內容（那是資產工作，不是引擎工作）
2. 量「現在會怎樣」—— 掉幀？當掉？還是驅動自己換頁換得還可以？
3. 有了那個數字才知道要做到哪一步：也許只要逐塊丟棄就夠，不必做到頁表

寫下來是因為**「還沒做」與「不該做」要分開**（doctrine 第 16 條旁邊那個教訓：
遮蔽剔除在清單上掛了很久的「還沒做」，做完才發現是「做了，走不到」）。
虛擬貼圖現在的狀態是明確的「還沒做，而且知道要先有什麼才做得下去」。

### 📐 貼圖壓力量了，而結論不是「要做虛擬貼圖」

前一節說虛擬貼圖量不了，要先有一份貼圖超過 VRAM 的內容。那份內容做出來了
（程序生成、每張都不一樣），而量到的東西**推翻了原本的假設**。

#### 第一次量錯了兩次

**一、`renderer.info.memory.textures` 讀到 0。** 我把它寫成物件的一般屬性，
於是取值發生在**建那個物件的當下** —— 那時一幀都還沒畫。0 看起來像「貼圖
根本沒上傳」，我差點照著那個假數字去查一個不存在的 bug。改成 getter 之後
是 2,049 張。

**二、把大板子疊起來量。** 想法是「每一張都鋪滿畫面，工作集就等於總量」，
而 1024 張半透明的全螢幕板子量到的是 **overdraw** —— GPU 時間跟著填充走，
跟貼圖住在哪裡一點關係都沒有。

第三次才問對：**拼磁磚**。N 張各佔畫面的 1/N，加起來剛好鋪滿一次。填充固定
是一個畫面，變的只有貼圖總量。

#### 量到的

| 貼圖總量 | GPU |
| ---: | ---: |
| 85 MB | 2.95 ms |
| 341 MB | 2.20 ms |
| 1,365 MB | 2.09 ms |
| 5,461 MB | 2.32 ms |
| 21,845 MB | **頁面載不起來** |

**幀時間到 5.5 GB 完全不動。** 而失敗發生在載入，不是繪製。

原因想通之後很直覺：有 mipmap 的話，**真正被取樣到的 texel 數受限於畫面上
的像素數**，不是貼圖有多大。一張 8192² 的貼圖鋪在四分之一畫面上，讀到的是
很低的那幾層 mip。工作集本來就小。

#### 所以要的不是頁表，是「放得掉」

虛擬貼圖解的是「工作集超過 VRAM」。而上面那張表說：**這個引擎的工作集受
畫面像素數綁住，不會超過**。真正的牆是**總量配置不下**。

而「總量配置不下」的解法不是頁表，是**丟掉用不到的** —— 串流的 `unload`
鉤子本來就在那裡（格子卸載時釋放資源是呼叫端的事，那是刻意的分界）。

缺的是**釋放得了的手段**，而查下去發現那裡有一個真的 bug。

#### 修掉的 bug：`clearAssetCache` 從來沒有真的釋放過 GPU 記憶體

它把兩個 Map 清掉就結束了。而 Three 釋放貼圖的 VRAM 靠的是 `dispose()`，
**不是垃圾回收** —— 只把參照丟掉的話 JS 這側乾淨了，GPU 那張貼圖還在，
而且永遠不會被收回。

一次性的頁面看不出來。串流的世界裡它是無上限的洩漏：每載入一批新資產就多
佔一份，畫面完全正常，直到配置失敗為止 —— 也就是上面那張表最後一列。

加了 `releaseMaterial(manifest, id)`：放掉一份材質與它的貼圖。
`clearAssetCache()` 是全部一起清，串流時那等於「走遠一格就把整個世界的貼圖
重新抓一次」。

#### 結論

**虛擬貼圖不做**，而理由不再是「量不了」，是量完發現它解的問題這裡不存在：
工作集受畫面綁住，牆在總量，而總量該用釋放解決。

真正該做的那件事（放得掉）做了，而且順手修掉一個一直在洩漏 VRAM 的 bug。

### ✅ 一個隨機會紅的關卡，堵起來了

`pnpm verify:all` 跑到 impostor 那一關掛掉：`net::ERR_UNSAFE_PORT`。

原因跟 impostor 一點關係都沒有 —— 那一關開 HTTP server 時用 `listen(0)` 跟
作業系統要一個空的埠，這次拿到 **1720**。而 1720 是 H.323，在 Chrome 的
拒絕連線清單上：連上去直接回 `ERR_UNSAFE_PORT`，請求根本不會送出去。

#### 它為什麼值得修，而不是重跑一次

重跑就好了 —— 這正是問題所在。**隨機會紅的關卡不算關卡**（doctrine 第 17
條）：紅的時候第一個念頭會是「又是那個」而不是「哪裡壞了」，而那個念頭
一旦養成，真的壞掉那一次也會被同樣打發掉。

而且它不只影響一關：全部 **23 個**驗證工具都是 `listen(0)`，也就是每一關
每一次跑都在擲骰子。

修法是 `tools/lib/listen-safe.mjs`：拿到黑名單上的埠就關掉再要一個。重試
而不是寫死某個埠，是因為寫死的話兩關平行跑會撞在一起 —— 那會變成另一種
隨機紅。

#### 順手抓到一個更糟的：掛了還印「全過」

impostor 那一關 catch 到例外之後設了 `exitCode = 1`，但接著還是走到最後
一行印出 **「Impostor 關卡：全過」**。離開碼是對的，所以 `verify:all` 有擋
下來 —— 但**人看的是印出來的字**。

一個會在自己掛掉的時候說自己全過的關卡，比沒有關卡更糟。

#### 而批次改那 23 個檔案時，又踩了一次同樣的坑

改法是「把 import 插在最後一個 `import` 之後」。但 `tools/package-check`
裡面帶著**產生出來的原始碼字串**（它會寫出一個 app.js 來測發布流程），那
段字串裡也有 `import` —— 於是 patch 插進了字串裡，把產生出來的檔案弄壞。

lint 抓到了，但抓到的是外層的 `listenSafe is not defined`，跟真正的損壞
看起來完全無關。教訓是：批次改檔要用**絕對錨點**，而且改完要看每個檔案
插在第幾行 —— 行號跳到一百多的那個就是掉進字串裡了。

### ✅ 全域距離場：Lumen 骨幹的最後一塊，而它是串流

單一物件的距離場能算遮蔽了，但一個世界有幾千個物件 —— 追蹤一條光線時逐一
去問每一個，等於每一步做幾千次查表。那不是慢一點，是不可能。

Lumen 的解法是把附近的場**合成一個**，跟著相機走。而「哪些要住在記憶體裡、
相機走遠了換誰」正是這個套件在做的事。**所以這一塊是串流，不是渲染。**

#### 合成就是取 min

一個點到「這堆東西」的距離，就是它到最近那一個的距離。取錯（例如取平均）
的話遠處的東西會把近處的距離拉大，光線一步跨過近處那個物件 —— 而症狀是
**遮蔽時有時無**。

#### 相機一動不能整份重算

32³ 是 32,768 格，每格要問附近所有物件。所以走 clipmap：格子是**世界對齊**
的固定網格，相機移動時整份平移整數格。

對齊那件事與 `WorldStream` 的格子是同一個理由 —— 不對齊的話相機動一點點
所有格子的世界座標就全變了，增量等於沒做。實測動 1 個單位（一格是 12.5）
不觸發，動 13 才觸發。

重算是**分幀**的。相機瞬移時整份都要換，一次做完是一次看得見的卡頓；分幀
的話那幾幀場是舊的 —— 遮蔽慢一點跟上，而那是安全的方向（畫面正確，只是
暗得慢）。

#### 一條靜靜不生效的路，堵起來了

測試裡「盒子裡面應該是負的」紅了一次：一格 12.5 而盒子是 10，**格心全部
落在盒子外面** —— 那個盒子在這份場裡等於不存在。

那不是 bug，是解析度的本質。但症狀是「那個東西就是不擋光」而畫面上看不出
原因，所以 `add()` 現在會在物件比一格還小的時候警告，並且說清楚該調什麼。

細節本來就不該由這份場管：貼身的遮蔽歸 `ScreenSpaceGI`，單一物件的準確形狀
歸 `DistanceFieldVolume`，這份場管的是「遠處那一大塊擋不擋」。三層各管一段。

#### 間接光現在有四層

| | 管什麼 |
| --- | --- |
| `IrradianceVolume` | 大範圍的光從哪來（烘的，含螢幕外） |
| 動態重烘 | 會動的東西造成的改變 |
| `ScreenSpaceGI` | 貼在一起那幾公分（畫面上的） |
| `GlobalDistanceField` | 鏡頭外、跨物件的遮蔽 |

### ✅ 距離場：Lumen 那一類做法裡搬得過來的那一半

「即時 GI 要擁有整條管線」這句話我用了三次來擋掉這條軸。拆開來看之後發現
它只對**完整的 Lumen** 成立，對它的骨幹不成立。

Lumen 的核心是「對距離場追蹤光線」，而那件事拆開是：

| | 誰做 |
| --- | --- |
| 距離場怎麼烘、怎麼存、怎麼串流 | **這裡** —— 那是資料，ADR-0001 說是我們的 |
| 追蹤那一步 | 一個後製 pass，與 `ScreenSpaceGI` 同一類 |
| 把畫面畫出來 | Three 的 renderer |

沒有一格是「擁有管線」。所以做了。

#### 它補的是另外兩個都補不到的那一段

| | 看得到鏡頭外嗎 | 角落問得出來嗎 |
| --- | --- | --- |
| `ScreenSpaceGI` | ❌ 只有畫面上的像素 | ✅ 像素級 |
| `IrradianceVolume` | ✅ 整個場景 | ❌ 格點之間靠內插 |
| **距離場** | ✅ 三維的場 | ✅ 每一點都問得到 |

一面在鏡頭外的牆，螢幕空間那條路完全不知道它存在；而探針知道那裡暗，但
不知道**貼著牆的那個角**有多暗。距離場兩個都答得出來。

#### 為什麼距離場可以大步走

每一格記的是「離最近的表面多遠」，也就是**至少可以安全走多遠而不穿過東西**。
所以光線行進不必一小步一小步試 —— 空曠處一兩步跨過去，貼近表面時自動變細。

步數跟著幾何的疏密走，不跟著距離走。這是它比體素射線便宜的原因。

#### 烘的做法與保守的方向

兩步，都是為了不要對每一格掃過所有三角形（32³ 配一萬個三角形是三億次）：

1. 標出三角形碰到的格子（用外接盒標，多標一點）
2. 從那些格子逐層往外擴散，每層加一格

第二步是 chamfer 距離的簡化版：對角線方向偏大。而**偏大是安全的** ——
光線多走一點，最多少擋一點光，不會穿過東西。

內外靠灌水判定，與 `innerBox` 同一個判準：破面的模型水會漏進去，於是場退化
成無號的 —— 光線照樣擋得住，只是貼著表面時少一點準度。安全的失敗方向。

#### 驗的是「同一點、不同方向，答案要不一樣」

那是整個東西存在的理由。兩邊一樣的話它只是一個常數的環境光遮蔽，那沒有用。

實測盒子外一點：朝著盒子 > 0.5，背對它明顯更小。把「撞到表面」那一行改成
回傳 0 之後那條測試會紅（doctrine 第 16 條）。

#### 還沒做的那一半

這裡是**單一物件**的距離場。Lumen 還有多物件合成的全域場、表面快取、輻射
快取。全域場那一件是**串流問題**（哪幾個場要住在記憶體裡、相機走遠了換誰）
——也就是這個套件已經在做的那一類，所以它是下一步而不是另一條路。

### ✅ 螢幕空間間接光做了 —— 前一節的「不做」被自己推翻

前一節的結論是「不做」，理由是「品質風險高，失敗形態是雜訊鬼影」。

**那不是一個量測，是一個擔心。** 而這個專案處理擔心的方式是：做出來、量它、
讓數字決定 —— 遮蔽剔除就是那樣處理的（做完發現拿不到，於是預設關 + 警告）。
拿「可能做不好」當理由不做，正是這一輪已經改過一次的那個毛病。

所以做了。

#### 它補在哪裡

探針記的是**格點上**的光，格點之間靠內插 —— 比格距小的東西落在縫裡，而
實測那一段會隨探針落點浮動好幾倍。這一支從**畫面上已經有的像素**收集，
尺度是像素級的，剛好補在探針下面。

兩者互補而不是取代：探針管大範圍與螢幕外的正確性，這裡管接觸尺度。

#### 為什麼不算「變成另一個渲染器」

它是一個**後製 pass**，與範例已經在用的 bloom 同一類：拿 renderer 畫好的
東西再處理一次。多的是一次 `overrideMaterial` 的法線重畫，用的還是同一個
renderer。沒有 G-buffer、沒有 deferred、沒有自己的材質系統。

ADR-0001 擋的是「擁有管線」，這個沒有碰到那條線。

#### 量到的

紅房間、白箱子、**探針關掉**，量 SSGI 自己收集到的那張圖：

| | 值 |
| --- | ---: |
| 收集到 | R 0.0080　G 0.0004　B 0.0004 |
| 紅藍比 | **20.73** |
| 每幀成本 | 0.08 ms（半解析度，這個場景） |

紅藍比 20.73 與探針那條路量到的 21.0 對得上 —— 兩邊收集的是同一片紅牆。

那個 0.08 ms **不能直接外推**：主要成本是法線那一次場景重畫，而它跟著場景
複雜度走。這個場景只有幾個面。真實內容要自己量。

把收集那一行拿掉重跑，兩項紅（doctrine 第 16 條）。

#### 途中三次量錯地方，其中兩次是同一個坑的兩面

1. **緩衝型別對不上**：gather target 是 HalfFloat，我用 `Float32Array` 去讀 ——
   全 0。而 0 看起來就是「什麼都沒收集到」，我照著它查了三個半徑。
   今天稍早才踩過反過來的那一面（烘探針把半精度位元樣式當數值用）。
2. **讀的矩形沒換算解析度**：傳進去的是畫布座標，而收集圖是半解析度 ——
   讀到別的地方，出界回全 0。又一次長得完全像「功能沒做」。
3. **估計式除錯了東西**：原本除以「命中的取樣數」，那樣十二個裡命中一個
   也會得到滿滿的紅。要除的是**總取樣數** —— 那才是「半球裡有多少比例被
   紅色佔住」。沒打到的方向本來就該貢獻 0。

第三個特別值得記：它不會讓畫面變黑，只會讓間接光**過亮而且不隨遮蔽變化**，
而那種錯很容易被當成「參數調太大」。

#### 誠實的限制

| 限制 | 意思 |
| --- | --- |
| 只收集得到畫面上有的 | 鏡頭外的紅牆不會反彈進來 |
| 一次反彈 | 反彈的光不會再反彈 |
| 有雜訊 | 取樣數有限；不做時間累積（那要 motion vector，屬於渲染器） |
| 被遮住的收不到 | 螢幕空間看不到就是看不到 |

前三項正是探針**沒有**的問題 —— 這也是為什麼結論是「兩個一起用」，不是
「用這個取代那個」。

### 📐 決定不做的那一版（後來推翻了）

下面這一節保留當紀錄 —— 它的推理錯在「拿擔心當量測」。



動態重烘做完之後，「會動的東西不反彈光」已經解掉。剩下的缺口是**尺度**：
探針是一格一格的，貼著牆的小東西造成的反彈落在格與格之間 —— 而那正是
螢幕空間 GI 補的東西。

所以先問一個問題再決定：**把探針加密，抓得到嗎？**

抓得到的話這是一個旋鈕（而且烘一顆只要 2.7 ms，加密付得起），不是缺掉的功能。

#### 量到的

板子貼到箱子旁邊（相距 1.5 個單位），量那一面沾到多少藍：

| 解析度 | 探針數 | 標到 | 藍色增量 |
| ---: | ---: | ---: | ---: |
| 4 | 32 | **0** | 0.0000 |
| 8 | 256 | 12 | 1.1102 |
| 16 | 2,048 | 110 | 0.2416 |
| 24 | 6,912 | 405 | 1.1711 |

第一列的 0 一開始被讀成「格子太粗，表示不出來」。查下去發現不是 ——
**一顆探針都沒有被標到**。那個體積的格距是 26.7，而 `invalidateAround` 的
半徑給了 14，那顆球整個落在格與格之間。

修掉了：半徑小於格距而且一顆都沒標到時會**警告**並說出原因。這是很典型的
「靜靜地沒效果」——回傳 0、間接光不更新、畫面上只是「那個東西不反彈光」，
看起來像功能沒做。

#### 剩下的那個非單調是真的，而且是探針體積的本質

16 與 24 都標到上百顆，所以那不是漏標。0.24 對 1.17 的差別來自**探針落在
哪裡**：那個 1.5 單位的縫隙，格點剛好落在有利或不利的位置，內插出來的結果
就差好幾倍。

那是探針體積的固有性質，不是 bug：**它記錄的是格點上的光，格點之間靠內插**。
接觸尺度的東西比格距小的時候，答案會跟著幾何運氣走。

#### 所以

| | |
| --- | --- |
| 抓得到嗎 | 抓得到，只要格距小於那個尺度 |
| 是旋鈕嗎 | 是 —— `resolution`，而且烘得起（一顆 2.7 ms） |
| 有沒有殘留缺口 | 有：量值隨探針落點變動，接觸尺度不穩定 |

而那個殘留缺口要不要用螢幕空間 GI 補，答案是**不補**：

- 它是渲染器等級的工程（雜訊、時間累積、去遮蔽），而失敗形態是**畫面上的
  雜訊與鬼影** —— 做半套比不做糟。
- 這個套件的身分是「渲染器是 Three 的」。Lumen 那一類要擁有整條管線，
  ADR-0001 擋掉的就是那個；螢幕空間那一類雖然是後製，但它的品質完全取決於
  G-buffer 與時間累積，而那兩樣都在渲染器手上。
- 而它要補的那一段，**加密探針已經補掉大部分**。

理由與之前不同了：之前寫的是「要擁有管線所以不可能」，那句話對螢幕空間
那一半講得太滿。現在的理由是**量過缺口有多大、也知道它大部分補得掉**，
剩下那一段不值得用一個會產生雜訊的做法去換。

### ✅ Impostor 做了 —— 而先前那個「不做」的結論是錯的

先前用「把選階壓到最粗」當代理量過一次，結論是「幾何那一側沒剩多少」。

**那個代理不夠遠。** 最粗階還有幾十個三角形，impostor 是**兩個** —— 差一個
數量級，而那次量測的符號還會翻面（−11% 到 +12.8%），自己就說了它落在雜訊裡。

所以把真東西做出來再量。

#### 量到的：它是一個**距離**問題

兩萬棵樹，同樣位置、同樣相機，只換表示法：

| 相機距離 | 省 | 畫面差異 |
| ---: | ---: | ---: |
| 300 | 60.0% | 31.20% |
| 700 | 65.0% | 7.94% |
| 1,500 | **90.4%** | **0.01%** |
| 3,000 | 96.1% | 0.00% |
| 6,000 | 95.6% | 0.00% |

近處看板明顯不對（31%），遠處**看不出差別**（0.01%）而且省九成以上。

這正是 impostor 該有的樣子：它是一個近似，而近似有一條成立的線。與選階的
品質契約是同一種東西 —— 差別在契約管的是幾何誤差投影到螢幕的像素數，這裡
管的是「多遠之後看不出來」。

#### 那個省下來的數字要打折看

對照組是**沒有 LOD 的**幾何（樹是三個 mesh 的 Group，接不進 `InstancedMesh`
的單一幾何形狀）。所以 90% 那個數字是對「完全不簡化」比的，偏樂觀。

公平一點的比法：接長鏈之後最粗階實測是 8 個三角形／instance，兩萬棵就是
16 萬；impostor 是 4 萬。**還是 4 倍**，而那 4 倍是任何 LOD 鏈都到不了的 ——
鏈的盡頭是「還看得出形狀的網格」，impostor 是兩個三角形。

#### 做的時候撞到三個，全部是「數字漂亮但畫面是空的」

1. **著色器沒編過。** 我把 `project_vertex` 整個換掉，而它宣告的 `mvPosition`
   後面的 chunk 還在用 —— 頂點著色器編不過。而 draw calls 少了、三角形少了，
   量出來「省 95.5%」。**畫面是全空的。**
   抓到它的是逐像素比對（差 51%），確認的是主控台那一行 undeclared identifier。
   這個專案在 VAT 的 `batchId` 上踩過一模一樣的形狀。

2. **`instanceMatrix` 漏掉。** 同樣是因為換掉了 `project_vertex`（Three 在那裡
   套用它）。三百個看板全部疊在 mesh 的原點。

3. **視埠設錯地方。** 綁了 render target 之後 Three 用的是 `target.viewport`，
   `renderer.setViewport` 只對畫布有效。十六個視角每一個都畫滿整張圖集，
   後面蓋掉前面 —— 圖集裡只剩最後一個視角被拉寬十六倍。

三個都不會讓任何一個效能數字變難看，只會讓它變**更好看**。

#### 為什麼是獨立的類別，不是 LOD 鏈的最後一階

`InstancedMesh` 底層是 `BatchedMesh`，整批共用一份材質。Impostor 的著色與
網格完全不同，塞進同一份材質等於每個 fragment 多一個分支 —— 而這個專案量過
那種分支：**淨虧 15–20%**，那個旋鈕最後被整個拿掉。

分開就沒有那筆錢。

### 📐 先前判定不做的那一版（結論是錯的）

保留當紀錄 —— 它錯在用一個**構不到**的代理去量。

（2026-08-19）

LOD 那一節寫過「極遠處真正該用的是 impostor 而不是 20 個三角形的爛網格」。
那句話放著沒被檢驗過，而 doctrine 第 5 條說先量再做。

#### 第一次量錯了，而錯的方式值得記

想法是：把 `errorPixels` 開得很大，逼所有 instance 掉到最粗階，看 GPU 少多少。
那是「往 impostor 的方向走得最遠的一步」。

跑出來三個場景分別是 −7.2%、−3.5%、−1.1%，看起來就是「幾何沒東西可省」。

**但那個結論是假的**：兩組的三角形數**一模一樣到個位數**（1,294,226 對
1,294,226）。也就是說 `errorPixels` 根本沒有改變任何一個選階。

原因查出來是：這份程序化資產的鏈只有三階，而遠景的 16,048 個 instance
**已經全部在最粗的那一階**（`levels: {0:0, 1:0, 2:16048}`）。沒有更粗的可以掉。

又一次「量到的東西不是想量的東西」，而它長得完全像一個真實的結論。

#### 用接長鏈之後才有得比

開 `extendLodChain` 把鏈接到八階，選階就真的動得了：

| 場景 | 正常 | 全壓到最粗 | 三角形 | GPU 差 |
| --- | ---: | ---: | ---: | ---: |
| 遠景・兩萬 | 5.858 ms | 6.5 ms | 214,666 → 128,930 | **−11.0%** |
| 遠景・六萬 | 13.398 ms | 11.682 ms | 632,776 → 384,370 | +12.8% |
| 貼地・六萬 | 10.322 ms | 9.572 ms | 629,224 → 177,314 | +7.3% |

**三角形砍掉四成到七成，GPU 時間在 −11% 到 +12.8% 之間亂跳。** 符號會翻面，
那正是「差異低於雜訊」的樣子 —— 尤其貼地那一列砍掉 3.5 倍的三角形只換到 7.3%。

#### 結論

這份內容**不是被幾何綁住的**。Impostor 要做的事是把最粗階再往下壓（8 個三角形
壓到 2 個），而上面那張表說：連從 63 萬壓到 18 萬都量不出穩定的差別。

所以它與多層 HLOD 是同一個結論：**它要省的東西，這裡已經沒有了。**

真正還在花時間的是 fragment 那一側，而那條軸的答案早就寫在「送幾個 fragment
進去」那一節：剔除、選階、遠景合併 —— 全部已經在做。

### ⛔ GPU 驅動繪製：上限量出來是 3%，而且要加在瓶頸那一側

impostor 那次的教訓是「代理構不到就別下結論」。所以這一條改成量**上限本身**：
GPU 驅動繪製能省的最多就是剔除那段 CPU，而 CPU 有多少是直接量得到的。

#### 量幀時間試了三次才對

| 做法 | 量到 | 為什麼錯 |
| --- | ---: | --- |
| 量 `step()` 的耗時 | 0.5 ms | 那只是**送指令**，不等 GPU 畫完 |
| 加 `gl.finish()` | 0.5 ms | Chrome 的命令緩衝下它不是真的同步 |
| **rAF 的間隔** | 11.9 ms | 真的被呈現的幀 |

第一種特別危險：0.5 ms 配上 GPU 的 10 ms，看起來像「CPU 超快」，其實是
**還沒開始畫**。

#### 量到的

| 場景 | 幀 | GPU | 剔除的 CPU | 上限 |
| --- | ---: | ---: | ---: | ---: |
| 遠景・兩萬 | 11.9 ms | 10.1 ms | 0.3 ms | **2.5%** |
| 遠景・六萬 | 31.1 ms | 29.2 ms | 0.9 ms | **2.9%** |
| 貼地・六萬 | 15.8 ms | 17.8 ms | 0.5 ms | **3.2%** |

**幀時間幾乎就是 GPU 時間。** 剔除那 0.3–0.9 ms 完全藏在後面 —— 它不在關鍵
路徑上，搬走它一毫秒都省不到。

而 GPU 驅動繪製是把那段工作**搬到 GPU 上**，也就是加在唯一真正是瓶頸的那一側。

#### 這與 impostor 那次的錯不一樣

impostor 那次用「壓到最粗階」去逼近「兩個三角形」，代理與真東西差一個數量級
——那是**構不到**。

這一次量的是上限本身：省不到比「存在的 CPU 時間」更多，而那個時間是直接量
出來的，還順便量到它是藏著的。不是逼近，是界。

要重新考慮的條件很明確：**哪天幀時間開始等於 CPU 時間**（內容變成幾十萬個
各自不同的物件、或剔除變得更複雜），這條界就會抬起來。現在不是。

### 📐 先前那一版（結論一樣，但當時只有旁證）



把剔除搬到 GPU 的前提是**CPU 是瓶頸**。而這個引擎的 CPU／GPU 比例早就量過了：

| 場景 | CPU（剔除＋選階） | GPU |
| --- | ---: | ---: |
| 遠景・六萬 | 0.9–1.1 ms | 29–33 ms |
| 貼地・六萬 | 0.4–0.6 ms | 15–16 ms |

**CPU 佔 GPU 的 3%。** 把那 1 ms 搬到 GPU 上等於在已經是瓶頸的那一側再加工作
——那不是優化，是把時間從有空的地方搬到沒空的地方。

而且它要一份 WebGPU 專用的路徑（compute + indirect），也就是兩份實作、兩份
失效方式 —— 這個專案在 VAT 與間接光上已經各付過一次那個代價，而那兩次是
**沒有選擇**（鉤子在兩邊不通）。這一次有選擇。

CPU 那條軸真正的下界是 0.8 ms（3.74 ns／instance），而現在是 5.5–7.9 ms 的
那個量測是**六萬個的最壞情況**；一般場景是 1 ms 上下。真的哪天 CPU 變成
瓶頸再回來看這一條。

### 📐 把 `extendLodChain` 那個懸案結掉（2026-08-19）

`extendLodChain` 量到省 **27.7%**，但預設是關的：`visual-check` 的「多畫」是
0.471%，而門檻 0.45%。當時留下兩個都成立的解釋，然後就停在那裡：

- **(a)** 誤差還有殘餘的低估
- **(b)** 更多輪廓落在容忍邊界上，於是抗鋸齒把更多像素推到界外

一個「兩種解釋都成立」的結論其實是「還沒查」。兩個都分得開。

#### (b) 抗鋸齒：用實驗排除

如果是抗鋸齒造成的，關掉它之後接長鏈那個數字應該往乾淨基準靠。實測（同一把
尺、同一個場景，只多一個 `?aa=0`）：

| | 多畫（抗鋸齒開） | 多畫（抗鋸齒關） |
| --- | ---: | ---: |
| 乾淨基準 | 0.265% | 0.090% |
| 接長鏈 | 0.471% | 0.293% |

**關掉之後差距不但沒縮小，還變大了** —— 對基準的倍數從 1.78 倍變成 3.3 倍。
所以那些多出來的像素不是抗鋸齒推出去的。(b) 排除。

順帶量到一件事：**乾淨基準自己在抗鋸齒開關之間差了 2.94 倍**（0.265% 對
0.090%）。也就是說「多畫」這個數字有一大半在描述抗鋸齒，而不是描述幾何。

#### (a) 誤差低估：已經有一支測試在守它

執行期（`lod-generation.ts`）與 cook（`cook/geometry.ts`）**兩邊都用
`maxSurfaceDeviation`** —— 實際量出來的單向 Hausdorff 距離，不是 simplifier
自己估的那個（那個估值低估 1.12–1.48 倍，早就換掉了）。

而「有沒有低估」不必靠讀程式碼相信：`lod-error-truth.test.ts` 拿**有封閉解**
的幾何（icosphere，頂點都在同一顆球上）當標準答案，檢查回報的誤差不低於
真值。那一支就是為了這件事寫的，而且它抓到過一次。

所以誤差沒有低估。(a) 排除。

#### 兩個都排除之後，契約其實是推得出來的

把三件事串起來：

1. 每一階回報的誤差是**真的上界**（`lod-error-truth` 守著）
2. 選階的判準就是「那個誤差投影到螢幕 ≤ errorPixels」（實作上如此）
3. 所以畫出來的位移 ≤ errorPixels

第 3 條是前兩條的**結論**，不需要再量一次。所以這裡沒有再去寫一把「逐像素
量輪廓位移」的尺 —— 它證明的東西已經被證明了，而多一把尺就多一種會分岔的
定義（doctrine 第 13 條）。

#### 剩下的那個解釋

兩個都排除之後剩下的是：**鏈接長之後更多 instance 落在更粗的階，而每一個都
仍然守著 2 像素的契約** —— 於是「有差異的像素」總數變多，但沒有任何一個
instance 違約。

支持它的證據：

| | 值 | 意思 |
| --- | ---: | --- |
| 少畫（東西不見了，危險的方向） | 0.057%（抗鋸齒關） | 門檻是 0.3%，還有五倍餘裕 |
| 梯度比 | 8.8–11.0 | 差異集中在輪廓上，正是契約允許的那一種 |

#### 那為什麼還是不改預設

因為**改了那道關卡就會紅**（0.471% > 0.45%），而接下來唯一能讓它綠的動作是
把門檻放寬 —— 那正是這個專案最不該做的事，而且 roadmap 上一節才剛寫過為什麼。

更根本的是：0.45% 這條線本身是 `少畫門檻 × 1.5` 推出來的，不是獨立訂的品質
判準。拿一個推導出來的、而且有一大半在描述抗鋸齒的數字，去擋一個契約上成立的
27.7%，那個決定的品質很低 —— 但**放寬它的決定品質更低**。

所以現在的狀態是：**預設仍然關，而懸案結了。**

留下來的不再是「不知道誤差準不準」—— 那個問完了，而且答案是準的。留下來的是
一個**尺與問題不合**的狀況：多畫在數像素，契約在管每個 instance 的誤差，而
一個守著契約的長鏈本來就會讓更多像素落在容忍範圍內。

要動預設的話該做的不是放寬那條線，是想清楚「多畫」這個指標在長鏈的情況下
到底該不該用同一條線 —— 那是一個需要人拍板的判斷，不是一個可以量出來的數字。
這裡把證據擺齊，決定留給下一次。

### ✅ 幾何虛擬化的第一塊：把一份大幾何切開

`MultiMesh` 早就量過「切塊」值多少（420 萬三角形的地形，省 54.7%）。但它要求
呼叫端**自己把 N 份相異的幾何準備好** —— 地形是自己生的、本來就一塊一塊，
所以用得上；而「我有一棟掃描回來的建築 / 一份很大的 GLB」的人只有一份幾何，
那 54.7% 就跟他無關。

`WW.splitWithLods` 補的是那一段。這也是 [ADR-0001](adr/0001-three-as-adapter.md)
明寫「Three 沒有、**要我們自己建**」的那一項：Nanite 等級的幾何虛擬化。

```js
const pieces = await WW.splitWithLods(bigGeometry, { chunks: 256 });
scene.add(new WW.MultiMesh(pieces, material));
```

#### 量到的

一份 1200×1200 段的地面（288 萬個三角形），相機貼著地面看向遠方：

| | GPU | 送出的三角形 | 畫面差異 |
| --- | ---: | ---: | ---: |
| 整片一份幾何 | 6.665 ms | 2,880,546 | —— |
| 切成 64 塊 | 2.916 ms | 139,434 | 0.02% |
| 切成 256 塊 | 1.934 ms | 84,866 | 0.04% |
| 切成 1024 塊 | 2.253 ms | 97,339 | 0.04% |

**省下來的是 56–71%，而送出去的三角形少了 20–34 倍。** 繪製次數三種都是 3。

塊數之間**不排名**：64／256／1024 的高低在幾次執行之間整個翻過來（62.2%
然後 58.0%；76.9% 然後 55.6%）。那是這台機器的雙峰（doctrine 第 15 條），
不是塊數的效果。對照組與切開之間的兩三倍才是穩的。

#### 切完一定要鎖邊界，否則會裂

相鄰兩塊共用一條邊。各自簡化的話兩邊會把那條邊化成不同的樣子，中間露出縫
——而且只在兩塊剛好選到不同階的時候才看得到，所以它很容易在開發時完全沒出現。

所以 `splitWithLods` 一定會開 `lockBorder`，那不是選項。代價是粗階粗不下去
（少了很多可以塌陷的邊），而那是為了不破圖必須付的。

#### 那個「破洞偵測」原本是假的

第一版的量測工具數「本來是地面、現在變成背景」的像素，叫它破洞。照 doctrine
第 16 條把鎖邊界關掉重跑 —— **那個數字還是 0**。

原因很簡單：起伏的地面裂開之後，縫裡露出來的是**後面那一塊地面**，不是背景。
這個場景裡它根本不會變暗。那個指標從頭到尾就沒有在量它宣稱在量的東西。

真正擋住裂縫的是單元測試「鎖邊界之後，邊界上的頂點在每一階都還在」——
結構上檢查頂點在不在，而它在關掉鎖邊界時**會紅**。工具那邊的畫面差異改成
只回答它真的能回答的問題：選階有沒有守住品質契約（鎖著 0.02–0.04%，
關掉之後 0.07–0.22%）。

#### 途中修掉的一個「錯誤訊息完全指不到原因」

只把 position 交給 LOD 產生器，其餘屬性從第 0 階接回來 —— 而簡化完會**壓縮
頂點**，壓縮是逐屬性一起做的。於是那一階的頂點數變少了，法線與 UV 卻還是
原本的長度。

症狀是 `BatchedMesh.addGeometry` 丟 `offset is out of bounds`，而那句話跟
真正的原因（屬性沒有一起壓縮）之間完全沒有關聯。

### 🔨 遮蔽剔除做出來了，而它在這個內容上**幾乎剔不到東西**

上面量到密的場景有 60% 以上的 GPU 時間花在完全看不見的東西上。做完之後
量到的是：**剔掉 0 個**，而每幀多花 1–4 ms 的 CPU。

那個上限是真的，這個結果也是真的。兩者不矛盾 —— 中間差的是「拿得到嗎」。

#### 為什麼拿不到：兩層保守相乘

剔除錯的兩個方向不對稱（該剔的沒剔只是慢；不該剔的剔了是**東西不見了**），
所以每一步都往少剔的方向倒。而那些保守**疊在一起是相乘的**：

| 哪一步 | 保守多少 |
| --- | --- |
| 遮蔽物只能用**內接盒** | 實測石頭的內接盒是 ±0.41 對外接的 ±0.99 —— 面積約六分之一 |
| 被測物要用**外接球** | 球的線性尺寸是外接盒的 1.73 倍，面積三倍 |
| 邊緣再往外擴一個像素 | 小東西上這一格就佔了大半 |

於是實際情況是：2,048 個遮蔽物畫進去，緩衝只被蓋掉 **4.2%** 的像素，而
真實幾何蓋掉的是 64%。13,589 次測試裡 13,489 次倒在「footprint 裡有像素
沒被蓋到」，另外 100 次是碰到畫面邊界。剔掉的：0 個。

（覆蓋率那兩個數字是把緩衝臨時開到 1024×576 量的 —— 先排除掉「是不是解析度
太低」這個解釋。從 256×144 開到 1024×576，剔掉的數量沒有變，還是 0。）

把石頭放大、擠近，緩衝蓋掉 47.6% 之後：977 個裡剔掉 **2 個**。把外接球
換成更緊的外接盒再試一次：**0 個**。

#### 這不是 bug，是技巧與內容不合

遮蔽剔除的原型場景是「幾面牆擋住後面一整片」—— 少數大遮蔽物，各自穩穩蓋住
一大塊。單元測試裡一排箱子就是那樣，剔得乾乾淨淨（600 個裡剔掉 400 多個）。

而這個引擎的代表內容是**幾萬個散佈的小東西**，那裡的遮蔽是**集體**的：
擋住遠處那顆石頭的不是某一顆石頭，是前面那一大片。一個保守的證明器沒辦法
證明「這一大片合起來剛好蓋住它」—— 每一顆都只能貢獻自己內接盒那一小塊。

#### 所以：留著，預設關，而且會自己講

| | |
| --- | --- |
| 留著 | 大遮蔽物的內容（牆、山、建築）它是有效的，而那是很多世界的樣子 |
| 預設關 | 這個引擎的代表內容上它是淨虧 |
| 連續 120 幀幾乎剔不到就**警告** | 開著沒效果是使用者看不見的 —— 他只會覺得「開了好像沒變快」 |

那個警告是這一整段的重點。一個「開了不會怎樣」的旋鈕比沒有這個旋鈕更糟，
因為它會安靜地花掉 CPU 然後讓人去別的地方找原因。

#### 那 60% 還在那裡

上限的量測沒有被推翻，只是這條路走不到。真正走得到的方向是**不保守的**
可見性 —— 例如上一幀的深度緩衝配 GPU 端剔除，代價是延遲一幀（而那正是
worker 那條路被否決的理由）。那是另一個取捨，不是這一個。

### ✅ 間接光：原本被整個擋掉的那一半，其實是這個套件的本業

全域光照原本標成 ⛔，理由是「會把 Three.js 的強化層變成另一個渲染器」。

那個理由是對的 —— 但它只對 GI 的**一半**成立，而我拿它擋掉了整個。這是
自己給自己畫錯邊界，見 [ADR-0006](adr/0006-baked-irradiance-not-realtime-gi.md)。

| | 誰做 |
| --- | --- |
| 把畫面畫出來 | Three 的 renderer |
| 探針怎麼烘、怎麼存、怎麼串流、怎麼分預算 | 這裡 |

分界線與物理（調度不求解）、水（契約不著色）完全一樣。著色端加的只有一次
三維查表加一個 SH 求值，沒有新的 render pass。

實作是 `WW.IrradianceVolume` + `bakeIrradiance` + `applyIrradiance`：一格
三維探針網格，每顆存 SH L1（4 個係數 × RGB），放在 4 張 RGBA16F 的
`Data3DTexture` 上。用半精度是因為 WebGL2 保證它可以線性過濾 —— 而硬體的
三線性過濾正是重點：自己在 shader 裡插的話是 8 次取樣 × 4 張 = 32 次。

烘是用 **Three 自己的 renderer** 在每顆探針位置拍一張 16×16 的 cubemap，
交給 `three/addons` 的 `LightProbeGenerator` 投影成 SH。求值的常數與 Three
的 `shGetIrradianceAt` 逐字相同（0.886227 / 1.023328）—— 與簡化器用
meshoptimizer、切線用 MikkTSpace 是同一個判斷。

烘會**分幀**：每顆探針要把場景畫六次再讀回 CPU，一次做完會凍住畫面幾十秒，
而那看起來像當掉。

#### 判準是顏色，不是亮度

新的第八道 gate `pnpm gi-check`。它沒有問「畫面有沒有變亮」—— 那是最容易
造假的訊號：多留一盞環境光、係數乘錯、色調對應換一個，畫面都會變亮。

場景是為了「難以造假」設計的：紅牆紅地板、**白**箱子、一盞方向光、沒有
環境光、沒有 env map。箱子的背光面拿不到任何直接光，所以那一面上出現的
紅色只有一個來源。

```
關：R 0.0    G 0.0   B 0.0      ← 純黑，一點光都沒有
開：R 97.1   G 43.4  B 44.1     ← 紅比藍高 53
```

| 造假的方式 | 會發生什麼 |
| --- | --- |
| 偷偷加一盞白色環境光 | 紅藍一起上去，比值不動 |
| SH 係數算錯 | 整面不亮 |
| 把 intensity 調大 | 關掉那一輪也會跟著亮，A/B 沒有差 |

A/B 是把 `intensity` 設成 0／1，**走同一條著色器路徑**。換材質做 A/B 比的
是兩個不同的著色器，那個比較說明不了間接光。

第一版的量測框往下多掃到幾十行紅地板，於是「關掉」那一輪就已經有
R−B = 25.3。現在關卡自己先驗一條「關掉時 R−B 要接近 0」—— 先確定尺量的
是白箱子，後面每一條才有意義。

#### 途中修掉的兩個「不會報錯」

- `uniforms()` 每次回傳新物件。`onBeforeCompile` 只在編譯時跑一次，所以
  接上去之後改 `intensity` **完全沒有反應** —— 而 A/B 正是靠它做的，壞掉
  的話兩邊量到同一個值，然後那個「沒有差異」會被讀成「間接光沒生效」。
- CPU 版的 SH 求值沒有夾負值，shader 有。CPU 那一份的存在理由就是當
  shader 的對照組 —— 對不上的話它反而會替錯的值背書。單元測試抓到的。

不做光照的材質（`MeshBasicMaterial` 那一類）沒有 `lights_fragment_maps`
這個插入點，字串取代找不到目標時不報錯只是原樣返回 —— 那個材質靜靜地
沒有間接光。現在會警告。

#### WebGPU 那條路也做了，而且是同一個接法

`onBeforeCompile` 是 WebGL 的鉤子，`WebGPURenderer` 整條編譯路徑不經過它。
只做一邊的症狀是 WebGPU 上**靜靜地完全沒有間接光** —— 這個專案在 VAT 上
踩過一模一樣的坑，所以那之後的規矩是兩邊一起做、兩邊一起驗。

node 那一側剛好有個現成的東西就是這件事：

```js
class IrradianceNode extends LightingNode {
  setup( builder ) { builder.context.irradiance.addAssign( this.node ); }
}
```

`addAssign( irradiance )` 與 GLSL 那份的 `irradiance += …` 是同一件事換一種
語言講。所以兩條路加的是同一個量到同一個地方，不是兩套各自近似的實作。

材質那一側的掛勾是 `setupMaterialLightings`，接法與 `onBeforeCompile` 完全
一樣：**先接住原本那個**，再把自己的加進去。

gi-check 現在兩邊都跑：

```
WebGL    關 (0, 0, 0)  →  開 (94.9, 37.6, 37.6)    R−B 57.3
WebGPU   關 (0, 0, 0)  →  開 (94.2,  7.2,  7.2)    R−B 87.0
```

#### 量到一件事：node 那條路的強度改不動

`intensity` 在 WebGL 是 uniform，每幀上傳，改了立刻生效。在 node 那條路
**改不動** —— 而這是量出來的，不是設計選擇。試過三種做法：

| 做法 | 結果 |
| --- | --- |
| 做成 TSL 的 `uniform()` | JS 這側讀回 0 / 1 / 50 都對，畫面**一個位元都沒動** |
| 重接一份新的節點圖 | 沒有變化 |
| `needsUpdate = true` 強制重編 | 沒有變化 |

而同一輪裡改 `scene.background` 是立刻生效的 —— 所以畫面是新的，是那一段的
uniform 沒有被重新上傳（它掛在 lighting context 底下）。

診斷過程本身值得記：一開始看到「改了沒反應」的第一直覺是「我的節點根本沒
接上」。而把節點的輸出乘 0 之後畫面變全黑 —— 證明它**確實在圖裡、確實在
起作用**，只是那個 uniform 不更新。少了這一步會去修一個不存在的東西。

所以現在的行為是：接了 node 材質之後再改 `intensity` 會**警告**，並且說
清楚要在建構時給定。假裝有效比沒有更糟。

gi-check 那一側因此改成**開兩次頁面**做 A/B（`?gi=1` 對 `?gi=1&giOff=1`）：
同一個場景建構函式、同一組相機、同一份著色器，只有那個常數不同。

#### 順便量到的：兩個後端烘出來的量級差兩倍多

同一點同一法線，CPU 那份公式求值：

```
WebGL    1.033, 0.042, 0.042      紅綠比 24.3
WebGPU   0.444, 0.020, 0.020      紅綠比 21.8
```

**比值一致，絕對值差 2.3 倍。** 比值才是這裡要問的（間接光是不是紅的），
而絕對值的差異來自兩個渲染器把場景畫進 cubemap 的輸出差異 —— 那是這個
模組管不到的。所以關卡比的是比值，不是絕對值。

#### 限制：會動的東西不反彈光

這是選這條路的代價，而且是真的限制不是偷懶。會動的光與會動的遮蔽要即時
GI 才處理得了，那個代價是整條管線 —— 也就是 ADR-0001 擋掉的東西。

### 順手抓到一個生態系的坑

`onBeforeCompile` 是**單一插槽**，而 Three 自己的 CSM addon 是**直接指派**：

```js
material.onBeforeCompile = function ( shader ) { … };   // 蓋掉前一個
```

所以 `csm.setupMaterial(material)` 只要在 `new WW.AnimatedInstancedMesh(...)`
之後呼叫，頂點動畫就沒了 —— 一群停在綁定姿勢的模型，不報錯，幀時間還更好看。

現在會警告並說出解法（換順序）。**不去搶插槽**：搶回來只是換一個方向蓋。
