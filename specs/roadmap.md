# 里程碑與通過條件

> 動手之前先讀 [doctrine.md](doctrine.md)（準則）與 [api.md](api.md)（契約）。

里程碑只有一種形狀：

> **W*n*：開發者能做到 ___，寫 ___ 行，而且比原本快 ___。**

通過條件一律用**使用者寫的程式碼**表達，不用內部狀態表達。子系統存在與否
不是里程碑 —— 十個子系統全部打勾而沒有人能用它，是這個專案實際發生過的事。

所有數字都是這台開發機的量測。天花板是**開發用的儀器**，不是引擎的規格；
引用時要帶機器與日期，換一台機器就重跑一次。

## ✅ W1 — 換一個字就有效

把 `THREE.InstancedMesh` 換成 `WW.InstancedMesh`，其他一行不動，得到螢幕
誤差 LOD 與空間分割剔除。

| | 條件 | |
| --- | --- | --- |
| 1 | 一個真的 Three.js 專案（不是 benchmark 場景），改一行 | ✅ [`apps/example`](../apps/example) |
| 2 | 物件數提高到原本無法接受的量級，幀時間不變 | ✅ |
| 3 | 換回 `THREE.InstancedMesh`，程式照樣跑，只是慢 | ✅ `?ww=0` |
| 4 | `raycast`、`.position`、`traverse`、後處理、陰影照舊 | ✅ |
| 5 | 沒有 `update()` 呼叫、沒有初始化步驟 | ✅ |

### `ab-native-instanced` vs `ab-ww-instanced`

真實 GPU、600 幀、**交錯執行 3 輪**取中位數。程序化內容，60,000 個 instance，
同一個種子的矩陣、同一條相機路徑、同一份材質與燈光。

| | `THREE.InstancedMesh` | `WW.InstancedMesh` | |
| --- | ---: | ---: | --- |
| 幀 p50 | 197.20 ms | **19.30 ms** | **10.2×** |
| 幀 p95 | 219.21 ms | 37.00 ms | |
| GPU | 194.90 ms | **17.68 ms** | 11.0× |
| CPU | 0.40 ms | 6.10 ms | ↑ |
| 三角形 | 30,000,001 | 2,178,381 | 13.8× |
| draw call | 2 | 27,227 | ↑ |
| 前 30 幀 | 5,727 ms | **594 ms** | 9.6× |
| GPU 記憶體 | 26.5 MB | **15.2 MB** | |

「幀時間不變」的量法是問：原生跑到同樣的幀時間能放多少物件？實測
`count=6000` → 幀 p50 **21.20 ms**。所以是 **10 倍的物件數，21.20 → 19.30 ms**。

三角形少 13.8 倍是兩個機制相乘：**剔除** 60,000 → 27,418 可見（2.2×），
**LOD** 平均 500 → 79 個三角形（6.3×）。

### CPU 的組成

6.10 ms 拆開（`stats.cpuMs` 只量 `onBeforeRender` 裡面）：

```text
剔除 + 選階        3.70 ms   29,418 個 instance，126 ns 一個
renderer 送繪製    ~0.95 ms  27,227 次
Three 的場景走訪等  ~1.4 ms
```

這個場景 GPU 受限（17.68 ms），所以 CPU 的餘裕不反映在幀時間上。

### 品質契約的實測

`__ww.verifyQuality()`，640×360，參考影像用真的 `THREE.InstancedMesh`
（最細幾何、不剔除、不選階）畫。判準是「強化版的每個像素，在參考影像的
±2 像素鄰域裡找得到相符的顏色」—— 逐像素相等會被輪廓平移的抗鋸齒差異淹沒。

| | 一般 | 加上後處理與陰影 |
| --- | ---: | ---: |
| 鄰域外的像素 | 708 / 230,400（0.307%） | 329 / 230,400（0.143%） |
| 最大未匹配色差 | 56 / 255 | 74 / 255 |
| 那些像素處的影像梯度 | 67.9 | 60.3 |
| 全域平均梯度 | 7.9 | 9.4 |

梯度比值 6–8 倍代表差異集中在**輪廓**，那是「幾何誤差 ≤ 2 像素」允許的
位移。加上 bloom 與陰影之後反而更低，因為兩者都會糊掉邊緣。

陰影驗的是「有沒有真的走到」：關掉 `rocks.castShadow` 會讓 1,840 個像素
（0.8%）改變，代表 instance 確實進了 shadow map。這條路徑沒有為它寫任何
程式碼 —— `BatchedMesh.onBeforeShadow` 會轉呼叫 `onBeforeRender`。

### 換成真實資產之後

`ab-native-real` / `ab-ww-real`：同樣的數量、種子、相機路徑與燈光，內容換成
cook 過的 Avocado（682 個三角形、7 階、albedo + normal + ORM 各 1024² BC）。

四個場景在**同一輪裡交錯**執行三次取中位數，所以程序化那一組的數字與上面
那張表略有出入（205.40 對 197.20）—— 那是不同次執行的機器狀態差異，只有
同一輪裡的四個數字彼此可比。

60,000 個 instance、spread 900：

| | 原生 | WW | |
| --- | ---: | ---: | --- |
| 程序化 幀 p50 | 205.40 ms | 18.80 ms | 10.9× |
| **真實 幀 p50** | **100.10 ms** | **7.80 ms** | **12.8×** |
| 程序化 GPU | 205.02 ms | 19.32 ms | |
| 真實 GPU | 99.46 ms | 6.25 ms | |

3,000 個 instance、spread 60（物件在螢幕上大得多）：

| | 原生 | WW | |
| --- | ---: | ---: | --- |
| 程序化 幀 p50 | 16.20 ms | 6.50 ms | 2.5× |
| 真實 幀 p50 | 11.40 ms | 6.20 ms | 1.8× |

**兩件事成立：**

1. 「換一個字」的效益在真實內容上**沒有變小**（10.9× → 12.8×）。
2. 剔除與選階的 CPU 成本與內容無關：60,000 個時 126–141 ns，3,000 個時
   91–100 ns，程序化與真實之間沒有系統性差異。矩陣數學不看貼圖。

### 真實資產反而比較便宜，而原因不是「真實」

上面每一個配置裡真實資產都比較快。這**不是**內容性質，是三件事同時不同：

| | 程序化 | 真實（Avocado） |
| --- | ---: | ---: |
| LOD0 三角形 | 500 | 682 |
| LOD0 頂點 | **1,500（非索引）** | **406（索引）** |
| 階數 | 3 | 7 |
| 最粗階 | 80 三角形 | **4 三角形** |
| 材質 | 無貼圖 | 三張 1024² BC |

頂點少 3.7 倍、最粗階少 20 倍，兩者都壓過了多出來的三張貼圖取樣。
`IcosahedronGeometry` 是非索引的，用它當基準會**高估**真實內容的幾何成本。

這一組的用途因此是「A/B 的效益在真實內容上還在不在」，而不是
「真實內容貴多少」—— 後者要控制住索引與階數才問得出來。

### 明講的不相容

| | |
| --- | --- |
| `.geometry` | 回傳內部合併後的幾何，使用者傳進來的那份在 `.sourceGeometry` |
| `.isInstancedMesh` | 沒有這個旗標（有 `.isBatchedMesh`） |
| 動態矩陣 | 靜態是宣告的（`dynamic`）。沒宣告而量到格子不划算時暫停，說出來，停下來就恢復 |

## ✅ W2 — 資產不再是門檻

三條路，同一個 API 形狀 —— 差別只在第一個參數：

```js
new WW.InstancedMesh(geometry, material, n);                     // 在 worker 裡自動產生
new WW.InstancedMesh({ lods, errors }, material, n);             // 自備
new WW.InstancedMesh(await WW.load(manifest, id), material, n);  // cook 過的
```

材質走同一條路，回傳的就是 `THREE.MeshStandardMaterial`：

```js
const material = await WW.loadMaterial(manifest, 'mesh:rock');
```

第二個參數收材質 id 或**網格 id** —— cooker 的材質命名是內部的，使用者手上
有的是網格 id，所以 `MeshEntry` 自己記著該用哪個材質（schema v3）。

| | 條件 | |
| --- | --- | --- |
| 1 | 不 cook 也有 LOD | ✅ |
| 2 | LOD 產生在 worker，不卡主執行緒 | ✅ |
| 3 | cook 過的路徑仍然可用且更快 | ✅ `@webworld/cook` |
| 4 | 缺 LOD 鏈時明確說出來，不靜默用最細的幾何 | ✅ |
| 5 | cook 出來的貼圖與材質載得進來 | ✅ `WW.loadMaterial` / `WW.loadTexture` |

### 真實資產的 LOD 鏈比程序化的短

程序化球體一律拿得到 7 階，真實資產不是 —— 簡化器停在誤差上限，而 UV 接縫
與材質邊界會擋住邊塌陷：

| | 三角形 | 階數 |
| --- | --- | --- |
| Avocado | 682 | 7 |
| DamagedHelmet | 15,452 | **4**（最後一階 3,863 → 3,258，幾乎沒簡化） |
| ToyCar | 88,837 | **4** |
| Corset | 18,324 | 7 |

**階數與三角形數無關。** 用程序化資產推論「LOD 鏈有多長」會高估真實資產，
而那個高估的方向是「以為遠處省得比實際多」。

### 自動產生的成本

一份沒處理過的密網格（`IcosahedronGeometry(1, 24)`，12,500 個三角形、非索引）：

```text
LOD 產生       39.7 ms   在 worker 裡
主執行緒付了    2.1 ms   複製一份給 worker + 把結果接回批次幾何
```

兩個數字必須分開報 —— 「在 worker 裡跑」沒有主執行緒那一項撐著就只是宣稱。

### worker 起不來的時候

worker 是**內嵌成 blob** 的（`?worker&inline`），所以沒有任何路徑要解析。
靠路徑的寫法在發布出去的套件上會壞：打包工具各自處理不同，不認得的那些
不會把 worker 檔案搬進使用者的輸出目錄，於是 404 之後靜靜退回主執行緒 ——
畫面正常，只是開場多一次卡頓，沒有紅字。

代價是需要 CSP 允許 `worker-src blob:`。不允許就走退路，並且說出來。

退路要能走，資料就必須還在。`postMessage` 的轉移是當場生效的，所以
**worker 必須先報到，主執行緒才把幾何交出去**：

```text
worker 端啟動後立刻 postMessage({ ready: true })
主執行緒收到才算可用，3 秒沒收到就當它死了
```

沒有這個握手的話，`new Worker()` 同步成功、非同步失敗的那段空窗裡，第一個
請求的緩衝區已經被轉移走了 —— 錯誤傳回來時主執行緒手上沒有資料可以重算，
那個 mesh 就永久停在最細的幾何。

### cook 值不值得

同一份資產（`mesh:rock-large`，5,120 個三角形）：

| | cook 過的 | 執行期自動產生 |
| --- | --- | --- |
| 階數 | 7 | 7 |
| 三角形 | 5120/2560/1280/512/204/80/32 | 一模一樣 |
| 誤差 | 0/.0492/.0795/.1393/.1971/.2895/.3901 | 0/.0489/.0795/.1386/.1946/.2624/.3666 |
| 產生成本 | **0 ms** | 12.8 ms（worker）+ 0.7 ms（主執行緒） |
| 額外下載 | `.wwm` 191 KB（16-bit 索引） | meshoptimizer chunk 44 KB |

鏈的形狀相同，因為執行期的預設比例與 cooker 對齊 —— 兩邊參數不同的話，
「cook 過的更快」就變成在比兩組設定而不是在比 build 時與 runtime。

所以 cook 的價值是**零產生成本、16-bit 索引、不必下載簡化器**，不是畫質。

### 三個發布的套件

| | |
| --- | --- |
| `@webworld/three` | runtime，裝進使用者的 Three.js 專案 |
| `@webworld/cook` | 離線 CLI（Node）：`npx ww-cook ./assets --out ./public/cooked` |
| `@webworld/format` | 上面兩個之間的格式契約（只有型別與常數） |

**format 必須是獨立的套件**，不能兩邊各自內聯一份 —— 內聯的話
`ASSET_SCHEMA_VERSION` 會悄悄分岔，而症狀是「cook 完載不進去」且訊息指向
錯的方向。拆出來之後 npm 的版本解析就是那個契約的守門員。

**cook 也必須與 runtime 分開**：`sharp` 與 `@gltf-transform/*` 絕不能出現
在瀏覽器的 bundle 裡。同一個套件同時提供兩者就得靠 tree-shaking 保證那件事，
而那是一個壞掉時完全沒有徵兆的保證。

`tools/package-check` 把三個都打包、裝進乾淨專案、真的跑一次 cook，比對兩邊
解析到的 `ASSET_SCHEMA_VERSION` 是否一致，最後用 esbuild 把它打包成一個網站
在瀏覽器裡跑起來。

最後那一段**只 serve 打包產出**，`node_modules` 讀不到 —— 那才是使用者網站
的樣子。它抓過一個真的會出去的 bug：worker 的 URL 被建成絕對路徑，在任何
使用者的站台上都是 404。當時的檢查全綠，因為它用 `autoLod: false`，剛好繞開
唯一會壞的那條路。

### 下載量

`apps/example` 建置後（把動態 `import()` 換成靜態的做對照）：

```text
主套件                608.7 kB   靜態 import 的話是 644.8 kB
lod-worker chunk       44.9 kB   只有走自動 LOD 才抓
lod-generation chunk   44.0 kB   只有 worker 不可用的退路才抓
```

meshoptimizer 走動態 `import()`，所以自備 LOD 鏈的專案不會下載它。

### 誤差的兩條規則

**每一階都從第 0 階簡化，不是從上一階。** `simplify()` 回傳的誤差是相對於
傳進去的網格，串接會拿到增量而不是相對 LOD0 的總誤差 —— 而品質契約講的是
「跟原始幾何差幾個像素」。實測 icosphere(3) 上串接會低估最多 23%，方向是
在太近的距離挑到太粗的階。

**丟掉被支配的階。** 簡化器對每個目標三角形數各做一次貪婪選擇，所以誤差
不保證隨階數遞增：球體會出現「第 5 階 0.3888（80 個三角形）比第 6 階
0.3709（32 個）還大」。前者同時比後者多三角形又比它不準，留著只是佔空間。
選階本身不會因此出錯，但「更粗 = 更不準」是所有下游都在假設的性質。

## ✅ W3 — 世界比記憶體大

```js
WW.worldFor(scene).stream({
  cellSize: 120,
  radius: 600,
  load(cx, cz, place) {
    for (let i = 0; i < 400; i++) place(rocks, matrix.compose(/* … */));
  },
});
```

| | 條件 | |
| --- | --- | --- |
| 1 | 長時間巡遊，記憶體漂移 ≈ 0 | ✅ |
| 2 | 使用者只回答「這格有什麼」，不碰載入時機、遲滯、優先序 | ✅ |
| 3 | 不開串流時一切照常運作，只是內容全部常駐 | ✅ |

直線走 600 個 tick，途中載入 750 格、卸載 823 格：

```text
                 開始      結束
geometries          1         1
textures            1         1
instance 數    38,400    38,400
capacity       60,000    60,000
JS heap      42.58 MB  43.23 MB
failedLoads / cancelled / pending    0 / 0 / 0
```

前四項是確定性的，那是能下結論的部分。JS heap 受 GC 時機影響，+0.65 MB
落在雜訊裡（每次載入會配一個暫存陣列）。

排程（遲滯、預算、優先序、自適應幀預算）沿用 `internal/engine` 的
`WorldStreamer`，payload 泛型化成任意型別。

**幀預算是量出來的，不是猜的。** 串流觀察這台機器安靜時的幀間隔當基準，
預算 = 基準 × 1.5。60 Hz、144 Hz、弱機器各自得到自己的值。

**`load` 是把東西交出去，不是回傳陣列。** 回傳陣列的話
`[m.makeTranslation(a), m.makeTranslation(b)]` 兩筆會指向同一個被改到最後
一次的 `Matrix4`，而重複使用暫存物件是 Three.js 到處都在做的事。
症狀是整格的東西疊在同一個點上，數量與統計全部正常。

## W4 — 兩端各自到極限

| | 條件 | |
| --- | --- | --- |
| 1 | 先有天花板數字 | ✅ 三角形那個修正過，見下 |
| 2 | 四格模型剩下三格逐一填上，附上相對天花板的位置 | 🟡 三格都動過：GPU 演算法層 ✅、機制層已結案、CPU 機制層縮到 15 倍 |
| 3 | 全部用真實資產量測 | ✅ `ab-*-real`，`pnpm cook:real` |

### 天花板（`ceiling-*` 場景，2026-08-17）

| | | 怎麼量的 |
| --- | ---: | --- |
| **CPU：純讀取下界** | **208,000 instance/ms**（5 ns） | 同一批矩陣，只把 64 個位元組讀進來 |
| CPU：剔除＋選階 | **13,780 instance/ms（73 ns）** | 我們自己的迴圈，物件不在場景裡 |
| **GPU：三角形（索引）** | **490,100 三角形/ms** | 20,000 instance × 1,620 面，全畫不剔除 |
| GPU：三角形（非索引） | 146,200 三角形/ms | 同一份幾何，只是沒有焊接 |
| **GPU：繪製呼叫** | **6,424 次/ms**（156 ns） | 30,000 次 multi-draw，每次 2 個三角形 |

「剔除＋選階每毫秒幾個」不能當天花板 —— 它量的是我們自己的實作，拿來對照
永遠是 100%。純讀取下界才是這件事最快能多快，**兩者差 15 倍**。

#### ✅ 快取的排列順序要對齊走訪順序（機制層）

包圍球快取原本依 **instance 編號**存，而走訪是依**空間格順序**走的 ——
所以每一次讀都是陣列裡的隨機位置。

那在小工作量上看不出來：六萬個 instance 的快取是 960 KB，塞得進 L2。
一百萬個是 16 MB，於是每一次讀都是一次快取失誤。

把快取排成走訪順序（格子重建時一起重排，本來就是同一個時機）之後：

| 一百萬個 | 之前 | 之後 | |
| --- | ---: | ---: | --- |
| CPU 總計 | 29.787 ms | **9.596 ms** | 3.1× |
| ↳ 走訪 | 27.204 ms | **6.989 ms** | **3.9×** |
| 每個 instance | 146 ns | **37 ns** | |

25 萬個那一格的 CPU 也從 1.855 → **1.083 ms**。

**一行邏輯都沒改**，只是換了資料的排列順序。這正是機制層的形狀：同樣的
工作，做得便宜一點。

> **這個問題是「拆解對不上」才發現的。** 一百萬個時 CPU 是 26.475 ms，而
> 「逐一走訪的數量 × 先前量到的每個 59 ns」只有 6.5 ms —— 差四倍。
> 帳不平就代表我對自己的程式有錯誤理解，所以先把 `cpuMs` 拆成
> 空間格／走訪／烘焙三項。拆完才看到烘焙只花 1.8 ms（我原本猜是它），
> 27.2 ms 全在走訪。

#### ✅ 世界空間包圍球快取（機制層）

熱迴圈原本每個 instance 要讀 12 個矩陣元素，做九次乘加算最大縮放、再做
九次把球心轉到世界空間 —— 而那些值**只在矩陣改變時才會變**。

改成矩陣一改就算好 `[cx, cy, cz, radius]`，熱迴圈只讀 4 個 float：

| | 之前 | 之後 | |
| --- | ---: | ---: | --- |
| `ceiling-cpu` 每個 instance | 123 ns | **73 ns** | 1.7× |
| 離純讀取下界 | 30 倍 | **15 倍** | |
| `ab-ww-real`（關 HLOD） | 136 ns / 4.017 ms | **59 ns / 1.738 ms** | **2.3×** |

代價是每個 instance 多 16 個位元組，以及矩陣改變時多走一趟。

**快取失效必須跟空間格綁在一起。** `setMatrixAt` 不會動
`instanceMatrix.version`，所以只看版本號的話，用 `setMatrixAt` 的人會永遠
拿到舊的包圍球 —— 物件搬走了，剔除與選階卻還在看原本的位置。

#### 三角形天花板曾經低估 3.35 倍

原本這個場景用 `IcosahedronGeometry`，而它出廠是**非索引**的 —— 每個三角形
帶三個獨立頂點。於是它量到的是頂點吞吐，卻被當成三角形吞吐報出去。

同一份幾何，唯一的差別是有沒有焊接：

| | 三角形/ms | 頂點/ms | 每三角形頂點 |
| --- | ---: | ---: | ---: |
| 索引 | **490,100** | 253,800 | 0.52 |
| 非索引 | 146,200 | 438,600 | 3.00 |

**真實資產一律是索引的**（Avocado 682 個三角形只有 406 個頂點），所以要用
的是 490,100 那個數字。

頂點速率反而是非索引的比較高，這代表索引之後瓶頸已經不在頂點端了 ——
兩個數字都不是「硬體上限」，它們都取決於內容。所以這個場景現在**兩個都報**，
擺在一起就藏不住「這份幾何的頂點三角形比是多少」。

低估天花板的後果比高估嚴重：它會讓人以為已經接近硬體極限，於是停在不該停
的地方，而且停得理直氣壯，因為手上有數字。

### GPU 時間的組成

W1 的 A/B（2,178,381 三角形、27,227 次繪製）。這個場景的幾何是**非索引**的，
所以對照的是非索引那個天花板：

```text
三角形   2,178,381 ÷ 146,200 = 14.9 ms
繪製呼叫    27,227 ÷   6,756 =  4.0 ms   ← 21%
                              ──────
                         合計 18.9 ms（實測 17.68）
```

兩項相加大致就是全部。繪製呼叫佔 21% —— `BatchedMesh` 在 WebGPU 上是每個
可見 instance 送一次 `draw()`，不是真正的 multi-draw-indirect。

**這個比例只對這種內容成立。** 換成索引幾何，同樣的三角形數只要 4.4 ms，
於是繪製呼叫的佔比會跳到 4.0 / 8.4 ≈ **48%**。真實資產全部是索引的，所以
繪製合併在真實內容上的價值遠高於這裡看到的。

### 真實 PBR 材質的價碼

`ab-native-real`，DamagedHelmet（15,452 個三角形、4 階），3,000 個 instance、
spread 300。這是最乾淨的量法：**單一 draw call、全部在 LOD0**，三角形數是
精確的而不是從 LOD 分佈估的。

```text
3,000 × 15,452  =  46,356,000 個三角形
GPU 162.51 ms   →     285,000 三角形/ms
天花板（索引、無貼圖）    490,100 三角形/ms
```

**58% 的天花板，也就是真實 PBR 材質讓每個三角形貴 1.72 倍。** 那個倍數裡
有三件事還沒拆開：三張 1024² 貼圖的取樣、法線貼圖需要的切線屬性、以及
48 位元組的頂點（天花板場景是 position + normal + uv）。

同一份內容換成 `WW.InstancedMesh`：

| | 原生 | WW | |
| --- | ---: | ---: | --- |
| 幀 p50 | 165.10 ms | **22.00 ms** | **7.5×** |
| GPU | 162.51 ms | 21.82 ms | |
| 三角形 | 46,356,000 | 約 4,872,000 | 9.5× |

繪製呼叫在這裡幾乎不算數：1,390 次 ÷ 6,424 = 0.22 ms，佔 1%。

**所以「三角形與繪製呼叫誰重要」也是內容決定的**：輕幾何（Avocado 682 個
三角形，60,000 個）是繪製呼叫，重幾何（Helmet 15,452 個）是三角形。這正是
第 3 條說的「哪個比較大不是該修哪個」—— 兩端都要各自到它自己的極限。

### 繪製呼叫值多少錢

`ceiling-gpu-drawcalls` 有對照組：**同樣的幾何、同樣的擺放、同樣 30,000 個
instance**，只差送法。

| | 幀 p50 | GPU | 幀 p95 |
| --- | ---: | ---: | ---: |
| 30,000 次繪製（`BatchedMesh`） | 6.35 ms | **5.62 ms** | **12.71 ms** |
| 1 次繪製（`InstancedMesh`） | 6.10 ms | **0.61 ms** | 6.50 ms |

**每次繪製 167 ns，佔那個場景 GPU 時間的 89%。而 p95 直接翻倍** —— 網站上
那個比 p50 重要。

同一組場景在 WebGL2 上（`--param forceWebGL=1`）：

| | 幀 p50 | GPU |
| --- | ---: | ---: |
| 30,000 次繪製 | 18.75 ms | 6.29 ms |
| 1 次繪製 | 6.10 ms | 1.28 ms |

**GPU 差額 5.01 ms，與 WebGPU 完全相同。** 所以 167 ns 是硬體與驅動的每次
繪製成本，不是某個 backend 的產物 —— 換 backend 換不掉。兩邊只有 CPU 側
差很多（18.75 對 6.35），那是 WebGPU 的迴圈比 WebGL2 的退路便宜。

這個場景裡**每一次繪製的 index range 都相同**，所以 167 ns 是固定的每次開銷，
不是幾何切換的成本。推論：**按 LOD 階排序不會有幫助，只有減少次數才有用。**
（先量再做省下的就是這種工。）

W1 的 A/B 有 27,227 次繪製 → 4.55 ms。

### 為什麼還沒做繪製合併

`WW.InstancedMesh` 的所有 instance 共用同一份來源幾何，只有 LOD 階不同 ——
所以 27,227 次繪製理論上可以收斂成**階數**次（3 到 7）。把可見清單按階排序
之後，每一階就是一段連續的 instance，一次 instanced 繪製就送得完。

而且 shader 不必改：Three 的 batching node 在 WebGPU 上用 `instanceIndex`
去查 `_indirectTexture`，而 `firstInstance` 會把 `instanceIndex` 平移到該段
的起點，查表結果剛好正確。

**卡在 Three 的 backend。** `WebGPUBackend.draw()` 對 `isBatchedMesh` 的分支
是每個 instance 一次 `drawIndexed(counts[i], 1, …)` ——`instanceCount` 寫死
是 1，而那個分支排在 indirect draw 的 `else if` 之前，所以 BatchedMesh 永遠
走不到 `geometry.setIndirect()` 那條路。

三條路，都不是這一層能自己決定的：

| | |
| --- | --- |
| 上游修 Three | 在那個迴圈裡把相同 `(start, count)` 的連續段合併成一次 instanced 繪製。約十行，而且**每一個 BatchedMesh 使用者都受益** |
| 自己畫 | 不再是 `BatchedMesh`，於是 `instanceof`、raycast、後處理全部要自己重來 —— 那正是 ADR 0001 用掌控權換相容性時說好要付的代價 |
| 接受並寫下來 | 現在這樣 |

#### 做完 HLOD 之後這題就結束了

當初的判斷是「先做 HLOD，做完重量一次再決定」。量完的結果是**不要動**：

| | 繪製次數 | 佔 GPU 時間 |
| --- | ---: | ---: |
| HLOD 之前 | 27,418 | **70%** |
| HLOD 之後 | 1,830 | **15%** |
| 假設自己畫 | 約 7 | — |

自己畫能再省 `(1830 − 7) × 167 ns` = **0.30 ms**。而這台機器的幀時間已經
卡在 **6.10 ms 的顯示上限**（空場景也是這個數字），所以那 0.30 ms 不但只佔
5%，還根本反映不到畫面上 —— 連驗證都驗不出來。

拿「使用者的材質、raycast、陰影全部要重寫」去換一個看不見的 0.30 ms，
差得很遠。

**先繞過去的價值就在這裡**：直接改架構的話，現在會付了全部的相容性代價，
然後發現省下的東西被顯示上限吃掉。

所以**機制層這一格暫時堵住了**，價值轉移到演算法層：減少可見 instance 數
（HLOD、遮擋剔除、impostor）同時砍掉三角形與繪製呼叫，而那完全在這一層
控制得了。

### 遠景幾乎全是繪製呼叫

把 `ab-ww-real`（Avocado、60,000 個、GPU 6.25 ms）拆開。LOD 分佈
`0/0/4/46/93/227/28522`，對應 Avocado 的 `682/341/170/68/26/9/4`：

```text
繪製呼叫  27,418 × 167 ns              = 4.58 ms
三角形    約 122,000 ÷ 490,100 tri/ms  = 0.25 ms
                                        ──────
                                   合計 4.83 ms（實測 6.25）
```

**繪製呼叫佔 73%，三角形只佔 4%。** 遠處那 28,522 個 instance 每個只有
4 個三角形，卻各自付一次完整的繪製成本 —— 送出去的錢比畫的東西貴 19 倍。

這就是 HLOD 的形狀：把一個 cell 的遠景 instance **烘成一份合併幾何**，
那個 cell 就從幾千次繪製變成一次。

### ✅ 遠景合併（HLOD）

`ab-ww-real`，Avocado、60,000 個。同一個場景開關 `hlod`：

| | 開 | 關 | |
| --- | ---: | ---: | --- |
| 繪製次數 | **1,830** | 27,418 | 15× |
| 合併格數 | 494 | 0 | |
| GPU | **2.06 ms** | 6.59 ms | 3.2× |
| 幀 p50 | **6.10 ms** | 8.60 ms | |
| **幀 p95** | **6.40 ms** | 16.20 ms | **2.5×** |
| 剔除＋選階 | **0.392 ms** | 4.017 ms | 10× |
| LOD 分佈 | 0/0/4/**46/93/227**/977 | 0/0/4/**46/93/227**/28522 | |

**畫質沒有動。** 細階的 46/93/227 兩邊完全相同 —— 該用細節的那些 instance
一個都沒被降級，被合併掉的全部來自最粗階。

CPU 少 10 倍是意料外的紅利：整格合併之後，那一格的逐 instance 視錐測試與
選階完全跳過。

#### 兩個 bug，兩個都「畫面完全正常」

**合併自己寫矩陣，被當成內容在動。** `setMatrixAt` 會把空間格標成過期，
而合併正好要寫一次 —— 於是每幀都失效，整個空間分割被當成動態內容
關掉。幀時間變差，畫面正常，沒有錯誤。是場景自我檢查抓到的，單元測試
沒看到（它們只跑一兩幀）。

**合併的距離判斷漏掉 instance 縮放。** 第一次量出來的數字更漂亮
（繪製 509 次、GPU 1.85 ms），但 LOD 分佈露餡：細階的 366 個掉到 22 個。
逐一判斷用的是「縮放 ÷ 距離」，合併若只用「1 ÷ 距離」就等於把物件當成小了
25 倍，於是提早合併 —— **那不是變快，是偷偷降畫質，而且效能數字更好看**。

第二個特別危險：只看幀時間的話會直接當成成功。

#### 代價

| | |
| --- | --- |
| 記憶體 | 合併等於把最粗階複製一份。超過 `hlodBudgetMB`（預設 64）就不啟用，並且說出來 |
| 剔除粒度 | 合併過的格子只剩 cell 層級的視錐剔除，沒有逐 instance 的。那些格子本來就遠、螢幕上很小 |
| 重建 | 矩陣一改就要重烘。舊的會先拆掉（`deleteGeometry`／`deleteInstance`），不會愈積愈多 |

而這件事完全不需要 Three 改任何東西 —— `BatchedMesh` 本來就支援多份幾何，
而且 `setInstanceCount()` 與 `setGeometrySize()` 都是公開 API，所以 LOD 鏈
從 worker 回來之後還能把容量長大。

形狀（還沒實作）：

```text
lodReady 之後
  每個 cell 烘一份合併幾何 = 該 cell 全部 instance 的最粗階，變換烘進頂點
  addGeometry(merged) + addInstance()，矩陣是 cell 中心
collect() 裡
  該 cell 的每個 instance 都會挑最粗階  →  只送那一次合併繪製，跳過整個 cell
  否則                                  →  照現在逐 instance 送
```

**代價是記憶體，而且必須有預算。** 合併幾何等於把最粗階複製 N 份：Avocado
的最粗階只有 4 個三角形，60,000 份仍然很小；DamagedHelmet 的最粗階是 3,258
個，同樣份數就爆了。所以超過預算就不啟用 HLOD，並且**說出來** —— 靜靜不啟用
的話，使用者會以為自己拿到了它。

### 容量掃描：這台硬體到底放得下多少

**幀時間會飽和，容量不會。** 這台機器的幀時間卡在 6.10 ms 的顯示上限
（空場景也是這個數字），所以「多快」問到某個點就問不下去了。改成問
**「維持流暢的前提下放得了多少東西」**，那個數字永遠有下一個量級可以問。

`ab-ww-real`（Avocado + 完整 PBR），一路往上加：

| instance | 幀 p50 | GPU | 繪製次數 | 合併格數 | CPU/instance |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 60,000 | **6.10 ms** | 2.04 ms | 2,094 | 494 | 14 ns |
| 250,000 | **9.60 ms** | 6.60 ms | 10,980 | 1,925 | **9 ns** |
| 1,000,000 | **23.90 ms** | 20.86 ms | 81,592 | 7,442 | **9 ns** |

CPU 分項（一百萬個）：空間格 0.666 + 走訪 2.695 + 烘焙 0.967 = **4.336 ms**。

**一百萬個那一格要暖機 900 幀。** 遠景合併是惰性烘的，每幀 2 ms 的預算，
而 15,876 格要烘十幾秒。暖機 120 幀時量到 40.20 ms，900 幀時 **23.90 ms** ——
兩個都是真的，但前者量的是暖機途中。

那個十幾秒**不只是量測問題，是真實的使用者體驗**：網站載入後有十幾秒是慢的。
下一步是把烘焙搬進 worker（它是純陣列運算，可以轉移），那樣預算才能開大。

**250,000 個帶完整 PBR 材質的物件維持在顯示上限附近。**

#### 掃描抓到一道自己造成的懸崖，修了兩次

第一次掃的時候一百萬個是 **100.85 ms，而合併格數是 0**。

記憶體預算原本是「全有或全無」：算出整份要多少，超過就**一格都不合併**。
於是 250,000 個好好的，一百萬個掉回 457,540 次繪製 —— 不是硬體撐不住，
是自己把功能關掉了。

| 一百萬個 | 全有或全無 | 用到為止 | **槽位池** |
| --- | ---: | ---: | ---: |
| 幀 p50 | 100.85 ms | 59.50 ms | **45.30 ms** |
| 合併格數 | 0 | 3,378 | **5,274** |
| 繪製次數 | 457,540 | 238,592 | **180,340** |

**第一次修**是「一格一格花到預算用完」—— 平順了，但一百萬個仍然只涵蓋
3,378 / 15,625 格。

**第二次修才對到根因**：一次烘全部格子的話，記憶體需求等於**世界有多大**。
但任何一刻真正需要合併幾何的只有**看得見的遠景**，而那個數量由視野決定。

所以改成一池固定大小的槽位反覆換內容：

```text
槽位大小 = 最大那一格的空間（大小不一的話回收後換不進去，池子會碎掉）
槽位數量 = 預算 ÷ 槽位大小
內容      = 按需要換，最久沒畫到的先回收
```

同樣 64 MB，合併格數 3,378 → **5,274**，因為槽位是重用的。

`BatchedMesh.setGeometryAt` 可以就地替換已保留範圍裡的幾何。**不能用
「刪掉再加」** —— `addGeometry` 會重用 id 但一律從 `_nextVertexStart` 往後
配，freed 的範圍要等 `optimize()` 才回收，所以那樣是會漏的。

#### 烘焙是惰性的，而且用時間當預算

收集時登記「這一格想合併」，之後在每幀 **2 ms** 的預算內烘。還沒烘好的
那幾格照原本逐 instance 送 —— 畫面完全正確，只是那幾幀還沒省到。

停下來等它烘完會變成一次卡頓，而那正好發生在**相機剛轉過去**的時候。

**預算用時間而不是「幾格」**：一格的成本差好幾個數量級（最粗階 4 個三角形
對 3,258 個），而且不同機器差很多。固定格數在小內容上浪費、在大內容上爆掉
—— 那正是準則裡說的「作者在自己機器上調好」那種常數。

> **懸崖是掃描才看得到的東西。** 只量一個工作量的話，250,000 那一格看起來
> 完美無缺，而且兩次修正都不會被發現有必要。

### 遮擋在這種內容上不值得做

先前否決遮擋剔除的那次，用的是一片散開的石頭 —— 那種內容裡根本沒有東西
擋住東西，量出來當然是「沒有價值」。所以用 **Sponza**（圖學界的標準遮擋
測試場景：室內、有牆、有柱子）重新問一次。

`occlusion-sponza`，103 個 primitive、262,267 個三角形，相機站在中庭：
幀 p50 9.30 ms、GPU **7.43 ms**。拆開對照天花板：

```text
三角形    262,267 ÷ 490,100 tri/ms = 0.54 ms
繪製呼叫      103 × 167 ns         = 0.02 ms
                                   ──────
                       幾何那一側    0.56 ms   ← 只佔 7.5%
```

**剩下的 6.9 ms 是 fragment 與材質，而那是畫在看得見的像素上的。**
被擋住的片段早就被硬體的 early-Z 丟掉了（Three 對不透明物件會由近到遠
排序，正好餵給 early-Z）。

遮擋剔除能省的**只有幾何那一側** —— 也就是最多 7.5%，而且實際上只是其中
完全被擋住的那部分。**不值得做。**

> 曾經用深度預繪製當探針，但它慢了 5.82 ms，遠超過一趟幾何該有的
> 0.54 ms —— 慢的原因不只是「多畫一趟」，而原因沒查清楚。那條路徑已經
> 從場景裡移掉了：**一條自己都不信的量測比沒有量測更糟**。上面的結論
> 來自拆解，不依賴它。

### ✅ 靜態變成宣告，門檻換成量測（2026-08-17）

原本是「矩陣連續 8 幀在變就**永久**停用空間分割」。兩個問題：8 是我訂的，
而永久停用讓載入時抖動幾幀的內容永遠拿不回空間分割 —— 畫面完全正常，
只有幀時間差。那正是 doctrine 說的「靜靜改變行為」。

改成宣告（`options.dynamic`），沒宣告時用**量出來的**帳判斷。順手量到的
第一個數字就推翻了原本的猜測：

| instance 數 | 每幀整份重建（17 幀累計） | 省下的走訪 | |
| ---: | ---: | ---: | --- |
| 2,500 | 8.16 ms | 0.10 ms | 81 倍不划算 |
| 10,000 | 16.30 ms | 0.83 ms | 20 倍 |
| 40,000 | 66.80 ms | 3.89 ms | 17 倍 |
| 160,000 | 267.64 ms | 16.63 ms | 16 倍 |

**每幀整份重建在任何規模上都不划算**，而且比例不隨規模改善。所以暫停是
對的判斷 —— 舊的門檻猜對了結論，只是沒有依據。

`HLOD_MIN_INSTANCES` 一併從 4 改成推導值 2。A/B 交錯量測（60,000 個真實
資產）：合併 494 格、槽位 1024/1024、p50 6.10 ms —— **兩邊完全相同**。
原因是空間格的目標是每格 64 個，所以這個下限只咬得到分佈的尾巴。
它值得改是因為 4 沒有論證，不是因為 4 比較慢。

### ❗ 串流期間會失去空間分割 —— 因為格子只能整份重建

上面那張表的直接後果：串流每載入一格就寫一批矩陣，於是載入中的每一幀
都要整份重建，而帳算不過來 → 暫停。載入停下來之後會恢復（這一版修掉了
永久停用），但**載入中就是逐 instance 走訪**。

這是機制層的洞，不是演算法層的：往格子裡塞 20 個 instance 不該需要把
10,000 個重新排序一次（doctrine 機制層第一問）。增量插入之後串流全程都
保得住空間分割。

#### 儀器先做好了：`streaming-move`（2026-08-17）

相機直線前進穿過世界，每十幀跨一格。34,459 個常駐 instance：

| | |
| --- | ---: |
| **spatial（有用到空間格的幀）** | **4.3%** |
| 平均逐一測試 / 常駐 | 32,978 / 34,459 |
| 空間格 CPU | 0.224 ms |
| 走訪 CPU | 0.988 ms |

**格子在串流全程幾乎是關著的。** 每一幀都在走訪全部三萬四千個。

#### 這個場景一開就抓到三個真的 bug

三個都是「畫面正常或幀時間正常，所以沒人看得出來」，而且三個都只有在
**內容會變動**的場景裡才浮現 —— 在那之前所有場景都是一次擺完的。

| bug | 症狀 | 為什麼靜態場景抓不到 |
| --- | --- | --- |
| `BatchedMesh` 快取的包圍球過期 | 相機走遠之後**整個物件一格都不畫**，console 一片乾淨 | 第一幀矩陣就都在了，那顆球算對了 |
| HLOD 槽位池每次重建都重配 | GPU 記憶體三秒漲 90 MB；空間格那步 0.05 → **7.38 ms**，幀 p50 **44.25 ms** 且一路變差 | 空間格只重建一次 |
| `ensureCapacity` 沒算槽位佔的 instance id | 串流丟 `Maximum item count reached`，78 幀裡 **117 格內容不見** | 容量從不成長 |

第一個的修法是關掉物件層級的視錐剔除（我們自己做的是逐 instance 的精確
剔除，外面那一層沒給我們任何東西，只帶來一顆會過期的球）。第二個是讓池子
只長大不重配。第三個是長大前先把槽位的 instance 讓出來、長大後排到新的尾巴。

#### 然後在同一條線上抓到第四個，而它比前三個嚴重

**`apps/example` 的 JS heap 是 1,005 MB。**

| | heap | 首次可見 | 外層頁面 rAF（3 秒） |
| --- | ---: | ---: | ---: |
| 這一輪開始時 | 165.6 MB | 499 ms | 128 幀 |
| 上面三個修完之後 | **1,005.7 MB** | 1,109 ms | 25 幀 |
| 修好之後 | **43.6 MB** | 407 ms | 172 幀 |

W5 記錄的是 13.8 MB —— 那是遠景合併之前量的，而合併進來之後**沒有人再看
那個數字**（site-check 只把它印出來，沒有擋）。所以 165 MB 那一步也是靜靜
發生的。

根因有兩層：

1. **記憶體估算只算了 position。** `slotBytes = 頂點數 × 12`，而帶法線與 UV
   的幾何是 32 B/頂點。低估三倍的後果是預算「看起來還很寬」，於是實際配下去
   的量是預算的好幾倍。
2. **預設預算是「要多少給多少，護欄 512 MB」。** 那在 benchmark 上是對的，
   在網站上是一張空白授權書 —— 典型的「把我這裡當成全世界」（這台開發機
   有很多顯示記憶體）。

改成 32 MB 的政策預設（不夠時說出想要多少、拿到多少），並且**讓
site-check 擋 heap**。真實 cook 過的內容在 32 MB 下拿到 1,365 / 1,395 個
槽位 —— 98%，所以頭條數字沒有變。

#### 順手學到：貴的不是「配很多槽位」，是「槽位被回收」

中途試過一個看起來更聰明的版本：池子只配「同時看得見幾格」而不是「總共
幾格」。實測否決了它 —— **繪製次數只多了 11%，GPU 卻從 2.79 漲到 7.90 ms**。

原因是 `BatchedMesh.setGeometryAt` 會把整個保留範圍標成 `needsUpdate`，所以
每一次重烘都是一次緩衝區重傳。池子剛好等於工作集時，相機一動就互相回收，
於是每幀都在重傳。一格一個槽位的話穩態下再也不烘，成本回到零。

這也是為什麼記憶體的解法是**壓小每個槽位**（槽位大小改用 `instancesPerCell`
而不是「最大那一格」，離群的大格子不再撐大每一個槽位），不是壓少槽位數。

#### 兩個機制層的優化，還不夠

| | 之前 | 之後 |
| --- | ---: | ---: |
| 空間格重建（34,000 個） | 6.047 ms | **1.189 ms**（計數排序） |
| 空間格重建（160,000 個） | 33.306 ms | **5.831 ms** |
| 整個空間格步驟（490,000 個常駐，串流） | 356 ms | **38.5 ms** |
| ↳ 其中 HLOD 重新分組 | 339 ms | **21.3 ms** |

而它省下的走訪，在 490,000 個時是 **9 ms/幀**（走訪 12.4 → 3.4 ms）。
38.5 對 9 —— 還是四倍算不過來，所以格子在串流中仍然被暫停（spatial 9%）。

**結論沒變，但變得清楚了：全份重建再快也不夠，要的是增量維護。**

#### 第一步做完了：包圍球快取只算改過的那幾段

先量再做，而量出來的第一名不是格子：**每幀走訪的 11.93 ms 裡有 6.76 ms 是在
重算全部 490,000 個包圍球**，而那一幀真正改過的不到千分之一。

改成追蹤「改過的編號區間」（最多 8 段，超過就退回整份重算）。兩個地方要
特別處理，兩個都是實測才發現的：

| | |
| --- | --- |
| `count` 每幀都在變（串流每載入一格就變一次） | 那條路原本走一般的失效 → **每幀把整份標髒**，增量等於沒做。改 count 不動任何矩陣，所以只讓格子過期 |
| 快取陣列長大時換了一塊新的 | 沒把舊的搬過去的話舊資料歸零，而半徑 0 的包圍球會被靜靜剔掉 |

| | 之前 | 之後 |
| --- | ---: | ---: |
| 包圍球（490,000 個常駐） | 6.76 ms | **3.6 ms** |
| 整個走訪 | 11.93 ms | **8.9 ms** |

剩下的 3.6 ms 幾乎全在**格子重建的那幾幀** —— 走訪順序一換，「第幾號髒了」
就對不到「快取的第幾格」，只能整份重算。要再往下就得有一張反向表。

正確性靠一組拿 Three.js 自己的 `Frustum` + `Sphere` 走世界座標的獨立實作
交叉比對：每做一次變動就比一次「該看得見的都還在嗎」。漏標一段的症狀是
畫面破洞而所有數字正常，所以這個測試自己也要驗 —— 故意把區間標窄之後它
確實會紅。

#### 第二步：不要蓋一座馬上就拆的橋

量到 p95 **31.93 ms**，而尖峰的形狀正好是一次格子重建（30 ms）。原因是恢復
的規則太急：「有一幀沒動就恢復」，而串流不是每一幀都在寫矩陣（載入本身有幀
預算）。於是**恢復 → 重建 → 又不划算 → 再暫停**，來回震盪，每一輪丟掉 30 ms。

改成要先回本：暫停期間累計「不用格子多花的走訪」，累積到超過那次重建才恢復。
兩邊都是量到的，不是幀數門檻。

中間走錯一次，而錯的地方值得記下來：**回本的帳一旦被打斷就要歸零**。第一版
讓它跨越「動了」的幀繼續累加，於是算出「該重建了」—— 但那次重建只撐得住
一幀（下一幀又有內容進來），等於花 30 ms 換一幀 6.9 ms 的節省。回本估的是
「靜下來之後每幀省多少」，而那筆錢只有在格子撐得住時才拿得回來。

| 490,000 個常駐、串流中 | 之前 | 之後 |
| --- | ---: | ---: |
| 幀 p50 | 12.15 ms | **9.55 ms** |
| 幀 p95 | 31.93 ms | **22.41 ms** |
| 重建次數（398 幀內） | 一路都在 | 16 次，而且都在暖機期 |

剩下的 p95 不是重建了 —— 是載入本身（建幾何、上傳）。那是另一件事。

#### ✅ 第三步：分割本來就在手上，不必算

前兩步都是在讓「重建」變便宜。第三步是發現那件事**根本不必做**。

空間分割的重點是「一次剔掉一整群在一起的東西」，而串流**已經知道哪些東西
在一起**了 —— 它就是照 cell 載入的，一次 `writeMatrices` 就是一格的內容，
寫在一段連續的編號上。原本的做法是把那個資訊丟掉，再用排序重建出來。

所以加了一張區塊表（`InstanceBlocks`）：邊界在寫進來的當下就知道，包圍球
在同一趟順手算完（那段記憶體本來就在手上）。每幀的成本是「測幾十顆球」。

| 490,000 個常駐、串流中 | 空間格 | 區塊表 |
| --- | ---: | ---: |
| 有做空間剔除的幀 | 4.0% | **100%** |
| 逐一測試 | 465,000 | **128,533** |
| 分割本身的 CPU | 1.5 ms（重建時 30 ms） | **0.013 ms** |
| 走訪 | 8.9 ms | **5.6 ms** |

34,000 個常駐時同樣是 100%，逐一測試 33,331 → 11,565，走訪 0.74 → 0.55 ms。

兩者是互斥的：只要有人用 `setMatrixAt` 動過區塊裡的東西，那一塊的包圍球
就過期了，整張表作廢、退回空間格。**過期的包圍球會讓一整塊憑空消失**，
所以寧可作廢也不猜。

猜錯過一次卸載的形狀：以為是「把最後一塊搬進洞裡」，實際上串流是「把洞
後面的全部往前挪」。猜錯的代價是每一次卸載都讓整張表作廢 —— 而症狀是
「加了新東西但數字沒有變好」，不是壞掉。

正確性靠一組**掃 48 個角度**的交叉比對。單一視角測不出來：只有視錐邊界
正好切在區塊邊界上時，「有沒有把 instance 的體積加進半徑」才會分岔。
把那一項拿掉之後測試確實會紅。

#### ✅ 第四步：遠景合併也接到區塊表上

分組原本掛在空間格的 cellRanges 上，所以串流走區塊表之後就沒有遠景合併了。
接上去的關鍵是**不要沿用「重建時整份重算」** —— 那 22 ms 會原封不動留著。

區塊的變動形狀是已知的：載入接在後面，卸載把洞後面的往前挪。所以分組也照著
做：前者只替新那一段建組，後者刪掉那幾組、把後面的編號整體平移。都是整數
工作，與世界大小無關。

| | 之前 | 之後 |
| --- | ---: | ---: |
| 34,000 個常駐：繪製次數 | 7,965 | **3,684** |
| 34,000 個常駐：走訪 | 0.35 ms | **0.19 ms** |
| 34,000 個常駐：GPU | 2.21 ms | **1.75 ms** |
| 490,000 個常駐：走訪 | 5.6 ms | **3.0 ms** |
| 490,000 個常駐：幀 p50 | 10.70 ms | **9.80 ms** |
| 490,000 個常駐：GPU | 10.97 ms | **9.05 ms** |

490,000 個時只合併了 14,567 個（槽位 1,365 / 可合併 7,520）—— **卡在記憶體
預算**，而它會說出來。那是開發者的旋鈕，不是引擎該自己決定的。

接上去的過程踩到一個：烘焙那一段還在讀空間格的順序表，而區塊路徑用的是
恆等表。症狀是「分組建好了、槽位配好了、合併次數 0」—— 每一步看起來都對。

#### ✅ 第五步：搬過去的東西不必重算包圍球

卸載一格是「把洞後面的全部往前挪」，而原本那一段被整段標成髒 —— 平均是
半個世界。實際上那些 instance 的**內容完全沒變**，只是換了編號，所以快取
依編號排的時候一次 `copyWithin` 就對了（矩陣本來就是這樣搬的）。

| 490,000 個常駐 | 之前 | 之後 |
| --- | ---: | ---: |
| HLOD 分組（含包圍球） | 3.8 ms | **0.42 ms** |
| `onBeforeRender` 全部 | 6.8 ms | **3.4 ms** |

34,000 個常駐時分組 0.31 → **0.04 ms**。

#### 這個配置的幀時間不可信，CPU 才可信

490,000 那一組每次執行的常駐數在 470,000–510,000 之間跳，繪製次數 79k–94k
—— **工作量本身就差 15%**，所以幀時間的差異讀不出程式碼的差異。這一組要看
的是 `stats` 裡的 CPU 分項，那是同一份工作量下的直接量測。

（34,000 那一組穩定得多，而且它一直在顯示器的下限上，所以那一組看 GPU。）

#### 量過否決：不回收「這一幀沒畫到」的槽位

池子裝不下工作集時槽位會互相踢，而每一次重烘都要重傳整個批次緩衝。看起來
只填空槽位就好 —— 實測否決：合併次數從 248 掉到 **14**，幀時間沒有變好。
槽位會被暖機期早到的那批佔住，而它們早就不在視野裡了。

真正的限制還是記憶體預算（1,365 槽位對 7,238 組）。那是開發者的旋鈕。

#### ✅ 第六步：熱迴圈裡兩件不必做的事

還是同一個問題：**已經知道的事不要再算一次**。

1. **整段都在視錐內側時，不必逐一測那六個平面。** 區塊測試一趟同時答得出
   「碰得到嗎」與「整顆都在內側嗎」（前者比 `-radius`，後者比 `+radius`），
   而後者成立時裡面每一個都必然可見。這條只會少做事、不會少畫東西 ——
   判斷錯的方向是多測一次，不是漏掉。
2. **選階不必開根號也不必除法。** 判斷式移項到距離那一側再兩邊平方：
   每階的係數與 instance 無關，每幀算一次，迴圈裡只剩一次乘法與一次比較。

| | 之前 | 之後 |
| --- | ---: | ---: |
| 走訪（490,000 個常駐） | 3.0 ms | **2.38 ms** |
| 走訪（34,000 個常駐） | 0.198 ms | **0.16 ms** |

選出來的階完全相同 —— `ab-ww-real` 的 LOD 分佈兩邊都是 `0/0/4/46/93/227/980`。
那是這個改動唯一該驗的東西：它是恆等變換，不是取捨。

（踩到一次：先取本地參照再長大陣列，於是本地那份還指著長度 0 的舊陣列，
讀出來是 NaN，比較永遠不成立 —— **所有東西固定用第 0 階**，畫面完全正常
只是慢。單元測試抓到了。）

### ✅ 畫面級的檢查：`pnpm visual-check`（2026-08-18）

這一輪抓到的四個 bug 全都是「數字正常、畫面不對」，而 `__ww.verifyQuality()`
早就存在 —— **只是從來沒有任何東西在跑它**。跟 heap 那個數字一樣：印出來、
沒有擋（準則第八條）。

現在有 `tools/visual-check`：建 example app、開真的瀏覽器、**兩個模式各掃
八個相機角度**，取最差的那一個。參考影像是一個真的 `THREE.InstancedMesh`
畫的 —— 同一批矩陣、最細的幾何、不剔除、不選階、不合併。

兩個模式都要驗，因為靜態與串流是**兩份不同的程式碼**，而這一輪四個 bug
全部只在串流那條路上出現。

順手修掉的三件：

| | |
| --- | --- |
| `verifyQuality` 只認得建構時的容量 | 串流時活著的是 `rocks.count`，所以它比的一直是錯的數量 |
| 兩張圖之間串流還在載入卸載 | 差的就不是畫質而是內容。現在先 `stopStream` 凍住 |
| 縮放畫布會改變哪幾格夠遠 | 於是第一幀正好落在重新烘焙的中間。擷取前先跑 60 幀 |

#### 查清楚了：數字會晃 2.5 倍是因為槽位池吃不飽

同一頁、同一個角度連續量五次：**959 / 959 / 2967 / 2129 / 959**。所以不是
載入時的狀態差異，是擷取當下的差異。

原因是遠景合併的槽位遠少於可合併的格數（預設預算下是 **60 對 443**），
於是每一幀被合併的是不同的那幾格。合併與不合併**都在品質契約內**，所以
那不是畫質問題 —— 但畫面因此每一幀都不一樣，檢查就讀不出程式碼的差異。

給滿槽位之後同一個角度連續五次是 958 / 958 / 958 / 958 / 1058。

第二個原因是**烘焙沒烘完就擷取**：縮放畫布會改變哪幾格夠遠，而原本只跑
固定 60 幀。改成跑到「這一幀沒有在烘」為止 —— 判準不能用「合併數量有沒有
變」，烘看不見的那幾組時它是不動的，會提早判定穩定。

順帶量到的產品面事實：**程序化那份內容在預設預算下是一直在互相踢的**，
而換槽位內容要重傳整個批次緩衝。它的最粗階是 80 個三角形而且非索引
（cook 過的真實資產是 4 個），所以特別容易撞到 —— 正是準則說「合成內容
不具代表性」的那件事。

#### 讓它長出牙齒：內容得換成「螢幕上很大」的

修完變異之後拿兩個故意做壞的版本試，**兩個都通過**。原因是內容不對：
example 預設是兩萬個又遠又小的物件，螢幕上每個只有幾個像素，本來就全部
在最粗階 —— 選階算錯根本不動畫面。

所以把 `spread`、`size`、`orbit` 開成參數，加了**近景那兩組**（600 個、
放大 20 倍、相機拉近），那時換一階會動到成千上萬個像素：

| 故意弄壞的地方 | 舊的兩組 | 加上近景之後 |
| --- | --- | --- |
| 選階固定挑最粗的一階 | ❌ 沒反應 | ✅ 多畫 1.675% / 2.174%，兩組都紅 |
| 區塊包圍球半徑縮成 0.7 倍 | ❌ | ❌ 少畫只從 0.29% 動到 0.51% |

第二個仍然抓不到，而且原因是結構性的：整塊在畫面邊緣被剔掉只佔幾百個
像素。那一類由單元測試掃 48 個角度、拿獨立實作比可見集合來擋（那一組
確實抓得到）。**兩邊互補，缺一個都會漏。**

另外兩件也是這一輪學到的：

1. **兩個方向都要比。** 「強化版有、原生版沒有」抓多畫；「原生版有、
   強化版沒有」抓**東西不見了** —— 後者才是這個引擎最危險的錯，而且只
   在那個方向上出現。挑最差角度時看的也是它。
2. **門檻要逐個模式訂。** 統一一條線的話，最鬆的那組會把所有組拉鬆：
   靜態那組乾淨狀態就有 1.58%，近景那組是 0.18% —— 用同一條線等於把
   唯一驗得動畫質的那一組鬆了九倍。

#### 剩下那一半：第一次到某個角度時量到的值偏高

逐角度量兩輪才看得出形狀 —— **大部分角度穩到小數第三位，而每一輪會有
一兩個角度爆高，爆的是哪一個每次不同**：

```text
第 1 輪:  0.172  0.174  0.811  1.545  0.193  0.184  0.177  0.171
第 2 輪:  0.172  0.174  0.166  0.161  0.202  0.255  0.177  0.171
```

不是隨機雜訊，是**第一次到那個角度**與**再訪**的差別。所以檢查改成同一個
角度量兩次取第二次。之後近景那兩組三次執行**一字不差**（0.178 / 0.286），
串流那組落在 0.195–0.338。

排除掉的：繪圖緩衝被清掉（開 `preserveDrawingBuffer` 沒有改善）、載入時的
狀態差異（換一頁重來形狀一樣）、烘焙沒烘完（擷取前已經跑到不再烘為止）。

#### 查下去：不是槽位裝錯，是合併的涵蓋範圍還在漂

第一輪證據看起來像引擎的缺陷：**引擎的決定幾乎一模一樣，只有像素差 4.5 倍**。

| t=4.8 | 第一次 | 第二次 |
| --- | ---: | ---: |
| 少畫 | **0.848%** | **0.189%** |
| 合併次數／涵蓋 | 244／11,028 | 243／10,902 |
| 可見／走訪 | 430／11,291 | 425／11,242 |
| LOD 分佈 | 0/0/186 | 0/0/182 |

那個形態正好是先前記下來的「槽位裝的內容對不上它宣稱的那一組」。

**但再查一層就排除掉了。** 從 `drawnInstances` 直接檢查：合併的那幾筆用的
是槽位的 instance id，同一個 id 出現兩次就代表兩組宣稱同一個槽位 ——
**重複是 0**，逐一送的那些也沒有任何一個被畫兩次。所以槽位對應是好的。

真正在動的是**合併涵蓋多少**，而且在「已經跑到不再烘」之後還在動：

```text
t=8   第一次: 合併 249／11,370   逐一 123
      第二次: 合併 248／11,356   逐一  78
```

合併次數只差一，逐一送的卻少了 45 筆。所以還沒穩的是「哪些格子算夠遠」，
不是槽位的內容。

**定位再修正一次**：不是引擎畫錯，是這個狀態比我以為的更慢才收斂，而
「這一幀有沒有在烘」不足以判斷它收斂了。

#### 查到了：量測期間動畫迴圈沒有停

`capture()` 中間有 `await`（等 PNG 解碼），而動畫迴圈會在那段空檔裡繼續跑
—— 它把相機移走、重新烘遠景、改變可見格。**「同一個 t 量兩次」實際上量的
是兩個不同的狀態。**

證據：連續呼叫 `verifyQuality(8.0)` 三次，相機矩陣是 0.235566 / 0.275634 /
0.310396。停掉迴圈之後，八個角度兩輪一字不差：

```text
停之前  0.172  0.174  0.811  1.545  0.193  0.184  0.177  0.171
停之後  0.172  0.174  0.166  0.162  0.193  0.184  0.177  0.171
```

也因此前面那條「可見格數會漂」的線索是**假的**：`stats` 是在 promise
resolve 之後讀的，那時動畫迴圈已經又畫了好幾幀，所以它反映的根本不是被
擷取的那一幀。**用錯時機讀到的狀態，會長得像一條很有說服力的線索。**

修掉之後門檻從「整片壞掉」的等級（3%／梯度比 1.5）收到量到值的兩倍以內
（0.3%–0.6%），而選階那個破壞照樣紅（1.675% / 2.174%）—— 收緊沒有犧牲
鑑別力。

#### 這條線索鏈值得留著

判斷改了四次：儀器雜訊 → 疑似引擎缺陷 → 排除槽位裝錯 → 疑似空間格漂 →
其實是量測時機。**每一次都有當時看起來充分的證據**，而每一次都是再挖一層
才推翻的。停在任何一層收工，接下來都會去修一個不存在的東西。

#### 還沒做的

**槽位指到別人身上的那種錯，測試看不到。** 卸載之後分組編號會整體平移，
槽位的反向連結要跟著修。修錯的症狀是「遠景畫成別的地方的東西」，而數量、
繪製次數、幀時間全都正常 —— `stats` 看不出來。目前只有「還在不在」與
「有沒有畫兩次」擋得住，那一段靠程式碼本身撐著。要真的驗它得比對畫面。

**走訪本身還是純量、單執行緒。** 490,000 個常駐時走訪 2.38 ms、分組 0.41 ms。
剩下的每個 instance 約 18 ns，而純粹讀過一遍的下界是 4 ns。這一格是四格模型裡的「CPU × 機制層」，
下一步是 SIMD 或 Worker。

### 四格模型

| | 演算法層 | 機制層 |
| --- | --- | --- |
| **CPU** | ✅ 剔除、LOD、分割、串流 | 🟡 **離下界 4.5 倍**（每個 instance 18 ns，純讀一遍是 4 ns）。已做：串流的分割改用現成的區塊表、包圍球增量更新與跟著搬、計數排序、熱迴圈去掉開根號與除法。剩下：Worker、SIMD |
| **GPU** | ✅ **HLOD**（繪製 15×、p95 2.5×、畫質不變）。遮擋剔除**量過否決**：幾何側只佔 7.5%，fragment 側 early-Z 已經處理掉了。impostor 待評估 | ✅ **已結案**：繪製合併卡在 Three 的 backend，但 HLOD 之後繪製只剩 15% GPU 時間，自己畫再省 0.30 ms —— 不值得付相容性 |

遮擋剔除與 GPU 驅動繪製先前被「GPU 沒問題」否決過。那個結論是用非索引、
無貼圖的程序化內容量出來的，而那種內容在兩個方向上都不具代表性 ——
**兩者都要重新評估**。

下一步的順序由內容決定，而不是由「現在哪個數字比較大」決定：

| | 誰是瓶頸 | 該做什麼 |
| --- | --- | --- |
| 輕幾何、多物件 | 繪製呼叫（索引內容約 48%） | 繪製合併 |
| 重幾何 | 三角形（只到天花板的 58%，差額是材質） | HLOD、impostor、遮擋剔除 |

兩條都要走完才算「GPU 到極限」。

## ✅ W5 — 網站跑得動

把這個套件用在網站上，而不只是 demo。幀率**量不到**這四件事，而它們才是
網站上會被感覺到的東西。

| | 條件 | |
| --- | --- | --- |
| 1 | 首次可見時間 | ✅ 429 ms（擋 3,000 ms） |
| 2 | 下載總量 | ✅ 606.9 kB（擋 800 kB） |
| 3 | 分頁記憶體 | ✅ JS heap 43.6 MB（擋 150 MB；遠景合併的槽位池佔大部分） |
| 4 | 與頁面其他內容共存 | ✅ 外層 rAF 149 幀／3 秒 |
| 5 | **看不見的時候完全停下來** | ✅ 捲出畫面後 1 幀／1.5 秒 |
| 6 | 畫面在品質契約內 | ✅ `pnpm visual-check`，靜態與串流兩條路各掃八個角度 |

**六條全部有東西擋。** 這一輪之前有兩條只是印出來 —— 而 heap 就是那樣從
13.7 MB 漲到 1,005 MB 沒人發現的（準則第八條）。

`pnpm site-check`（`tools/site-check`）量的是 **example app**，不是 benchmark
app —— 網站的指標必須用網站的形狀量。benchmark 為了量測本身載入了 overlay、
harness 與十幾個場景，那些數字對使用者沒有意義。

### 60,000 個 instance 的網站（2026-08-17）

```text
首次可見        468 ms
下載總量        601.4 kB（2 個檔案）
JS heap         13.7 MB
GPU 物件        3 個幾何、3 張貼圖
```

首次可見量的是「把第一幀交給 GPU 的時刻」，不是「像素真的出現在螢幕上」——
後者從頁面裡量不到，硬報一個數字比誠實地少報一段更糟。

### 與頁面共存

3D 在真實網站上通常只是頁面的**一塊**，而 demo 永遠是整頁一個 canvas 加
自己的 rAF 迴圈 —— 那種寫法在真實頁面上會跟頁面本身的動畫打架，而 demo
看不出來。

所以檢查把 example app 放進一個 400×300 的 iframe，外層頁面跑自己的 rAF：

```text
外層頁面的 rAF  168 幀（3 秒內）   ← 沒有被佔住
iframe 首次可見 178 ms
iframe 可見物件 27,385
畫布 400 px / 視窗 400 px          ← 沒有假設獨佔整個視窗
```

三條斷言都是「壞掉時 demo 完全正常」的那一種：外層停住代表主執行緒被吃光，
畫布比視窗寬代表假設了全螢幕，可見物件為 0 代表在非全螢幕的容器裡剔除算錯。

### 看不見的時候完全停下來

網站上的 3D 大多數時間不在視野裡（在頁面下方、在別的分頁）。套件若自己排了
`setInterval` 或 `requestIdleCallback` 去串流、去烘遠景，那些工作會在使用者
根本沒在看的時候吃他的電池 —— 而 demo 永遠看不出來，因為 demo 就是整頁一個
canvas，永遠在視野裡。

驗的是**行為不是實作**：把 iframe 設成 `display:none`（瀏覽器停掉它的 rAF），
然後看引擎的幀數有沒有繼續往前。抓 `setInterval` 的字串擋不住第三種寫法。

實測整個套件只有兩個計時器，而且都不是迴圈：worker 的三秒握手逾時，以及
裝置遺失後的重試延遲。所以「頁面不畫，引擎就完全不動」是**構造上成立**的，
而現在有一條線在守著它。

### 這一節不涵蓋什麼

寫下來免得被當成空白支票：沒有驗過真的手機、沒有驗過慢速網路下的載入行為、
沒有驗過 WebGL2 退路（site-check 用的是瀏覽器給什麼就用什麼）。那三件都是
真的網站條件，只是還沒有儀器。

**同一頁兩個引擎實例已經驗了**（單元測試）：兩個 mesh 各自用自己的相機、
統計不互相污染；兩個 scene 各自串流、載入自己的內容，停掉一個不影響另一個。

會擔心是因為套件裡確實有模組層級的共用狀態（LOD worker 是單例、manifest
有快取）—— 那是刻意的，一個 worker 服務所有 mesh 才對。但共用狀態只要有
一份是「以為只有一個使用者」寫的，症狀就是**其中一塊套用了另一塊的相機**，
而 demo 永遠看不出來，因為 demo 只有一塊。

### 首次可見的一個發現

計時原本只加在手動推幀那條路上，而動畫迴圈另外寫了一份 render 呼叫 ——
於是永遠量不到。兩條路各寫一份是這個 app 裡最容易寫歪的地方，現在都走
同一個 `renderFrame()`。

## 範圍宣告：桌機瀏覽器

`load-material.ts` 一直指向「roadmap 的範圍宣告」，而那段從來沒有寫下來。
決定是真的做過的，只是留在腦子裡 —— 這一段補上。

### 在範圍內

桌機瀏覽器（Chrome / Edge / Firefox / Safari），WebGPU 或 WebGL2。

### 不在範圍內，而且是**明確排除**不是「還沒做到」

| | 為什麼 |
| --- | --- |
| 行動裝置的壓縮貼圖 | cooker 只產 BC 系列。手機要的是 ETC2/ASTC，那是另一條編碼管線，不是調個參數 |

**排除的是「cook 過的貼圖」這一條路，不是整個套件。** LOD、剔除、串流、
遠景合併全部與貼圖格式無關 —— 手機上自己 load 一張 PNG 給 material，
其餘功能照常。

### 宣告不等於可以靜靜壞掉

原本踩到這條線的症狀是：把壓縮資料交給不支援的 GPU，貼圖變黑或不見，
材質看起來像沒接上，而錯誤（如果有）在 renderer 深處。

現在 `loadTexture` 會先問這台裝置支不支援，不支援就**丟出例外並說清楚**
缺什麼、少了它會怎樣、可以怎麼繞。準則第 155 行講的就是這件事：
「缺前置時必須大聲說出缺什麼、少了它會怎樣」。

判準用的是 WebGL2 的三個擴充（s3tc / rgtc / bptc）。那是**代理指標**：
問得到、同步、不需要拿到使用者的 renderer，而會缺的裝置兩邊都會缺。
所以訊息講的是「這台裝置**看起來**不支援」。

### 什麼時候該重新看這條線

要支援行動裝置的話，缺的不是一個開關，是 cooker 多一條 ETC2/ASTC 的編碼
路徑加上 manifest 帶多組格式、runtime 依裝置挑一組。那是一個里程碑的量，
不是一個修補。

## W6+ — 候選

順序取決於 W4、W5 量到什麼：

- **地形與植被** —— 完全不同的幾何密度，現有量測涵蓋不到
- **成本可控的材質系統** —— 目前直接用 `MeshStandardMaterial`，shader 成本不受控
- **骨骼動畫** —— cooker 目前丟棄，而靜態變換的優化建立在「東西不會動」上
- **叢集 LOD（Nanite 式）**、**虛擬貼圖**、**編輯器**

每一項動手前先問 [doctrine.md](doctrine.md) 的三個問題：屬於四格的哪一格、
量測內容具不具代表性、是消滅浪費還是降低品質。
