# ADR 0005：物理要接，但這個套件負責的是**調度不是求解**

狀態：已採納

## 決策

這個套件**不寫物理求解器**。它寫的是把既有的求解器接到大世界上的那一層：
哪些剛體該算、串流的內容怎麼跟著載入卸載、遠處要不要簡化、原點重定位時
物理世界怎麼跟著搬。

求解器建議用 [Rapier](https://rapier.rs)（Rust／WASM）。

**而套件對它連 peer dependency 都不是 —— 一行都沒有 import。**

這一句原本寫成「peer dependency」，回頭核對才發現實際上更乾淨：
`PhysicsScheduler` 進出的只有 **id**（`onActivate(id)` / `onDeactivate(id)`），
剛體長什麼樣、由誰算，它完全不知道。

所以它對任何求解器都成立 —— Rapier、cannon-es、自己寫的、甚至不是物理
（「這些 id 現在該載入音效」也是同一個形狀）。**不用物理的人一個位元組
都不必下載**，而且用別的求解器的人也不必繞過我們。

寫錯的那個方向值得記：「peer dependency」聽起來已經夠鬆了，所以沒有人去
問「有沒有可能連那個都不需要」。

## 理由

### 一、這與這個專案已經證明有效的做法是同一個形狀

| 領域 | 用誰的 | 為什麼不自己寫 |
| --- | --- | --- |
| 網格簡化 | meshoptimizer | 自己寫的誤差與別人不一致，症狀是細微的錯誤且不報錯 |
| 切線 | MikkTSpace | 烘焙工具用的是它，換一組基底等於每張法線貼圖都偏一點 |
| 世界尺度陰影 | Three 的 CSM addon | 同上 |
| **物理** | **Rapier** | **同上，而且嚴重得多** |

剛體求解器要正確、穩定、而且**決定性**（同樣的輸入每次跑出同樣的結果，
不然多人連線與重播全部不成立）。那是好幾年的工程，而 Rapier 已經做到了。

UE 自己也不是一開始就寫求解器 —— 它 license PhysX 用了十幾年，Chaos 是
後來才自研的。

### 二、UE 的物理價值不在求解器，在整合

把「UE 的物理很好用」拆開，好用的部分幾乎都不是解算：

| 問題 | 與這個套件已經做過的什麼同形 |
| --- | --- |
| 哪些剛體現在該算，哪些該睡 | 逐 instance 剔除 |
| 串流進來的格子，碰撞體怎麼跟著載入卸載 | `WorldStream` |
| 遠處用簡化碰撞體或根本不要 | LOD 選階 |
| 幾千個相同物件的碰撞體 | 批次 |
| 走遠了物理座標也會塌 | 原點重定位（**同一個洞**） |
| 物理該不該進 worker | LOD 產生已經在 worker 裡 |

**每一項都是「量得出上限」的**，而寫求解器不是。

### 三、水：「完全真實」做不到，UE 也沒有

UE 的 Water 是波函數（Gerstner）加著色，不是流體模擬。真正的流體（FLIP／SPH）
只在小範圍局部用。**海洋看起來真實是渲染的功勞，不是物理的。**

所以「水要跟真的一樣」必須拆成兩件事：

| | 屬於 | 這裡做不做 |
| --- | --- | --- |
| 看起來真 | 渲染（著色、反射、折射） | ⛔ 那是全域光照那一類，見 ADR-0001 |
| 互動起來對 | 浮力、船體、濺起 | ✅ 波函數 + 剛體做得到 |

混在一起講會做出一個很貴又不對的東西。

## 後果

### 好的

- 求解器的正確性不是我們的風險。
- 不用物理的人不付任何代價（peer dependency）。
- 「物理在大世界裡怎麼調度」變成一條**量得出上限**的軸，與其他五條同一個判準。

### 要付的

- 多一個 peer dependency，而使用者要自己裝。
- 我們的碰撞體形狀受限於 Rapier 支援的那些。
- 換求解器的話這一層要重寫 —— 所以介面要盡量薄。

### 明確不做

- 自己寫剛體求解器、布料、破壞。
- 流體模擬。
- 把物理狀態寫回 `InstancedMesh` 以外的東西（那是使用者的迴圈）。

## 這條線在哪裡

> **求解是別人的，調度是我們的。**

判斷方法：這件事需要知道「世界有多大、相機在哪、什麼東西被串流進來」嗎？
需要 → 是我們的。只需要知道剛體與接觸點 → 是求解器的。
