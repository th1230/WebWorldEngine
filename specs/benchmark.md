# Benchmark 場景與量測協定

實作：`apps/benchmark`、`tools/benchmark-runner`

## 場景

多數場景使用**程式產生的合成資料**，量到的是硬體與 backend 的上限，不是真實場景效能。

`ab-*-real` 是例外，而且是必要的例外。合成內容在兩個方向上都不具代表性，
而且錯的方向相反：

- `IcosahedronGeometry` 是**非索引**的 → 幾何看起來貴 **3.35 倍**
- 沒有貼圖 → 材質看起來免費（真實 PBR 是 **1.72 倍**）

只有合成資料的話，「CPU 與 GPU 誰是瓶頸」是拿錯的內容決定的，而那個答案會
傳染給後面每一個決策。

| 場景 | 量測目標 |
| --- | --- |
| `baseline-empty` | present 與瀏覽器合成的成本地板 |
| `instancing` | `InstancedMesh` 吞吐與 culling 成本（renderer 層） |
| `batching` | `BatchedMesh` multi-draw 吞吐（異幾何、同材質） |
| `material-complexity` | fragment shader 成本與 overdraw（`iterations` × `layers`） |
| `texture-load` | VRAM 佔用與上傳頻寬 |
| `compute-indirect` | compute 寫 draw 參數 → indirect draw 的可行性 |
| `shader-compile` | 首幀編譯 stutter，跑 `precompile=0` 與 `=1` 兩次 |
| `device-loss-soak` | device 遺失恢復的正確性與資源洩漏 |
| `ab-native-instanced` | **A/B 對照組**：原生 `THREE.InstancedMesh` |
| `ab-ww-instanced` | **A/B 實驗組**：`WW.InstancedMesh`（W1） |
| `ab-native-real` | 同一個對照組，換成 cook 過的真實資產 |
| `ab-ww-real` | 同一個實驗組，換成 cook 過的真實資產 |
| `ceiling-cpu` | **天花板**：剔除＋選階的吞吐，以及同一批資料的純讀取下界 |
| `ceiling-gpu-triangles` | **天花板**：每毫秒能吃多少三角形 |
| `ceiling-gpu-drawcalls` | **天花板**：每毫秒能送出多少次繪製 |

### `ceiling-*` 的幀時間沒有意義

這三個場景**刻意什麼都不平衡**：每一個都把一端壓到零去量另一端。
要看的是 verdict 與「數量 ÷ gpuRenderMs」，不是幀率。

`ceiling-cpu` 特別報**兩個**數字。「剔除＋選階每毫秒幾個」量的是我們自己
的實作，拿它當天花板是循環論證 —— 永遠 100%。所以另外量了「把同一批矩陣
讀過一遍要多久」當下界，兩者的比值才是機制層還剩的空間。

### `ab-*` 這一對是為了 A/B 而存在的，規則跟其他場景不同

兩者**除了那一個類別以外完全相同**：同一個種子的矩陣、同一條相機路徑、
同一份材質與燈光、同一份 LOD 第 0 階幾何。差異若不只一項，量到的差就不知道
是誰造成的。

它們在 `DEFAULT_RUNS` 裡**必須相鄰**。runner 的迴圈是
`for 每一輪 { for 每個場景 }`，相鄰就代表同一輪裡背靠背執行、輪與輪之間交替
—— 那是這台雙峰機器上唯一有效的 A/B 形式（見「重複要交錯，不能連續」）。

`--scene` 接受逗號分隔，所以 `--scene ab-native-instanced,ab-ww-instanced`
可以只跑這一對而仍然保持交錯。

**LOD 誤差從幾何本身量，不用公式推。** `sphericalLodErrors()` 逐面算矢高。
公式推導看起來便宜，但推錯一個係數就會低估誤差二成以上，而低估的方向是
**選到太粗的階** —— 靜靜地違反品質契約，沒有任何東西會報錯。

### 真實資產的那一對

`ab-*-real` 與程序化那一對是**同一個實驗**：一樣的數量、種子、相機路徑與
燈光，一樣的兩兩相鄰交錯。變的只有內容。

| | 程序化 | 真實 |
| --- | --- | --- |
| 幾何 | `IcosahedronGeometry(1, 4)`，500 個三角形 | Avocado，682 個 |
| LOD | 3 階，誤差由矢高算出 | cook 好的 7 階，誤差 cook 時量的 |
| 材質 | `MeshStandardMaterial`，**沒有貼圖** | albedo + normal + ORM，各 1024² BC |

三角形數刻意挑成接近的（500 vs 682），差異才集中在**材質**上。幾何量本身
的影響用 `--param mesh=…` 換一個更重的資產單獨看。

每個資產都先依 LOD0 的包圍球半徑正規化成半徑 1。不正規化的話，換資產等於
同時換了「螢幕上多大」，而那會直接改變選階與填充率 —— 兩個都是要量的東西。

**需要先跑 `pnpm cook:real`。** 二進位美術檔不進版控，所以這一對在 CI 上
不執行（`profiles: ['hardware']`）。資產不在時場景會**明確失敗**，不會靜靜
退回程序化內容 —— 那正是它要防的事。


## 可重現性規則

### 相機路徑以幀索引驅動，不以時間驅動

這是可比較性的關鍵。若相機跟著 wall-clock 走，快的機器在 600 幀內繞完兩圈、慢的機器只繞半圈 —— 兩者看到的內容根本不同，數字自然不能相比。用幀索引，每次執行的第 N 幀永遠是同一個視角。

代價是路徑的速度感隨 FPS 改變。benchmark 不需要好看，需要可重現。

### 所有程序化內容用固定 seed

`createRng(DEFAULT_SEED)`（mulberry32）。用 `Math.random()` 會讓每次執行的幾何分布不同。

### 暖機幀一律丟棄

先跑暖機再 `profiler.reset()`，把 shader 編譯、首次資源上傳與瀏覽器暖身排除在外。

例外：`shader-compile` 場景設 `overrideWarmupFrames: 0`，因為它要量的**正是**那段成本。harness 也會因此跳過對它的 `precompile()`。

## 執行 profile

兩種 profile，結果**絕不可混用**，寫在不同目錄：

| profile | 環境 | 用途 |
| --- | --- | --- |
| `hardware` | 有頭 Chrome + 真實 GPU | 唯一能當效能基準的來源 |
| `smoke` | 無頭 + SwiftShader | 只驗證「跑不跑得起來、有沒有正確降級」 |

`smoke` 使用大幅縮小的工作量（例如 instancing 從 200,000 降到 2,000）。煙霧測試問的是「會不會壞」，不是「多快」；用硬體規模的工作量去跑軟體 adapter 只會逾時，那不是有意義的失敗訊號。

`writeBaseline()` 會拒絕寫入 `performanceMeaningful: false` 的結果。

瀏覽器優先使用系統安裝的 Chrome，其次才用 Playwright 自帶的 Chromium：系統 Chrome 用的是使用者真正的驅動與 GPU 設定。實際用了哪一個由報告的 `userAgent` 記錄。

## 基準依機器分檔

`benchmarks/baselines/<machineId>.json`，`machineId = hash(backend + adapter + userAgent)`。

WebGPU 的效能、記憶體上限與 feature 暴露程度都由硬體、瀏覽器與驅動共同決定，**跨機器數字沒有可比性**。`compareReports()` 偵測到 machineId 不同會直接拒絕比對並發出警告，而不是產生假警報。

`benchmarks/results/` 不進版控；`benchmarks/baselines/` 要進。

## 停用 GPU shader 快取

`hardware` 與 `smoke` 兩個 profile 都帶 `--disable-gpu-shader-disk-cache --disable-gpu-program-cache`。

這是為了**可重現性**，不是為了模擬最差情況。驅動會把編譯好的 shader 存到磁碟並跨瀏覽器行程重用，於是「第一次編譯」在一台機器上一輩子只發生一次：

```text
shader-compile-cold 開頭 30 幀
  第一次執行（全新機器狀態）  17,314 ms
  之後每一次                  1,684 ms   ← 差十倍，來自殘留狀態而非程式碼
```

停用之後**同一次執行內**的三次重複收斂到 1,624 / 1,610 / 1,615 ms（±0.9%）。

> **但這個結論當初下得太早。** 那三次重複共用同一個瀏覽器行程，本來就會一致；用它來宣稱「已可重現」是錯的推論。後來累積 5 次**獨立執行**才看到真相：2369 → 2283 → 2149 → 1669 → 1634ms，一路單調下降 24%。代表這兩個 flag **並未完全阻止跨行程的快取殘留**。
>
> 場景改為由輕到重之後這項漂移消失了，所以主因也可能是散熱而非快取。成因尚未定論；能確定的是「同執行內一致」不等於「跨執行可重現」。

代價是所有場景的開頭數幀都比真實使用者（第二次開啟）略慢。這個代價值得付：隱藏的狀態依賴會讓基準悄悄失效，比數字偏保守嚴重得多。

## 場景自我檢查（verdict）

有些場景驗證的是**正確性**而非效能。`device-loss-soak` 要確認的是每次遺失都真的恢復了 —— 只回報數字而不下判斷，等於要人每次用眼睛看報告，那種檢查遲早會被略過。

場景可提供 `verdict()`，回傳 `{ ok, detail }`。runner 在 `ok === false` 時把該場景記為**失敗**（等同於場景跑不完），因為功能壞掉比效能退步嚴重。

目前有兩個場景會下判斷：

| 場景 | 檢查什麼 |
| --- | --- |
| `device-loss-soak` | 結束時狀態必須是 `running`，恢復次數不得少於觸發次數 |
| `compute-indirect` | 在有 compute 的 backend 上，indirect 路徑必須成功建立且執行期沒有失效 |

`compute-indirect` 這一項尤其重要：它是 GPU-driven 幾何路徑的可行性探針。如果 TSL 或 indirect draw 的 API 變動讓這條路壞掉，場景原本只會安靜地降級成一般繪製、留下一行 note，整輪 benchmark 照樣通過 —— 等到真的要用時才發現。有了 verdict，它會立刻是紅的。

涵蓋不到不等於失敗：沒有 compute 的 backend（WebGL2）回報 `ok: true` 並註明「未驗證」。

## 回歸判定

比對「越大越糟」的六項：`frameMs.p95`、`cpuFrameMs.p95`、`gpuRenderMs.p50`、`gpuRenderMs.p95`、`peakMemoryMB`、`earlyFramesTotalMs`。

GPU 同時看 p50 與 p95 是刻意的：**p50 抓「整體變慢」，p95 抓「出現卡頓」**，兩者失效的方式不同。只看 p95 會被雙峰分布騙（見下），只看 p50 會漏掉卡頓 —— 而卡頓正是玩家最有感的東西。

`earlyFramesTotalMs` 是為了擋下只發生在啟動期的退步；它的噪音下限設為 20ms。

### 每個指標各有噪音下限

兩邊都低於下限就視為相同。這是必要的，不是保險：Chrome 把 `performance.now()` 量化到 **0.1ms**，低於下限的數字其百分比變化幾乎全是量化誤差。

| 指標 | 下限 | 理由 |
| --- | ---: | --- |
| `frameMs.p95`、`gpuRenderMs.p50`、`peakMemoryMB` | 1.0 | 量化誤差 |
| `cpuFrameMs.p95` | **3.0** | `performance.now()` 量化到 0.1ms |
| `gpuRenderMs.p95` | **3.5** | 小場景上是雙峰的，見下 |
| `earlyFramesTotalMs` | 20 | 啟動視窗本身變異大 |

實際遇過的兩次假警報：

- `gpuRenderMs` 的 `0.425ms → 0.822ms` 被算成「退步 93%」——兩個都約等於零的數字
- `shader-compile` 的 `cpuFrameMs` 在 1.1–2.0ms 之間跳被算成 **32.9%** 偏離——一個 1.5ms 的值光是 0.1ms 量化就有 ±6.7% 誤差，所以 CPU 的下限必須比其他項高

### 報告 schema 版本

`REPORT_SCHEMA_VERSION` 在報告新增或改變欄位時必須遞增。`compareReports()` 遇到版本不符會拒絕比對並要求重新產生基準 —— 舊基準缺少新欄位，硬比會炸開，或更糟：比出看似合理的錯誤結論。

### 每個場景重複 3 次取中位數

單次執行不足以判定回歸。實測：**完全相同的程式碼**連跑兩次，`batching` 的 frame p95 在 11.4ms 與 14.8ms 之間跳動（約 30%）。內顯時脈隨散熱與電源狀態變動，而每個場景的散熱起點又取決於前面跑了什麼。

取中位數（而非最佳值 —— 使用者不會永遠處於理想條件）後，同樣的 `batching` 三次分別是 14.50 / 14.80 / 14.91ms。

`run` 與 `baseline` 必須用**相同**的重複次數，否則等於拿一次雜訊很大的量測去比一個穩定的中位數。兩者都預設 3。`--repeat 1` 適合快速迭代，但結果不該拿來判定回歸。

每份報告會把觀察到的 p95 範圍寫進 notes —— 看不見的變異會被當成回歸。

### 量出「這次執行時機器有多快」，不可比較就拒絕比較

交錯執行之後仍然遇到一次假警報，而這次的形態完全不同：

```text
                  baseline   bench
batching            5.100  →  9.605   +88%
ceiling-gpu-tris    5.600  → 10.005   +79%
batching            4.700  →  8.905   +90%
ab-ww-instanced    15.300  → 27.600   +80%

baseline-empty      0.500  →  0.505   ok      ← CPU 輕的場景完全不變
instancing          0.600  →  0.700   ok
material-complexity 0.800  →  0.900   ok
所有 GPU 指標                          ok
```

**四個 CPU 密集場景全部乘上約 1.85 倍，CPU 輕的場景與所有 GPU 指標完全不變。**

隨機爭用不會讓四個場景乘上同一個倍數。那是整台機器的 CPU 時脈在該次執行中降檔了 —— 熱受限筆電在持續負載下的常態，而且降下去不會自己回來。

排除過的其他假設：

- **散熱漸變**：三輪重複各自內部極穩（15.60/15.70/15.70 對 27.20/28.61/28.11），不是漸變
- **殘留的瀏覽器行程**：查了 32 個 chrome 行程，**沒有一個帶 benchmark 的旗標** —— 全是使用者自己的
- **預熱不足**：加了 60 秒預熱之後問題完全沒變

門檻處理不了這種情況：它不是雜訊，是**兩次量測的前提不同**。調鬆會漏掉真的退步，調緊會天天誤報。

所以改成把前提量出來。每次執行在量測前跑一段固定的純 CPU 工作（`cpuReferenceMs`），比對時若兩次相差超過 **15%** 就**拒絕比對**並說明原因。

> 列出一串假退步讓人逐一追查，比明確說「不可比較」糟糕得多。前者會消耗
> 信任，而且第三次之後就沒有人會認真看紅燈了。

### 重複要交錯，不能連續

`輪1(全部場景) → 輪2(全部場景) → 輪3(全部場景)`，而不是「場景 A 連跑三次再換 B」。

這是 median-of-3 能不能發揮作用的**前提**，不是風格問題。實測的失效案例：

```text
batching         15.30  15.61  26.01   ← 干擾從這裡開始
ab-ww-instanced  25.80  26.51  25.91   ← 三次全在干擾期內，中位數也壞了
instancing       31.71  31.71  19.50   ← 干擾結束，第 3 次恢復
```

那次外部干擾持續約兩分鐘。因為同一場景的三次重複是**相鄰**的，全部落在干擾窗內 —— 取中位數完全沒有幫助，結果是 **+76% 的假警報**。

`instancing` 的「恢復」很關鍵：它排除了散熱累積（散熱只會越來越糟），確認是外部干擾。

交錯之後，同一段兩分鐘的干擾最多只能污染每個場景的**一次**取樣，中位數必然存活。總執行次數與頁面載入次數完全不變 —— 這個修正沒有成本。

> 同一個問題出現三次才被系統性解決。前兩次都是「重跑一次就過」，
> 而重跑確實有效，於是沒有人去問「為什麼中位數沒擋住」。
> **有效的權宜之計會掩蓋根因** —— 這比沒有權宜之計更危險。

### 執行順序：由輕到重

場景順序是量出來的，不是隨意排的。

把最重的場景排在第 3 位時，五次獨立執行的分析顯示**四項指標呈現單調漂移**（GPU 時間一路從 7.2 爬到 9.6ms、shader 編譯成本一路從 2369 降到 1634ms），下游場景的隨機散布也從 7.4% 惡化到 13.3%。重負載場景把機器加熱之後才輪到別人跑。

改成由輕到重之後，**漂移項目從 4 項降到 0 項**。這是可驗證的改善，不是猜測。

耗時最長的幾個（`instancing`、A/B 那一對、`material-complexity`）排在最後；`shader-compile` 排在最前，因為它量的是編譯成本，越接近冷啟動越有代表性。

**改動順序會讓既有基準失效**，必須重跑 `pnpm bench:baseline`。

### 第一次執行不可信

同一批五次執行中，**第一次是 2 倍的離群值**：

```text
ab-ww-instanced cpuFrameMs.p95   29.5 │ 14.7  14.8  14.6  14.8
batching       cpuFrameMs.p95    9.0 │  5.1   5.3   5.2   5.1
                               ↑第1次 └── 後四次差異 1.4–3.9% ──┘
```

關鍵在於第一次的**三次重複全都慢**，所以那不是隨機尖峰，而是整段 session 的環境效應（CPU 頻率狀態、與剛結束的其他工作競爭）。

**驗收前不要緊接著跑其他重活。** 若要嚴謹，跑兩次 `pnpm bench` 並採用第二次。

> **第二次觀察。** 在 `bench:baseline` 之後緊接著跑 `pnpm bench`，
> 兩個 GPU-bound 場景同時衝破 40% 門檻：
>
> ```text
> compute-indirect  gpuRenderMs.p95   4.567 → 7.109   +55.7%
> batching          gpuRenderMs.p95   5.790 → 9.286   +60.4%
> ```
>
> **兩個場景都不碰那批資產，而且在執行順序上排在它之前** ——
> 所以當次改動不可能是原因。立刻重跑一次就通過，確認是同一種 session 效應。
>
> 這是它第二次出現，而且這次落在 **GPU 指標**（第一次是 CPU）。
> median-of-3 是在**單次 session 內**取中位數，對整段 session 都偏慢的情況
> 完全無效 —— 要根治得跨 session 取中位數，那是還沒做的事。
>
> 判斷準則：**退步的場景與改動的內容有沒有因果關係**。沒有就先重跑，
> 不要開始「優化」一個根本沒被碰到的場景。

### 有些指標是雙峰的，門檻對它們沒有意義

`compute-indirect` 的 GPU p95 連續兩次誤報之後，回頭看 19 次執行的歷史：

```text
p50   4.48 – 5.03                        （12% 全距，非常穩）
p95   4.56 – 4.65   或   6.88 – 8.12     ← 中間完全沒有值
```

這不是散布，是**兩個母體**：要嘛整段執行沒有卡頓幀（p95 幾乎等於 p50），要嘛出現卡頓幀（p95 高出約 3.2 ms）。

單一門檻套在雙峰指標上，只會隨著落在哪一峰而隨機開關 —— 那正是「訓練大家忽略紅燈」的最快方式。而 `bench:variance` 的模型只分離「系統性漂移」與「隨機散布」，**沒有涵蓋這第三種形態**。

處理方式有兩個，兩個都做了：

1. `gpuRenderMs.p95` 的絕對下限提高到 **3.5 ms**（實測的卡頓幅度），讓小場景的模式切換不觸發。對真正重的場景（material-complexity 47 ms）40% 的相對門檻依然有效。
2. 新增 **`gpuRenderMs.p50`** 當主要閘門。它是這組指標裡最穩的一個，而放寬 p95 之後需要有東西補上覆蓋率。視錐剔除曾讓某個場景的 p50 從 46.13 降到 14.52 —— 那個量級的反向退步會被這一項立刻擋下。

> **診斷順序**：指標紅了先問「退步的場景與這次改動有沒有因果關係」。
> `compute-indirect` 走 `submitRaw`，完全不經過 engine kernel，所以視錐剔除
> 不可能影響它。加上 p50 只動 12% 而 p95 動 70%（真的變慢會讓兩者一起動），
> 判斷就很明確了 —— 不必再跑一次。

### 門檻 40%，由實測雜訊推導

門檻不該用猜的。猜太鬆會漏掉真的退步；猜太緊會天天誤報，然後被所有人忽略 —— 後者比沒有門檻更糟，因為它訓練大家忽略紅燈。

`pnpm bench:variance` 先用 **Spearman 等級相關係數**把兩種變異分開，再推導門檻：

- **系統性漂移**（|ρ| ≥ 0.9）：數值隨時間單調變化，代表量測環境本身在變。**排除在推導之外** —— 這類問題要修根因，任何固定門檻遲早都會被走出去。
- **隨機散布**：真正的量測雜訊。門檻取「最差散布 × 2」，向上取整到 5 的倍數。

> 這個區分是修 bug 修出來的。初版只算「相對中位數的最大偏離」，無法分辨「上下亂跳 30%」與「一路單調爬升 30%」，於是在偵測到散熱漂移時建議把門檻調到 **70%** —— 那等於廢掉閘門。

### 演變

| 階段 | 最差散布 | 漂移 | 門檻 |
| --- | ---: | ---: | ---: |
| 單次執行、未停 shader 快取 | ~30% | — | 25% |
| median-of-3 + 停用 shader 快取（6 次） | 7.4% | — | 15% |
| 把最重的場景排第 3 位（5 次） | 13.3% | 4 項 | — |
| 場景改為由輕到重（後 4 次） | **19.4%** | **0 項** | **40%** |

### 40% 是很弱的閘門，這是這台機器的限制

它只抓得到大幅退步。要收得更緊，必須降低 session 之間的變異：

- 基準與比對兩邊都取**多個 session 的中位數**（成本：每次驗收 ×N）
- 或使用時脈穩定的機器（桌機、固定 GPU 時脈）

**這裡調高是因為量到的散布真的有這麼大，不是為了讓某次比對通過。** 兩者的差別在於前者有數據支撐且記錄了代價，後者沒有。

換機器或改變場景組成／順序後，必須重跑 `pnpm bench:variance` 重新推導。

### 機器狀態需要**兩個**參考值，因為一個有盲點

`cpuReferenceMs` 是純整數、資料全在 L1 的迴圈，只反映時脈與 IPC。那個選擇對「整台機器降檔」是對的，但它造就了一個盲點：**記憶體頻寬劣化時它完全沒有反應。**

實測漏掉一次：某個場景的 CPU p95 從 15.40 跳到 30.41（+97%），而同一次的 CPU 參考值是 **3.8 對 3.8** —— 一模一樣。比對因此認定可比較，報出一串假退步。後續四次獨立量測是 15.60 / 15.60 / 15.41 / 15.40，證實程式碼沒問題 —— **但閘門沒攔下來，那才是缺陷。**

十萬個物件的場景在串流數 MB 的 typed array，它受頻寬支配而不是 ALU。核心時脈不變但 uncore／ring 降檔、或其他行程在打 DRAM，都會讓場景變慢而整數迴圈毫無感覺。

所以加上 `memoryReferenceMs`：32 MB 緩衝區、步長一個 cache line、掃 16 遍、取五次最小值。任一個參考值偏離就拒絕比對。

#### 為什麼要掃 16 遍

單遍只要 1.6 ms，而 `performance.now()` 量化到 0.1 ms —— 量化雜訊足以讓閘門報出「1.5ms → 1.8ms，20%」而拒絕比對，機器根本沒事。

**明明沒事卻拒絕比對，跟假退步一樣糟**：兩者都會訓練人忽略這個訊號。掃 16 遍把量測拉到約 20–27 ms，量化就不再是主導項。

#### 容差由它自己的散布推導，而且有一件事還沒驗證

五次獨立執行的記憶體參考值：

```text
20.0   21.9   27.1   26.2   26.2      ← 全距 35.5%
```

所以容差是 **40%**（實測全距向上取整），與 `DEFAULT_THRESHOLD_PCT` 同一套推導。用 CPU 那邊的 15% 會讓閘門在多數執行上開火。

**還沒有證據的部分**：促成這個參考值的那次事件發生時這個欄位還不存在，所以「40% 的容差會不會攔下那一次」目前只是合理推測。要驗證得等下一次同型事件。

另一個讀法同樣沒有證據：這台機器的記憶體頻寬真的在跑次之間差 35%，而那正是整段量測工作一直在對抗的場景雙峰的來源。若是如此，真正的解法是換機器或固定時脈，任何門檻都只是繞過它。

### 閘門本身要被驗證會紅

一個從來沒有紅過的閘門，跟沒有閘門是同一回事 —— 它可能因為讀錯欄位、比錯基準、或把例外吞掉而永遠回報通過，而那種故障看起來跟「一切正常」完全一樣。

所以基準建立之後，注入了一個真實的退步（把 `RenderExtraction` 的視錐剔除短路掉）並確認它被攔下來。結果是**兩層獨立攔截**：

| 層 | 反應 |
| --- | --- |
| 場景 `verdict()` | `bench:compare` | `bench:compare` | 額外指出「基準含有某個場景，但這次沒有結果 —— 覆蓋範圍縮小了」 |

第三列比前兩列更重要。**一個嚴重到讓場景跑不完的退步，最自然的偽裝就是「這次沒有那個場景的資料」** —— 若比對只走「兩邊都有的指標」，那種退步會靜靜地通過。覆蓋範圍檢查堵的是這個。

還原之後重跑，全部回到 ok（最大偏移 −4.8%）。這與程式碼測試的紀律一致：改完要把修正倒回去，確認測試真的會紅。

## 已知限制

1. **合成資料**：量到的是硬體上限，不是真實場景。 選定情境（森林／城市／室內）後要補上真實資產場景，屆時 baseline 分兩組。
2. **只有一台基準機器**：Intel gen-12lp 內顯。分級門檻與參考常數都只依這一個資料點校準。
3. **session 之間的散布是 19.4%，門檻因此只能是 40%（弱閘門）。** 已用 10 次獨立執行確認，並靠場景重排消除了全部系統性漂移。收緊的路徑見上方「40% 是很弱的閘門」。
4. **per-pass GPU 時間不存在**：見 [02-diagnostics.md](02-diagnostics.md)。
5. **smoke profile 走 WebGL2**：`--enable-unsafe-swiftshader` 實測落到 WebGL2 而非 WebGPU-on-SwiftShader，所以煙霧測試**不覆蓋 WebGPU 專屬路徑**（compute、indirect draw、真實 device loss）。那些只能靠 `hardware` profile 驗證，CI 若只跑 smoke 會有這塊盲區。
6. **cold shader 編譯的絕對值仍受行程狀態影響**：停用磁碟快取後同一次執行內的三次重複已收斂到 ±0.9%，但在完全全新的機器狀態下曾量到 17,314ms（對比穩定後的 1,617ms）。可比較性在同一台機器上成立，絕對值不要當成使用者實際會遇到的數字。
