# 工程準則

這份文件不描述任何功能。它描述**判斷一件事該不該做、做完了沒有**的準則。

其他規格會過期，這一份不會 —— 每一條都是被實際的錯誤逼出來的，而那些錯誤
都有同一個形態：**看起來成功了。**

---

## 定位：這是一個會被裝到別人專案裡的**套件**

**先講這個，因為後面每一條都是從它推出來的。**

| 是 | 不是 |
| --- | --- |
| 一個 `npm install` 進**別人專案**的套件 | 一個我們自己跑的引擎執行檔 |
| 跑在**別人的機器**上 | 跑在這台開發機上 |
| 處理**別人的內容** | 處理我們造的程序化場景 |
| 畫進**別人的 `Scene`** | 自己開一個 Scene |

`apps/benchmark` 是**儀器**，`apps/example` 是**證明**。兩個都不是產品。
產品只有 `packages/three`，而它會落在一個我們永遠看不到的環境裡。

### 這個專案犯過的每一個大錯，根因都是同一個

> **把「我這裡」當成「全世界」。**

| 症狀 | 「我這裡」是什麼 |
| --- | --- |
| 做出跑得很快的 benchmark 而不是套件 | 我這裡跑得起來 |
| 用程序化資產量效能，連天花板也是 | 我這裡的內容 |
| 提議在開發機上掃出最佳值寫進套件 | 我這裡的硬體 |

三次都通過了當時所有的檢查，因為檢查也是在「我這裡」做的。

### 決定之前必須先答的一題

> **這個決定在別人的機器、別人的內容、別人的專案上還成立嗎？**

答案若取決於我的環境，它就**不能進套件**。套件裡的每一個數字只有三種
合法來源：

| 來源 | 為什麼合法 |
| --- | --- |
| **由內容推導** | 量測發生在使用者的機器上、對使用者的內容做 |
| **自適應** | 引擎觀察實際情況調整，而且輸出畫面不變 |
| **交出去當旋鈕** | 引擎講清楚它在權衡什麼，由開發者決定 |

**沒有第四種叫「作者在自己機器上調好」。**

### 基準與天花板都是開發用的儀器，不是產品的規格

`ceiling-*` 那三個場景量的是**這台開發機**的上限。它們存在的理由只有一個：
讓我判斷一個優化值不值得做。

它們**不進產品**：不影響套件行為、不出現在 API 上、不被寫成「這個引擎的
規格」。引用那些數字時一定要帶上機器與日期，否則下一個人會把它當常數。

`benchmarks/baselines/` 也一樣。它以機器指紋當檔名，換一台機器
`bench:compare` 會**拒絕比對**而不是給出垃圾數字 —— 所以它不影響套件的
通用性。

但它有一條不能跨的線：**基準只能用來跟自己比，不能當目標。** 一旦開始
「調到讓基準好看」，那就是替這台機器調校，也就是回到「把我這裡當成全世界」。
基準的用途只有一個：擋下退步。

## 〇、這個專案要解決的問題

> **Three.js 做得到 UE 做的那些事，但要開發者自己刻。這個專案把那一整套補上。**

用這個套件寫 Three.js，應該像遊戲開發者用 UE：**不必鑽進底層優化**，
因為套件已經做好了；而且它給你更多能力。每開一個新專案，起點就在巨人肩膀上。

### 分界線：交給它的用它的方式，沒交給它的完全不受影響

這個套件**不重包 Three.js** —— 那個工作量無邊無際，也不是目的。

| 領域 | 誰說了算 |
| --- | --- |
| 交給 `world` 的（大量放置、剔除、LOD、串流） | **套件的定義。** 選擇用它就接受它的方式 |
| 沒交給它的（角色、UI、後處理、控制器） | **完全不受影響**，原生 Three.js |

「相容」是指**第二欄不受干擾**，不是「第一欄要能吃任何形狀的輸入」。

想把任意既有的 `Object3D` 階層丟進來「自動變快」，那是魔法加速器 ——
它必須對使用者的結構做推測，而推測錯的症狀是「畫面少了東西」且毫無線索。

### 它不取代 Three.js

這是**硬約束**，不是偏好：

- 使用者原本的 `THREE.Scene`、`Mesh`、`Material`、loader、controls、後處理，
  **全部照樣能用**
- 採用是**漸進的**：一次把一塊吃重的東西交給引擎，不是全有全無
- 隨時可以掉回原生 Three.js

要用這套就得把專案重寫 —— 那是取代，不是強化。**如果一個判斷會讓現有的
Three.js 程式碼失效，那個判斷就是錯的。**

### 判斷 API 好不好的標準

> **一段原本用 Three.js 寫的邏輯，換成強化版要改幾行？**

理想是**一行** —— 把 `THREE.X` 換成 `WW.X`，參數與方法完全相同。

使用者不該需要認識 cell、lodSet、AssetId 這些字。它們是**內部
機制**，出現在對外介面上就是設計失敗。

### 內部與外部是兩回事

「Three.js 只能位於 renderer adapter 層」這條規則是對的 —— **引擎內部**要與
渲染器無關，資料才能排成 SoA、才能快。

但那是**內部**的規則。**對外要講 Three.js 的話**：你給我 `BufferGeometry`
和 `Material`，我處理。把內部規則套到對外介面上，等於要求使用者先把世界
翻譯成我的語言 —— 那正是這個專案想替他省掉的事。

### 每一層都是「用了更好，不用也能動」

這是最核心的一條，而且**每一個層級都要成立**，不只資產管線：

| 你做的事 | 結果 |
| --- | --- |
| 完全不用這個套件 | 原本的 Three.js，能動 |
| 用了，但不 cook 資產 | 能動 —— 套件替你產 LOD |
| 用了，但不開串流 | 能動 —— 內容全部常駐 |
| 用了，但某個物件不交給它管 | 能動 —— 那個物件走原生路徑 |
| 把 `WW.X` 換回 `THREE.X` | 能動 —— 一個字的差別，只是沒有優化 |

**套件永遠不拿走任何東西，只加東西。** 任何一層拿掉，剩下的照樣跑，
只是慢一點。

這條的反面是**分岔路**：一旦某個功能變成「用了就不能用原本的方式」，
它就違反了這個專案存在的理由。UE 讓你拖檔案進去就能用，優化是它
**替你做**，不是它**跟你要**。

### 同性質的東西，概念與層次不要差太多

使用者已經知道 `Mesh`、`Material`、`BufferGeometry`、`LOD` 是什麼。
**同一種性質的東西就用同一套詞彙**，不要無謂地另創一組 —— 發明一個
`Prefab` 型別只是讓他多學一個名字，而它表達的東西跟 `Mesh` 沒有本質差別。

反過來說，**套件真正擁有的領域可以有自己的概念**。串流的格子、可見性的
管理 —— 那些 Three.js 本來就沒有，硬套既有詞彙反而扭曲。

> 判準：**新概念要對應到真實存在的新東西**，不是同一件事的新說法。

**而套件獨有的能力會產生真實的前置依賴** —— 要串流就必須有格子、來源、
半徑。那不是設計失誤，是能力本身的要求。設計紀律是**把前置鏈壓到最短**：
單一物件的能力不該有任何前置（它是 `Object3D`，加進 scene 就運作），
跨物件的能力才需要共用上下文，而那個上下文用**發現**的而不是用**要求**的。

**缺前置時必須大聲說出缺什麼、少了它會怎樣** —— 靜默退化成沒有優化的
版本，會讓人以為自己在用強化版。那正是這個專案最常見的失效形態。

介面的具體形狀見 [api.md](api.md)。

## 一、引擎的定義

> **不管拿到多少資源，一點都不浪費。**

使用者有什麼硬體是**不可控的**，所以它不進引擎。引擎唯一能做的是：在現有
資源下把利用率推到極致。

### 降級是開發者的政策，不是引擎的行為

「使用者只有 XXX 時就少畫一點」——那是**應用開發者**的決定。引擎把資訊和
旋鈕交出去，然後閉嘴。

引擎自己決定降級，等於替開發者做主。`internal/platform-web` 偵測到的機器
等級是**給開發者的資料**，不是引擎的自動開關。

### 目標不是「弱機器看少一點」

好機器和弱機器應該看到**同一個精緻畫面**。差別只在弱機器本來就慢一點，
不是弱機器被餵了比較醜的東西。

### 一個決定是誰的？四問，依序

「引擎不能擅自決定」講得太寬 —— UE 自己決定的事非常多（LOD 選階、Nanite
的 cluster 剔除、串流順序），而那些都是對的。它不自己決定的是**畫質**與
**預算**。

分界的判準是：**做這個決定需要的資訊，誰手上才有？**

#### 一問：會不會改變畫面？

會 → **永遠是開發者的**，而且引擎要把成本算出來交出去。

UE 把 LOD 的螢幕尺寸放在每個資產上、Nanite 的像素誤差放在專案設定 ——
因為只有做那個資產、做那個遊戲的人知道意圖。

這一項與「省下的工 ≠ 降低的品質」是同一條線的兩面：畫面一模一樣的優化
是引擎的責任，畫面會變的是政策。

#### 二問：這是開發者早就知道的內容性質嗎？

是 → **要求宣告，引擎不猜。**

UE 的 Mobility 是最直接的對應：每個 actor 要標 Static / Stationary /
Movable。標了 Static 就享有烘光、預計算可見性、合進靜態繪製清單。**標了
Static 卻在執行時移動它，UE 不會偷偷換策略** —— 它警告，把那當成你的錯，
不是它該適應的事。

「內容是靜態還是動態」「這個網格要不要 Nanite」「碰撞要多精細」全部是宣告，
沒有一個是推論。**UE 不推論它本來可以被告知的事。**

沒宣告時取一個安全的預設，而假設被違反時**大聲說**（見四問）。

#### 三問：花的是開發者管的資源嗎？（幀時間、記憶體）

是 → **上限是開發者的，上限內的分配是引擎的。**

UE 的貼圖串流池大小是設定，池子裡先丟哪個 mip 是引擎的事。沒有人期待
開發者去挑要丟哪一階。

所以旋鈕的形狀是**上限**，不是策略。而上限的預設不能是作者訂的數字 ——
它要從觀測或內容推導（串流的幀預算是「這台機器安靜時的幀間隔 × 1.5」，
遠景合併的記憶體是「可合併的格數 × 一格的大小」）。

#### 四問：是純機制，而且給定內容只有一個對的答案嗎？

是 → **引擎自己決定，寫死，不給調。**

UE 的 Nanite cluster 固定 128 個三角形。暴露它只會讓人改壞。

但「寫死」不等於「隨手訂」：那個值仍然只有三個合法來源（見「決定之前必須
先答的一題」）。`HLOD_MIN_INSTANCES` 曾經是 4 —— 那是隨手訂的；正確的推導
是「省下的繪製次數要大於 1」，也就是 2。

### 引擎不得靜靜改變行為

四問之外還有一種情況：**畫面沒變、預算沒變，但行為變了，而開發者看不到。**

犯過的實例：矩陣連續 8 幀在變就關掉空間分割剔除。那既不是畫質也不是預算，
是引擎自己判定「你的內容是動態的」然後拿掉一個優化 —— 而且門檻是我訂的、
通知只有一行 console。

UE 對這種情況的處理是兩段的：

| | |
| --- | --- |
| 事先知道的 | **要求宣告**（Mobility），執行時發現不符就警告，不改策略 |
| 只有執行時才知道的 | 照樣降級，但**吵得不可能沒被發現** —— 貼圖串流池爆掉時，開發版會在畫面上印紅字 |

所以規則是：

1. **可以宣告的就要求宣告**，不要用觀察去推論。推論錯的時候沒有人知道。
2. **真的只有執行時才知道的**（池子爆了、worker 起不來），降級可以，但要
   吵到不可能漏掉，而且要能從 `stats` 讀到，讓程式也判斷得出來。
3. **無論哪一種，開發者都要能覆寫。** 宣告了就不猜。

> 判準：**如果某個行為變化只有讀 console 才知道，那個設計就是錯的。**

那個實例照這三條改完長這樣（`options.dynamic`）：

| | |
| --- | --- |
| 宣告 `true` | 不建格子。**不猜也不警告** —— 宣告過的事引擎不再有意見 |
| 宣告 `false` | 永遠用格子。矩陣真的在動就警告宣告錯了，但**不換策略** |
| 省略 | 當靜態。**量到**重建比它省下的走訪還貴才暫停，說出來，矩陣停下來就恢復 |

門檻消失了：省略時的那個判斷是「這台機器上剛剛花掉的重建時間」對「沒被
走訪到的 instance 數 × 實測的每個 instance 走訪成本」。兩邊都是使用者
環境的實測值，所以它在別人的機器上也成立 —— 那正是「由內容推導」與
「作者在自己機器上調好」的分野。

## 二、四格模型

優化只有兩層，乘上兩端：

| | **演算法層**<br>不做多餘的工 | **機制層**<br>必要的工做得便宜 |
| --- | --- | --- |
| **CPU** | 剔除、LOD 選擇、空間分割、串流 | 增量更新、多執行緒、SIMD、避免重傳 |
| **GPU** | 遮擋剔除、HLOD、impostor | 繪製合併、shader 成本、buffer 生命週期 |

**做完一格不等於做完。** 這份文件寫下來的當下，四格只有左上填了。

### 兩層的差別

- **演算法層**：想清楚就能做。決定「哪些東西要處理」。
- **機制層**：要把每一個位元的搬動都摳出來。決定「決定好之後，多便宜地處理」。

演算法層做完之後很容易產生「做完了」的錯覺，因為場景時間確實大幅下降。
但那只是把工作量除以一個常數，每一件剩下的工作仍然是用最笨的方式做的。

### 具體的檢查方式

問這三個問題，任何一個答不出來就是機制層沒做：

1. **這個資料上一幀算過嗎？算出來一樣嗎？** 一樣就不該重算。
   （實例：靜態物件每幀從 TRS 重組 4×4 矩陣，而它三分鐘沒動過。）
2. **走訪的順序與資料的排列順序一致嗎？** 不一致就是每次都快取失誤。
   實例：包圍球快取依 instance 編號存、走訪依空間格順序走 —— 六萬個時
   看不出來（快取 960 KB，塞得進 L2），一百萬個時每個 instance 從 37 ns
   變成 **146 ns**。**這種問題只有在大工作量上才出現。**
3. **這件工作只有一顆核心在做嗎？是純量的嗎？**
   （瀏覽器有 Worker，WASM 有 SIMD。矩陣組裝是教科書等級的 SIMD 題目。）

## 三、省下的工 ≠ 降低的品質

引擎該消滅的是「**畫面看不出差別，但機器要付錢**」的工作。

剔除、LOD（用螢幕空間誤差綁住上限）、instancing、合批、遮擋 —— 共同點是
**畫面一模一樣**。那是優化。

降低解析度、簡化 shader、減少物件數 —— 那是**降低品質**，屬於政策。

把兩者混在一起談，會讓「優化」變成「找地方偷工」的藉口。

### 品質契約要寫下來並守住

LOD 的品質契約是「幾何誤差投影到螢幕上 ≤ 2 像素」。

正因為有這個上限，cook 時的 LOD 鏈才可以做得很粗 —— 誤差再大也不會被選中。
反過來說，**任何想把 2 像素放寬來換效能的提議，都是在掏空整套論證**，
不是優化。

### 契約要連它管不到的東西一起寫下來

「幾何誤差 ≤ 2 像素」綁的是**頂點位置**。它**不綁法線、不綁著色**——
簡化過的網格法線會變，而位置誤差的上限對那件事完全沒有約束力。

實測（`apps/example`，60,000 個 instance，640×360）：±2 像素鄰域內找不到
相符顏色的像素佔 0.307%，而那些像素處的影像梯度是全域平均的 **8.6 倍**
—— 差異集中在輪廓，不是區域著色。目前這個缺口沒有咬人。

寫下來的理由不是它現在有問題，而是**契約沒講到的部分，日後一定會被
當成契約有講**。一句「畫面一模一樣」比一個數字危險得多。

## 四、量測的紀律

### 1. 測試內容決定所有後續決策

用不具代表性的內容量測，會讓**每一個**決策往錯方向走。而且最惡劣的形式是：
你會用自己造成的錯誤結論，去否決正確的路。

量到的兩個差距（2026-08-17，都是同機器同一輪）：

| | | |
| --- | ---: | --- |
| 索引 vs 非索引幾何 | **3.35 倍** | 同一份幾何，唯一差別是有沒有焊接。真實資產一律是索引的，`IcosahedronGeometry` 不是 |
| 真實 PBR 材質 vs 無貼圖 | **1.72 倍** | DamagedHelmet 285,000 三角形/ms，天花板場景 490,100 |

兩個相乘接近六倍，而且方向相反地錯：非索引讓幾何看起來比較貴，無貼圖讓
材質看起來免費。**在那種內容上量到「GPU 沒問題、CPU 是瓶頸」，於是連續
好幾輪都在修 CPU，還用同樣的理由否決了遮擋剔除與 GPU 驅動繪製。**

（此處原本寫著「程序化石頭的 GPU 成本是真實資產的 1/21」。repo 裡沒有任何
量測撐著那個數字，而重新量出來的是上面兩項 —— 一個沒有來源的數字正是
第 7 條在講的東西。）

**所有效能結論都必須註明它是用什麼內容量的**，天花板也一樣。

### 2. 幀時間會飽和，容量不會

幀時間有下限 —— 顯示器的更新率。這台機器上空場景也是 6.10 ms，所以任何
把幀時間壓到那附近的內容，之後的優化都**看不出來**：數字不動，而你分不出
「已經沒得優化」與「優化了但被上限吃掉」。

所以主要指標是**容量**：維持流暢的前提下放得了多少東西。它不會飽和，
永遠有下一個量級可以問，而且那正是「這個套件讓開發者多做到什麼」。

而且要**掃一串工作量，不是量一個**。實測：250,000 個 instance 一切完美，
一百萬個卻掉到 100.85 ms —— 而原因是遠景合併的記憶體預算是「全有或全無」，
超過就整個關掉。只量 250,000 那一點的話，那道懸崖看起來不存在。

**預算與上限一律要平順降級，不能是懸崖。** 用到為止、剩下的走原本的路，
而且說出來涵蓋了多少。

### 3.「哪個比較大」不是「該修哪個」

CPU 與 GPU 的佔比取決於這台機器加這組內容。照佔比決定工作順序，等於替
某一台機器調校。

**兩端各自都要到它自己的極限。**

### 4. 沒有分項天花板就不能說「到極限」

場景時間是**兩端相加**。要說任一端到了極限，必須有它單獨的上限數字：

- CPU：每毫秒能處理多少物件（完全不畫）
- GPU：每毫秒能吃多少三角形／繪製呼叫／像素（CPU 不參與）

沒有這兩個數字，就不知道離極限還有多遠，也無法判斷下一個優化該不該做。

**而天花板本身也是用某種內容量出來的。** 第 1 條同樣適用於它 —— 只是後果
更嚴重：一個偏低的天花板會讓你以為已經接近硬體極限，於是**停在不該停的
地方**，而且停得理直氣壯，因為手上有數字。

實例：`ceiling-gpu-triangles` 原本用 `IcosahedronGeometry`，那是**非索引**的
（每個三角形三個獨立頂點）。於是它量到的是頂點吞吐，卻被當成三角形吞吐
報出去。真實資產一律是索引的（Avocado 682 個三角形只有 406 個頂點）。

所以天花板要**連量它的內容一起報**，而且盡量報成不會被幾何形狀左右的
單位 —— 現在同時報三角形／毫秒與頂點／毫秒，兩個數字擺在一起就藏不住
「這份幾何的頂點三角形比是多少」這件事。

### 5. 先量再做

至少三個規劃好的系統被量測否決過（螢幕尺寸剔除、HZB、LOD 分批更新），
其中一個做完之後讓幀時間從 25.10 變成 74.80 ms。

**規劃不是證據。**

### 6. 驗證測試會紅

修好之後把修正倒回去，確認測試真的變紅。一個從來沒紅過的檢查跟沒有檢查
是同一回事 —— 它可能因為讀錯欄位、比錯基準或吞掉例外而永遠回報通過，
而那種故障看起來跟一切正常完全一樣。

同樣適用於 benchmark 的閘門：注入一個真實的退步，確認它被攔下來。

**但注入只證明檢查對它走過的路是敏感的。** 檢查沒走到的那條路，注入也不會
紅 —— 而那正是最危險的地方，因為儀表板是綠的。

package-check 就是這樣放走一個 bug：worker 的 URL 被建成絕對路徑，在任何
使用者的站台上都是 404，但檢查用 `autoLod: false`，剛好繞開唯一會壞的那條路。
在那個版本上做注入一樣是綠的。

所以每加一個檢查要問兩題，不是一題：

1. 缺陷注入回去，它會不會紅？
2. **它走的是會壞的那條路嗎？** 環境跟使用者的一不一樣？

第二題常常答錯，因為錯的環境也「跑得起來」：Node 裡沒有 `Worker`，所以一定
走退路；直接讀 `node_modules` 的話，worker 的兄弟檔案永遠找得到，而真實部署
裡 `node_modules` 不會上線。兩種都會通過，也都什麼都沒驗到。

### 7. 錯的資訊比沒有資訊更糟

- 過期的警告（說某個東西被丟棄，但它其實已經支援了）
- 把別人的工作記在自己頭上的計時器（`admit` 的 0.984 ms 有 98% 是呼叫端的）
- 標籤錯的統計（把貼圖算進「mesh 位元組」）

這三種都會把後續的判斷引到錯的地方，而且比缺少那個數字更難察覺。

**任何跨越 API 邊界的計時都要問一次：這段時間是誰花的？**

### 8. 只印出來、沒有擋的數字，等於沒有檢查

`site-check` 一直在印 `apps/example` 的 JS heap，但沒有任何一條會因為它失敗。
於是它從記錄裡的 13.8 MB 漲到 165 MB，再漲到 **1,005 MB**，而三個檢查全綠。

儀器有兩個工作：**量**與**擋**。只做前者的話它只是一行風景 —— 沒有人會每次
去比對上一次的輸出，尤其在其他數字都變好的時候。

> 判準：**每一個報出來的指標都要有一條會讓它失敗的線**，否則就不要報。

上限本身可以是政策（網站的記憶體預算不是引擎常數），但那條線必須存在。

寫下這一條之後回頭審自己的儀器，`site-check` 還有兩個是只印不擋的：下載
總量（只擋了主 script）與 GPU 物件數。而後者正是這一輪其中一個 bug 的
形狀 —— 槽位池每次重建都重配，GPU 記憶體三秒漲 90 MB，幾何數一路往上，
三個檢查全綠。**寫下規則跟套用規則是兩件事。**

### 9. 只在同一個效能模式內比較

這台機器的量測是**雙峰**的 —— 同一份程式碼會落在兩個相差近兩倍的狀態。
跨模式比較會得出完全相反的結論，而兩邊都是拿不同母體在比。

A/B 必須**交錯**執行，不能連續跑完一組再跑另一組。

## 五、比較對象

不是「我的筆電跑幾 fps」。是：

> **UE 這類引擎內建給你的東西，Three.js 做得到但要開發者自己刻。
> 這個專案就是把那一整套補上。**

所以「做完了沒有」的判準是清單，不是數字：自動 LOD、剔除、空間分割、
串流、資產管線、剖析 —— 以及還沒做的遮擋剔除、GPU 驅動繪製、impostor、
虛擬貼圖、成本可控的材質系統、叢集 LOD。

## 六、這些準則是怎麼來的

每一條都對應一次實際的失敗，而失敗的形態高度一致：

| 形態 | 實例 |
| --- | --- |
| 看起來成功了 | 10 個資產全部烘焙成功、零警告，而骨骼、貼圖、頂點色全被靜默丟棄 |
| 數字很漂亮因為世界是空的 | 代理環該有 340 個 cell 只填了 72，佇列積著 206 個 |
| 局部指標很好、總帳很爛 | LOD 分批更新省了 2.6 ms CPU，換來 71 ms GPU |
| 註解宣稱的事從來沒被測過 | 「遠超過任何實際世界」，而該座標實際會溢位 |
| 只會讓畫面偶爾破洞 | 22 萬個物件裡 11 個被錯誤剔除，所有時間指標完全正常 |

**共同點：沒有任何一個會讓程式報錯。**

所以檢查的重心永遠放在「這件事錯了會怎樣」，而不是「這件事對了會怎樣」。
